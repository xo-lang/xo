# Rune class lookups: an unchecked binary search and one ASCII compare, 13% off the classes row, 2026-10-24

Every Rune class method (`Rune.is_letter`, `is_symbol`, `is_punct`, ...)
dispatches ASCII first, then a bitmap for U+0080 to U+07FF, then
`unicode.in_ranges`, a binary search over a sorted table (LETTER has
657 ranges, so 10 steps; a row's call reads `mov x2, #657`).
`bench/perf/unicode`'s classes row runs all 13 predicates over
`(ASCII + MIXED)` repeated 1,000 times, so both the ASCII test and the
search are on the hot path.

## The change

`std/native/llrt/unicode.xo`, two pieces:

`in_ranges` took its midpoint with a signed division and a checked add,
`m = lo + (hi - lo) / 2`, and looked up `k = m * 6`, `k + 3` and
`lo + 1`. `lo` is at most `hi`, at most `n` (at most 3,950, and 12
steps), so nothing in the loop can overflow, but the base compiled each
step with its check:

    sub x9, x2, x11 ; add x9, x9, x9, lsr #63 ; asr x9, x9, #1   // (hi - lo) / 2
    adds x12, x11, x9 ; b.vs fault                              // m = lo + ...
    mul x10, x12, x13 ; smulh x9, x12, x13 ; cmp x9, x10, asr #63 ; b.ne fault
    adds x9, x10, #3 ; b.vs fault                               // k + 3

Checked arithmetic is `adds`/`b.vs` for a sum, and for a product a
`mul` with `smulh` and a comparison against the sign extension. With
`lo.wrapping_add(hi).shr_logical(1)`, `m.wrapping_mul(6)`,
`k.wrapping_add(3)` and `lo.wrapping_add(1)` the same iteration is:

    add x9, x10, x2 ; lsr x12, x9, #1 ; mul x11, x12, x14
    ldr x9, [x13, x11] ; and x9, x9, #16777215
    cmp x3, x9 ; b.ge next
    mov x2, x12 ; cmp x10, x2 ; b.lt top

7 instructions less along the smaller half (19 to 12) and 8 along the
larger (25 to 17), for the bounds the loop invariant states: the two
sides of a midpoint of `0 <= lo <= hi <= n`.

`is_letter` tested the ASCII letters as two ranges, `97 to 122` and `65
to 90`. Upper and lower case differ only in bit 5, so `r | 32` covers
both in one unsigned range compare, and the test now comes after the
`r >= 0x80` dispatch, so a rune above ASCII pays the same two compares
as before and an ASCII letter pays 6 instructions instead of 8:

    cmp x0, #128 ; b.lt ascii
    cmp x0, #2048 ; b.ge table
    ... bitmap ...
    ascii: orr x9, x0, #32 ; sub x9, x9, #97 ; cmp x9, #25 ; cset x0, ls

The one sided form `(r | 32) - 97 < 26` is wrong in Xo: `-` is signed
and checked, so it prints as `subs` + `b.vs` (a fault path) followed by
a signed `cmp`/`cset lt`, and a control byte such as 1 reads as a
letter (`33 - 97 = -64 < 26`). The two sided test on the folded value
is the form that compiles to one unsigned compare.

## A/B, one revision, A = origin/main, B = the change

`xo bench --ab`, 10 rounds, both sides building the same
`bench/perf/unicode` source with their own xo and std. B/A below 1.0 is
better.

| workload | A instructions | B instructions | B/A | A wall ms | B wall ms | B/A |
|---|---|---|---|---|---|---|
| classes (13 predicates over ASCII and mixed text) | 581,069,482 | 505,469,755 | 0.870 | 38.11 | 35.65 | 0.936 |
| latin1 (all 256 runes: ASCII and the bitmap only) | 37,647,456 | 37,590,469 | 0.998 | 5.603 | 5.583 | within noise |
| fieldsfunc (split_where on `is_space`, which this does not touch) | 209,405,796 | 209,420,393 | 1.000 | 18.88 | 18.68 | within noise |

The checksums are identical on both sides (`classes` 129070000,
`latin1` 2838200, `fieldsfunc` 4640000). The two controls confirm where
the gain comes from: `latin1` (all 256 runes, so the bitmap and never
the search) and `fieldsfunc` (is_space, untouched) stay at 1.000.

Attribution, each variant measured against that same base on classes:
`in_ranges` with `shr_logical` alone (still a checked add) is 0.902;
adding the `is_letter` fold, whose ASCII test is placed first there, is
1.003 on its own (a rune above ASCII paid its extra compare, 0.3% more),
0.889 with the two; and putting the `r >= 0x80` dispatch first, with
`wrapping_add` for the midpoint, is 0.870. `latin1` moved 0.5% the
wrong way with the first fold (it pays four instructions for a
non-letter) and is 0.998 in the final form.

## What is left in the loop

`is_letter` still sets up every `in_ranges` call with five
instructions (`adrp`/`add` for the table, the range count for LETTER
and the table's end) and `in_ranges` is not inlined at any of its four
call sites. The loop also repeats its `lo < hi` test at the end of each
arm, and the two `u24` reads could come from one load
(`rt.bytes_word(t, k)`, `hi` from a shift by 24). A two level index
table (a 16 bit entry per 4,096 rune block pointing at the first
candidate range) would cut LETTER's 10 steps to a load and a scan of
one or two ranges, which is the larger change and is not in this
commit.

`is_space`'s ASCII set is not an `(r | 32)` range: it is
`cmp #32`/`b.ne` then `sub #9`/`cmp #4`/`cset ls`, 7 instructions.
`is_symbol`'s ASCII set is nine scattered values tested in a chain of
six compares and branches; a 64 bit mask per half of ASCII would be
about 8 instructions but is a wash on text whose symbols are mostly
above U+0080, and it is not in this commit.

## Coverage

The `runes` corpus (every Rune class method against Go's `unicode` and
`strconv` over all of them), `where`, `trimchars`, `regexp` (which
searches class ranges of its own but shares the predicates), `bytes`
and `strings` on arm64 and llvm; the wasm goldens (TestSelfhostWasm);
and the full fixed point (s1 = s2 = s3, identical assembly and
binaries), since `std/native/llrt` is in the fixed point set.
