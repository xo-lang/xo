# Xo against Go on the network side (2026-10-22)

One table of tonight's measurements of Xo's servers and client against Go's
(net/http, crypto/tls, gorilla/websocket), for the owner and the website to
cite. Every figure below was measured; nothing is estimated. Each row gives
its source, date, machine state, and commit.

All runs are linux/arm64 in Docker Desktop on the Mac (12 CPUs; servers
pinned to cores 0-5 and the load generator to 6-11 for the tlsrate and CRUD
rows), the native arm64 backend. Xo / Go means Xo's rate over Go's (higher is
better for Xo) unless the column says time or CPU (lower is better for Xo).

**Machine state.** "Quiet" is the lead's quiet window (2026-10-22 03:39 to
04:30, load average 5 to 9 on the 12 core Mac: the other agents' gates
paused, not an idle machine). "Loaded" is a run with gates or soaks running
(load 7 to 25): its absolute numbers swing by 2x between rounds (the same Go
server measured 2,958 and 3,495 MB/s of bulk TLS in two runs), so those rows
give ratios inside one round only, and the ratio range is the spread of the
rounds.

| HTTP/2, 256 MiB download | 0.74 / 0.69 |

Xo's own AES-GCM TLS 1.3 bulk rate in this run, 1,830 and 1,910 MB/s, matches
the quiet Docker measurement of the same code (1,830 and 1,858 MB/s, bulk TLS
1.3 with our own client, `bench/perf/tlsrate/client -mode bulk -tls 13 -size
268435456 -reps 3`, medians of 3 reps, 2 rounds, commit `b9092b2b6^`; the
fused loop `93f258200` against its parent: 1,863 / 1,854 against 1,577 /
1,627). That harness has no Go server, so no ratio is given from it.

Why the AES-GCM rows are behind: Go's `gcmAesEnc` runs CTR and GHASH
interleaved over 8 blocks; Xo's fused loop does it per 64 byte chunk. A NEON
`cpu.ghash4` attempt (decision 0339, `b9092b2b6`) cut instructions 12.6% but
lost 24% of the throughput on the loop (a 16 byte load spanning two 8 byte
stores cannot be forwarded on Apple cores), and was reverted (`344764528`);
a half-load version is with Xo Lang 4.

## WebSocket echo (gorilla/websocket server and client in Go)

Source: `bench/perf/netgo/ws` (this commit); Xo's server is
`bench/websocket/autobahn/server`. 2026-10-22 04:33 to 04:37, loaded
(load 11 to 21), main `2719f79a0` (Xo built by xobuild key
e272789d4fd679ed). Messages per second, the Go load client (`cli`, N
connections each sending one message and reading its echo), two to five runs
of 3 to 5 s per configuration; ratios only.

| configuration | Xo / Go |
|---|---|
| 1 connection, 64 B | 0.77 (median of 5 alternating runs: Xo 21.9k, Go 28.4k msgs/s) |
| 16 connections, 64 B | 1.05 and 1.63 (2 runs) |
| 16 connections, 4 KiB | 1.21 and 1.42 |
| 4 connections, 64 KiB | 0.83 and 1.64 |

`strace -f -c` per message, 1 connection, 64 B (33,000 messages): Xo sendto
1.0, read 1.02, epoll_pwait 1.8, futex 0.12; Go write 1.0, read 1.0,
epoll_pwait 0.7, futex 0.01, nanosleep 0.12. std/websocket is
syscall-minimal; the excess is the netpoll poller's wakes (the same
epoll_pwait count appears on plain HTTP/1), which the lead has passed to Xo
Lang 2. The one row below Go is this single-connection round trip.

## HTTP client, keep-alive GETs

Source: `bench/perf/netgo/httpclient` (this commit) with
`bench/perf/httpclient/serve`; Xo's client is
`bench/perf/httpclient/main.xo`, Go's an `http.Get` loop with
`io.ReadAll`. 2026-10-22 04:35, loaded, main `2719f79a0`. 20,000 requests on
one kept connection to the same Go server, 3 runs per cell, medians; time is
wall seconds, "Go time / Xo time" above 1 means Xo is faster.

| workload | Xo wall (user / sys) s | Go wall (user / sys) s | Go time / Xo time |
|---|---|---|---|
| /len (256 B body) | 0.78 (0.22 / 0.33) | 0.87 (0.30 / 0.24) | 1.12 |
| /chunked (4 KiB, 32 chunks) | 0.91 (0.25 / 0.35) | 1.05 (0.44 / 0.30) | 1.15 |
| /big (64 KiB) | 1.12 (0.30 / 0.49) | 2.13 (0.77 / 0.65) | 1.92 |
| /redirect (302 then /len) | 1.72 (0.41 / 0.66) | 1.83 (0.61 / 0.54) | 1.06 |

Xo uses less user CPU on every row and more system CPU on /len and /chunked.
Syscalls per request on /len (strace -c -f, 5,000 requests): Xo sendto 1,
recvfrom 1 (EAGAIN), read 1, epoll_pwait 2.0; Go write 1, read 1 (EAGAIN),
read 1, epoll_pwait 1.06: the extra poller wake again.

## CRUD server (bench/perf/http)

Source: `bench/perf/http/listlock-docker.sh XO OUT HEAD` with LOADS=mixed
(`loadgen`'s CRUD cycle, 64 preloaded users, a list every 8th cycle), 1024
connections, 3 rounds of 10 s; the script builds an "old" and a "new" server
of each kind, here both from `2719f79a0`, so each round has two samples per
server. 2026-10-22 04:47 to 04:50, loaded (load 23 to 25); ratios only.

| | requests per second, 6 samples (low to high) | median | CPU per request, median | peak RSS |
|---|---|---|---|---|
| Go | 54.2k 56.9k 63.9k 81.6k 84.7k 105.6k | 72.8k | 33.8 us | 66 to 78 MB |
| Xo, before `d08537802` | 58.6k 64.5k 66.7k 69.3k 70.3k 75.3k | 68.0k | 28.0 us | 2.14 to 2.22 GB |
| Xo, after `d08537802` | (same run, same throughput within noise) | | | 47 to 60 MB |

Xo / Go: 0.93 by the medians, with the Go samples spanning 54k to 106k, so the
ratio is not resolved better than "within noise of parity". CPU per request is
0.83 of Go's (28.0 against 33.8 us). Xo's peak RSS was about 30 times Go's:
each live fiber's 64 MiB stack held a 2 MiB transparent huge page (THP
`always`), 2.2 MB per connection; `d08537802` marks the stacks
MADV_NOHUGEPAGE and the same run gives 47 to 57 MB at 1024 connections (60 MB in `scripts/docker-rss-guard.sh`, the hourly check, bound 150 MB) (64
connections: 21 MB against 158 MB), throughput unchanged within noise
(gotchas/fiber-stacks-huge-pages.md).

Earlier on the same server: decision 0291 (`knowledgebase/decisions/
0291-native-map-log-and-fork.md`, 2026-10-21, same method, medians of 3
rounds of 10 s, Docker, loaded): Go 89,846 / 74,478 / 107,522 req/s against

`f3d13232`): 0.84, 0.94, 0.77. `http-list-under-lock-2026-10-21.md`

Xo / Go: 0.92, and the Xo samples span 2% where the loaded run's Go samples

computing more, so a CPU profile will not find it: the investigation uses the
scheduler's park and wake counters (`XO_RTSTATS=1`).

## What is open

- AES-GCM bulk: 0.70 of Go on TLS 1.3 and 0.4 to 0.5 on TLS 1.2 after `75dd849d6` and `696511527` (aesgcm-2026-10-22.md); the fused CTR, AES and xor kernel (Xo Lang 1) is next.
- CRUD mixed: 0.92 of Go on a quiet machine with equal CPU per request; Xo waits (wake latency), under investigation.
- HTTP/2 download: 0.61 to 0.67 of Go on the quiet run. Not a regression:
  the same Docker container, Go and Xo servers interleaved (load about 10),
  Go 1,194 to 1,377 MB/s against Xo 798 to 822 at `f0aae00e5` (2026-10-21),
  791 to 818 at `7f6e6c203` and 927 to 993 at `2719f79a0`; the 2026-10-21
  "parity" was a loaded Go round. The server is not CPU-bound (1.2 s of CPU in
  2.8 s of wall on 6 cores) and sends the same number of times as Go (32.3k
  against 32.8k writes of 8 KiB per 256 MiB, paced by the receiver); it makes
  1.08 epoll_pwait calls per send against Go's 0.57, and 0.38 futex calls
  against 0.30: the poller's wakes, as in the WebSocket and HTTP client rows.
