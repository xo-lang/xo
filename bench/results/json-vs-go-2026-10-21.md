# std/json and std/multipart against Go's packages (2026-10-21)

Native Xo (`--backend=arm64`) and the Go backend (`--backend=go`) against
the same program written against Go's `encoding/json` and
`mime/multipart` (go1.26.1), on the development Mac (Apple M4 Pro, 12 cores,
24 GB, macOS 27.0). xo built from main at d5b915869 (std from the same tree).

## Method

- One workload per program, written twice: the Xo program (std/json,
  std/multipart) and a Go twin with the same data, the same loops, and the
  same output. Each program takes a mode: `none` builds the data and exits,
  `dec`, `enc`, or `run` does the timed loop as well.
- The metric is instructions retired (`/usr/bin/time -l`), the median of 5
  runs, minus the median of 5 `none` runs of the same binary (the setup:
  process start, data building). Wall time is reported the same way (median
  minus setup). Instructions are used because the machine was loaded by other
  agents' jobs (load averages 22 to 36 on 12 cores during the runs), which
  makes wall time unreliable; the ratios are instructions.
- The runs were interleaved (repetition, then mode, then implementation).
- `Go` is the Go twin built with `go build`; `native` is the arm64 binary;
  `Go backend` is the same Xo program built with `--backend=go` (Xo std/rt
  code for json and multipart there).

## Workloads

- **small**: one 115 byte document decoded into a struct (7 fields: an Int, a
  Str, a list of three Strs, a Float, a nested object of an Int and a Bool,
  an optional Str that is null), 200,000 times; the same struct encoded
  200,000 times.
- **big**: 10,000 records of that struct (a 1.46 MB array), decoded 10
  times, and encoded 10 times.
- **stream**: 10,000 such records as top level values, one per line (1.4 MB),
  fed in 4096 byte chunks to the streaming decoder (`json.decoder()` with
  `write` and `finish`; Go's `json.NewDecoder` over a 4096 byte reader into an
  `any`), 10 times.
- **multipart**: a body of three parts (one with a file name and a content
  type) parsed 100,000 times (`multipart.parse`; Go's `NewReader` with
  `NextPart` and `io.ReadAll`).

## Results (instructions, millions; ratio to Go's package)

| workload | Go | native | native / Go | Go backend | Go backend / Go |
|---|---|---|---|---|---|
| small decode | 5,126 | 1,710 | 0.33 | 2,418 | 0.47 |
| small encode | 1,186 | 514 | 0.43 | 930 | 0.78 |
| big decode | 2,741 | 874 | 0.32 | 1,396 | 0.51 |
| big encode | 544 | 219 | 0.40 | 488 | 0.90 |
| stream decode | 2,540 | 1,251 | 0.49 | 9,027 | 3.55 |
| multipart parse | 4,215 | 4,853 | 1.15 | 6,577 | 1.56 |

Wall time over the same runs (seconds, setup removed, on the loaded
machine): small decode 0.59 Go, 0.18 native, 0.21 Go backend; stream 0.34,
0.26, 1.36; multipart 1.06, 1.32, 1.01.

An earlier run of the wall-clock programs on the same machine, with the same
direction: small decode 292 ms Go against 90 ms native; big decode 150 ms
against 48 ms; stream 142 ms against 71 ms (medians of 5, 2026-10-21 18:22).

## Findings

- Native json decodes in a third and encodes in about 0.4 of the instructions
  of Go's `encoding/json` on these workloads, and the streaming decoder in
  half.
- Native multipart parse is 15% more instructions than Go's package (a run
  under load first read 2.4 times; the instruction count is the figure).
- The Go backend's streaming decoder (std/rt/jsonstream.go) takes 3.55 times
  Go's instructions; the next section of this file records the fix.
- Native cost ranking, `XO_PROF=cpu`, small decode: jsontext.scan 26% (cum),
  num.parse_float_at 8.5%, string building (obj.reserve and rs_append) 15%,
  jsontext.find 10%, str_end 7%; stream: json.value_end 23% flat, value_at
  48% cum, same_key 11%.

## Reproducing

The programs are the workloads above, `os.env.args()[0]` / `os.Args[1]` as the
mode. Build the Xo one with `xo build --backend=arm64 -o native.bin .` (and
`--backend=go`), the Go one with `go build`, then for each mode and
implementation five times `/usr/bin/time -l ./bin MODE` and read
`instructions retired`.
