# Native arm64 backend: closing the gap to LLVM (2026-10-08)

Question: the native arm64 backend (decision 0049) ran interp at 1.23x
of the LLVM backend, sort at 1.15x, strings at 1.10x. What in the code
costs that, and can the backend reach interp within 1.05x of LLVM with
no other bench program slower?

Answer: yes. interp now runs at 0.70x of LLVM (83.4 to 47.9 ms), sort
at 1.09x, strings at 0.99x; no program got slower. Three changes paid,
two hand experiments did not. Host: Apple M4 Pro, darwin/arm64, Go
1.26.1, Apple clang 21.

## Method

`bench/perf/llvm/native.sh` with `STAT=median REPS=5` (new: the median
of the interleaved runs instead of the best), once with the compiler of
the branch point (`cfb86dc`, "before") and once with the final commit
("after"), back to back at load average 6 to 8 (the host was shared with
another agent's builds). Each change was measured on its own against
the previous step with a private script running LLVM, before, and after
binaries interleaved, 7 to 11 runs, median; changes worth less than the
noise (about 1 percent) were dropped. Ideas were first tried by editing
the generated `.s` by hand and linking with `cc -O2 prog.s xo_rt.c`.

## What paid

| Change | Program | Before ms | After ms | LLVM ms |
|---|---|---|---|---|
| Compare chains laid out as a run of tests (`jumptab.go`) | interp | 80.7 | 54.9 | 65.1 |
| Jump table for matches of 8 or more values (decision 0051) | interp | 54.9 | 44.5 | 65.1 |
| Branchless select of a compare picked by another compare (`selectCompares`) | sort | 249.7 | 237.2 | 215.8 |
| Retain of a variant payload cancelled against the release of its enum (`cancelRC`) | strings | 36.4 | 34.8 | 34.5 |

1. **interp**: LLVM's code for the dispatch is a binary search tree of
   compares; ours was a linear chain whose failing tests were all taken
   branches, because reverse postorder puts each arm between two tests.
   Laying the chain out contiguously was most of the win; a jump table
   took the rest. The threshold (8 values) comes from synthetic
   matches over random tags, where the table lost at every size from 4
   to 16 arms (`gotchas/arm64-match-dispatch-prediction.md`).
2. **sort**: `less` (`if a.key != b.key { a.key < b.key } else { a.id <
   b.id }`) branched on key equality, which mispredicts on the many
   equal keys of the sort's last levels. LLVM computes both compares
   with `cset` and picks with `csel`; `selectCompares` does the same for
   any branch on a compare that only chooses between two compares.
   A companion pass, `reuseFlags`, drops a compare whose only
   predecessor ended with the same compare (no measurable time, one
   instruction less per iteration).
3. **strings**: `if let Some(w) = words.pop()` retained `w` (inline
   increment) and released the `Option` (a call into a generated drop
   helper that decremented `w` again) on every iteration. When a block
   runs only for one variant (its predecessor branches on the tag) and
   that variant has one counted field, the pair cancels.

## What did not pay (dropped)

- **ldp/stp pairing** of adjacent loads and stores (a text peephole):
  sort 1 percent faster, nbody 1.2 percent slower (pairs of `d`
  registers); integer only: within noise. Dropped.
- **Loop rotation** of sort's inner loops by hand: 50M fewer
  instructions, same time.
- **Tail call** for quicksort's second recursive call by hand: same
  time.
- **sieve** by hand: strength reduced store pointer, capacity kept in a
  register in the push loop: same minimum time (109.6 ms all three).
- **Rematerializing spilled constants**: no bench program spills (no
  reload from a spill slot in any hot loop), so there was nothing to
  measure; still worth doing when real programs spill.
- **Jump tables in `__TEXT,__const`** or as **branch tables**: see
  decision 0051.

## Correctness

`go test ./internal/arm64` (golden assembly unchanged for fib and sieve;
all bench programs, the 16 SSA goldens and `testdata/run/*` with exact
output and zero live allocations). New run programs: `switch` (enum and
Int matches with gaps, offsets, alternatives, guards, values outside
the table, sparse chains, arms that call), `select` (lexicographic
compares on Int and Float fields, a tie break different from the first
compare), `rc_cancel` (popped Str and List payloads kept, appended to,
and mutated). Writing `select` found that the native backends order NaN
differently from the Go backend (`gotchas/native-float-nan-order.md`).

## What is left (ranked by likelihood of paying off)

1. **sort (1.09x)**: we retire 28 percent more instructions than LLVM
   (1763M against 1376M, `/usr/bin/time -l`). Candidates: induction
   variable strength reduction (LLVM walks the element pointer by 24
   bytes instead of recomputing `base + 24 * i` and the bounds check);
   keeping the swapped elements' fields in registers instead of
   reloading them. Experiment: hand edit `quicksort` in
   `<build dir>/arm64/prog-darwin.s` to use a pointer induction
   variable in both scan loops and measure with `icount` and time.
2. **Enum drop helpers**: `Lxo_dropN` for an enum stores its argument
   words to the stack and reloads them; a register only helper (tag
   test, tail call to the field's drop) made strings 2 percent faster
   by hand before `cancelRC`. Experiment: rewrite the enum case of
   `rcHelper` in `rc.go`.
3. **sieve (about 1.07x in quiet runs)**: retires fewer instructions
   than LLVM (1879M against 2088M) but takes 11 percent more cycles; the
   hand experiments above did not find it. Next: an instruction level
   profile (`xctrace record --template 'CPU Counters'`) of both binaries.
4. **NaN order in native Float comparisons**: a semantic mismatch with
   the Go backend and `spec/std.md` (gotcha above); needs a decision.
