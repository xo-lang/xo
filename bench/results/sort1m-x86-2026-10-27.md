# sort1M on x86 against Go (Intel tester 0.33.0, 2026-10-27)

The Intel tester's micro benchmark (sort of 1M LCG Ints, a frozen Buf's
List) ran 1.64x Go on an i7 (126 against 77 ms) while the same program is
0.81x Go on arm64 in release-vs-go. Reproduced with our own copy (the
tester's files were only read): i7-9750H, best of 5 sorts per process,
three processes, alternating with Go 1.26.1's `slices.Sort`.

## Where it stands

| sort1M, best of 5 | i7-9750H | arm64 (M-series) |
|---|---|---|
| list_sort's stable merge (before) | 114 to 117 ms | 59.0 ms |
| pdqsort port, swaps through a function | 102 to 106 ms | 58.1 ms |
| pdqsort port, swaps inline (3b0f706ac) | 81 to 84 ms | 54.7 ms |
| Go slices.Sort | 67 to 69 ms | 56.5 ms |

So x86 went from 1.67x to 1.23x, and arm64 is 0.97x. `--ab` on arm64 (the
whole program, A the merge): wall 0.907, cycles 0.924, instructions 0.627.

## What was found

- The merge's step `if a[j] < a[i]` mispredicts on random input (the
  XO_PROF line profile put 330 of 440 ms on its two arms). isel keeps it a
  branch on purpose: select_branch's from_memory rule leaves a condition
  on loaded values as a branch, since a select makes the next load wait (a
  binary search over sorted input predicts well). The merge and that search
  have the same dependence shape, so the rule could not be narrowed
  honestly; a ceiling with the rule off gave 81 ms on the i7 for a
  branchless merge.
- Instead, `List[Int].sort` became a port of Go's pdqsort (equal Ints are
  indistinguishable, so unstable is safe; Float and other types keep the
  merge, spec/std.md).
- An out of line swap per exchange (a uniqueness check, two bounds checks,
  saved registers) held it at 1.48x; written inline it is 1.23x.

## Ruled out for the last 1.23x

- **Instruction count.** callgrind in Docker linux/amd64 (Go run with
  GODEBUG=asyncpreemptoff=1: valgrind crashes on Go's signal preemption):
  xo 1,638 M instructions against Go's 1,770 M for the same work
  (partition 1,169 M against 1,298 M, insertion 264 M against 186 M, the
  recursion 124 M against 68 M). xo does less work and takes longer: the
  gap is instructions per cycle.
- **The materialized `!(a < b)`** in `while i <= j && !(d[j] < p)` (setl,
  movzbl, xor, test, je; on arm64 cset, eor, cbz): written `>=`, the loop
  is a plain cmp and jl, and no faster on the i7 (83 to 86 ms).
- **The Skylake jump erratum.** Assembled by clang with
  `-mbranches-within-32B-boundaries` (Go's toolchain pads the same way):
  83.5 to 84.3 ms against 80.8 to 83.4 without.
- **Loop alignment.** `.p2align 5` before each of pdq's 31 loop heads:
  91 to 94 ms, worse.
- **The copy a shared List's sort makes first** (8 MB in 4 KB pages):
  0.6 ms on the i7.

## Parked

The cause of the remaining gap is microarchitectural (it moves with code
layout: alignment made it worse by 10%) and needs hardware counters
(branch mispredicts, decoded uop cache misses) to name. The i7 has only
the command line tools, so Instruments' CPU Counters cannot run there
without installing Xcode, outside the laptop's rules. Linux perf on an x86
machine (CI has none; Docker's VM exposes no counters) would answer it.
x86 runs are best effort (CLAUDE.md, arm64 only testing), so this stays at
1.23x until such a machine is available.
