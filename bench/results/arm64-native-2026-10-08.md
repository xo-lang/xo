# Native arm64 backend: `xo build --backend=arm64` (2026-10-08)

Question (decision 0040, "possibly a direct arm64 backend"; task 10):
can Xo lower its SSA IR (decision 0045, with reference counting from
decision 0046) straight to AArch64 assembly, with no LLVM, and run the
bench programs correctly and at a speed comparable to the LLVM backend
and Go?

Answer: yes. All seven `bench/perf/llvm/xo` programs and all 16 SSA path
golden programs of `internal/llvm` run natively with output identical to
the Go and LLVM backends (fault messages and exit status included) and
every allocation freed at exit. On fib and sieve, the first targets, the
native code runs at 1.00x and 1.11x of the LLVM backend's time and 0.96x
and 1.02x of hand written Go, with the LLVM backend's peak memory. Across
the seven programs it is 0.93x to 1.17x of LLVM (faster on nbody) and
0.42x to 1.10x of Go.

Host: darwin/arm64 (Apple M4 Pro), Go 1.26.1, Apple clang 21.0.0 (the
LLVM backend's `clang -O2 -flto`; the native backend's `cc -O2` compiles
only the C runtime and assembles the `.s`).

## What was built

| Part | Path |
|---|---|
| Value layout (words) | `internal/arm64/layout.go` |
| Instruction selection to MIR (virtual registers, templates) | `internal/arm64/isel.go`, `mir.go` |
| Local optimizations: memos, dead code, bounds, threading | `internal/arm64/opt.go` |
| Inlining of small leaf functions (SSA to SSA, verified again) | `internal/arm64/inline.go` |
| Register allocation | `internal/arm64/regalloc.go` |
| Emission: frames, parallel moves, fault stubs | `internal/arm64/emit.go` |
| Reference counting helpers in assembly | `internal/arm64/rc.go` |
| Build (`cc`, SDK fallback shared with LLVM), `--backend=arm64` | `internal/build/arm64.go`, `cmd/xo` |
| Tests | `internal/arm64/arm64_test.go`, golden assembly `testdata/*.s`, programs `testdata/run/*` |
| Measurement | `bench/perf/llvm/native.sh` |

The design is decision 0049. In short: SSA values are flattened into 64
bit words; aggregates are register aliases; block parameters are parallel
moves; the allocator computes live ranges with holes, coalesces moves,
and places each virtual register in the first physical register whose
ranges do not intersect (calls block the caller saved registers for one
position); spilled registers live in stack slots; faults go to out of
line stubs that recover a clobbered operand by undoing the wrapped
operation. No change to `internal/ssa`, `internal/llvm`, or `xo_rt.c`.

## Correctness

- `TestGoldenRun`: the 16 programs of `internal/llvm/testdata/golden` that
  take the SSA path (abs_fault, arith, div_zero, float_int_fault,
  index_oob, loops, neg_overflow, overflow_add, overflow_mul, rc_aliasing,
  rc_values, shl_overflow, sort_structs, strings, user_fault, var_alias)
  build with `--backend=arm64` and match their `want.txt` exactly; those
  that exit normally report 0 live allocations (`XO_LEAKCHECK=1`).
- `TestRun`: backend specific programs in `internal/arm64/testdata/run`
  against the Go backend: `stress` (21 arguments, 11 on the stack; 20
  values live across calls; division and remainder by powers of two over
  negative and positive values; `List[Pt]` with Float fields through
  push, pop, get, `with`, field set; enums with Float and List payloads;
  lists of structs holding a Str and a `List[Str]`, copied and then
  mutated; `var` parameters; NaN comparisons), and four fault programs
  whose checked operation shares a register with its operand
  (`fault_add_loop`, `fault_sub_loop`, `fault_neg_loop`) or whose check
  branch bounds must not remove (`fault_bounds`).
- `TestBench`: the seven bench programs print the expected checksums with
  0 live allocations (fib 1, sieve 81, nbody 4, sort 40, interp 7,
  collatz 1, strings 2,000,261 allocations, the same counts as the LLVM
  backend).
- `TestInlineVerifies`: every program above verifies (RC balance on every
  path) after the backend inlines small functions.
- `TestGoldenAsm`: fib and sieve assembly for Darwin and Linux against
  `testdata/*.s`; the Linux text is assembled as ELF
  (`clang -target aarch64-unknown-linux-gnu -c`). `TestLinuxEmit` builds
  for linux/arm64 on a Darwin host (assembly written, not linked).

## Benchmarks

`bench/perf/llvm/native.sh` (REPS=5, binaries interleaved Go, LLVM,
arm64; best wall time of whole processes; peak RSS from
`/usr/bin/time -l`). Go is `llperf` (hand written Go, same algorithms).
Measured at load average 7 (another agent was running builds on the host
earlier; runs at load 40 to 85 were discarded,
`gotchas/bench-host-timing-drift.md`).

| Workload | Go ms | LLVM ms | arm64 ms | arm64/LLVM | arm64/Go | Go MB | LLVM MB | arm64 MB |
|---|---|---|---|---|---|---|---|---|
| fib | 228.5 | 219.0 | 219.8 | 1.00x | 0.96x | 4.5 | 1.8 | 1.8 |
| sieve | 106.9 | 97.4 | 108.6 | 1.11x | 1.02x | 48.6 | 54.4 | 54.4 |
| nbody | 163.1 | 186.0 | 173.3 | 0.93x | 1.06x | 4.5 | 1.8 | 1.8 |
| sort | 261.7 | 213.6 | 245.3 | 1.15x | 0.94x | 92.1 | 75.9 | 75.9 |
| interp | 139.9 | 66.6 | 78.0 | 1.17x | 0.56x | 4.3 | 1.8 | 1.8 |
| collatz | 451.9 | 450.2 | 497.3 | 1.10x | 1.10x | 4.4 | 1.8 | 1.8 |
| strings | 89.8 | 35.8 | 37.7 | 1.05x | 0.42x | 27.3 | 16.7 | 15.6 |

Peak memory is the runtime's (the same allocator and reference counting
as the LLVM backend), so it matches LLVM; sieve's 54 MB is one 10 MB list
doubling plus allocator chunks.

Build time, `xo build` end to end, best of 5 (ms): fib 107 LLVM / 113
arm64, sieve 113 / 116, interp 128 / 119. Both are dominated by clang
compiling `xo_rt.c`; the arm64 code generation itself takes a few
milliseconds.

### How the gap closed (fib and sieve, arm64/LLVM)

| Step | fib | sieve |
|---|---|---|
| First working version (every field read loads the whole element, no coalescing) | 1.53x | 1.33x |
| Dead code, per block memos, store elision, move coalescing, compact frames, operand recovery in fault stubs | 1.35x | 1.49x |
| Branch forwarding, loop header duplication, power of two division | 1.39x | 1.59x |
| List length in a register across blocks (`gotchas/arm64-loop-carried-store-forwarding.md`) | | 1.11x |
| Bounds from branches drop `n - 1`, `n - 2` checks | 1.33x | |
| Callee saved pairs stored high register first (`gotchas/arm64-stp-pair-order.md`) | 0.98x | 1.08x |

Two findings came from editing the generated `.s` by hand and linking it
with `cc -O2 prog.s xo_rt.c`: the sieve's push loop was bound by store to
load forwarding of the list length (the instruction count was not the
problem), and fib's 1.33x was entirely the register order inside one
`stp` pair (305 ms against 217 ms, identical instructions otherwise).

### Caveats

- One host; wall clock of whole processes; the host was shared with
  another agent's builds, so every number above comes from one quiet run
  with Go and LLVM interleaved.
- linux/arm64 output is assembled as ELF but not linked or run here.
- The subset is the SSA subset: programs with closures, generics, failing
  functions, or `==` on aggregates are rejected (the LLVM backend falls
  back to its AST path for them).

## What is left (ranked by likelihood of paying off)

1. **Loop invariant code motion** for constants and list capacity: the
   sieve's push loop materializes `1` and loads the capacity every
   iteration, collatz rebuilds `3000000` (movz, movk) in the outer loop
   header. Experiment: a MIR pass before `regalloc` that moves pure
   constant instructions of a loop into its preheader (the header's one
   outside predecessor ending in a jump); check
   `WORKLOADS="sieve collatz" bench/perf/llvm/native.sh`.
2. **Jump tables for `match`**: interp dispatches through a chain of up to
   ten tag compares. Experiment: detect in `isel` a chain of blocks that
   each test `tag == k` on the same tag register and emit
   `adr`/`ldrsw`/`br` through a table; `WORKLOADS=interp`.
3. **Cheaper checked multiply by a constant** (collatz `3 * n`): two
   `adds` with overflow branches instead of `mul`, `smulh`, `cmp`; or the
   range of `n` from the loop condition.
4. **Cache the runtime object** (`xo_rt.o` keyed by the runtime's hash
   and the compiler) so a native build is code generation plus a link.
5. **Run linux/arm64**: link and run the ELF output in a container or on
   an arm64 Linux CI runner (`--targets=linux/arm64` already emits it).
6. **Grow the subset with the SSA IR**: everything the LLVM backend gains
   from `internal/ssa` (equality on aggregates, generics, closures) needs
   lowering here too; spill slot sharing and a graph coloring fallback
   once real programs spill.
