# The compiler edit loop: rebuilding xo after a one-line edit (2026-11-05)

Owner-approved item (2026-11-05, ahead of native arenas): how long
`go run ./scripts/xobuild` takes after a one-line compiler edit, where the
time goes, and what fixed it. Gotcha:
[xobuild-edit-rebuilds-cold.md](../../knowledgebase/gotchas/xobuild-edit-rebuilds-cold.md).

Method: a worktree at a commit, one `// edit N` comment line added to
`module_scans` in compiler/ssa/build.xo per step (each step a new edit, as
when iterating on a change), built by `XO_XOBUILD_TIMES=1 go run
./scripts/xobuild` (xotool's step times, the build's `--phase-times` and
`XO_CACHE_STATS=1`); a std/native edit adds one comment line at the top of
std/native/llrt/unwind.xo. Mac: darwin/arm64, 24 GB, heavy.sh bulk slots,
shared with other agents' jobs (wall times vary by a few seconds with load).
Host 1: linux/arm64 offload host. Scripts: ~/xo-lead/notes/xo-lang-4/scripts
(editloop-mac*.sh, editloop-remote.sh, stablebuilder-remote.sh).

xobuild's own steps: precheck 2.6 to 3.1 s, seed smoke 0.7 to 1.6 s, built
checks 1.7 to 2.4 s, `go run` about 1 s. Host 1 was the same (cold edit

Causes (the gotcha): the builder was the previous edit's xo (a new codegen
key, so nothing cached under it); xobuild's per-edit stamps were in every
body's front end key; a second hop past `HopMax` built every edit with a new
xo.

## The ceiling: one fixed builder (host 1)

The same xo X0 building four successive edits (A to D): A, X0's first build
of these sources, cold; B and C hit 12,116/12,350 bodies, 22/23 module
checks, every rc, inline, function, object and part entry. D: 5.15 s wall,
3.26 GB max RSS, against about 52 s cold.

Run 3's first edit after a new builder (e1, 47.0 s, 0/12,122) is that

## A resident compiler: what it would save (decision 0283's input, host 1)

Question (owner-approved, 2026-11-05): of a warm one-line compiler rebuild,
how much would a resident compiler process save? Measured on linux/arm64
host 1 at main bf01d00f0: a clean xobuild, then one-line edits to
compiler/ssa/build.xo, each rebuilt through `go run ./scripts/xobuild`
(XO_XOBUILD_TIMES=1, --phase-times, XO_CACHE_STATS=1, /usr/bin/time -v).
The stable builder makes every build after its first one warm.

| Build | Wall s | Build s | Built checks s | Max RSS GB |
|---|---:|---:|---:|---:|
| e0, the clean build (cold) | 50.8 | 47.2 | 1.61 | 4.54 |
| w1, the builder's first build of these sources | 44.2 | 42.4 | 1.42 | 5.04 |
| w2, warm | 17.6 | 15.9 | 1.38 | 3.31 |
| w3, warm | 17.5 | 15.7 | 1.39 | 3.31 |

Where a warm build's 15.9 s go (w2 and w3 phases over 200 ms; the top-level
phases sum to 16.3 and 15.9 s):

| Part | Seconds | A resident process removes it? |
|---|---:|---|
| process start (`xo version`, 5 runs) | 0.00 (8.5 MB) | nothing to remove |
| assemble (objects 0/126 reused, parts 119/125) | 9.2 to 9.5 | no: a cache key bug, below |
| a first pass that is dropped (check, fe.build, ssa, insert_rc) | about 2.4 | no: the module check cache, below |
| the kept pass (check.dirs 0.2, fe.build 0.6, ssa 2.7, insert_rc 0.45, inline 0.45, inline.verify 0.33, fn_keys 0.25, emit 0.3, hollow 0.45) | about 5.7 | only its cache reads and decodes |
| xobuild built checks (`version` and the smoke build) | 1.4 | no (a check policy) |
| `go run ./scripts/xobuild --key` (go's build cache and git) | 0.09 to 0.10 | no |

Two cheap fixes come before any server (reported, not built):

1. Objects are never reused under xobuild on Linux. xobuild sets
   XO_NOLIBC=0 there, so the build links with cc and assembles its parts with
   cc (compiler/xo/main.xo, cached_cc_assemble). That cache's key includes
   each part's .s path (asmparts.xo:511, part_keys with srcs as the tags), and
   the path is in the build's private directory `w-<random>` (main.xo:1641),
   so every key is new. 119 of 125 parts were unchanged, so assembling only
   the changed ones would save about 8 s of the 15.9. Fix: run cc in the work
   directory on the part's base name and key on that. A Mac build and a direct
   `xo build` assemble with Xo's assembler, which reuses objects (117/126
   after an llrt edit, above).
2. The first pass is dropped. Each warm build logs "the module check cache
   skipped 21 module(s) a body of which was built from source" and checks the
   program again (fe 11320/12225 bodies, then 11991/12225), at about 2.4 s.

With both fixes, a warm compiler edit would cost about 5.5 s of build plus
1.5 s of xobuild. A perfect resident process could then save only the cache
reads and decodes inside the kept pass. A warm build reads 1.83 GB from the
cache: 682 entry reads (345 MB), 55 pack reads (602 MB) and 14 shared reads
(26 MB). This run did not split decode out of the kept pass: the profiled
round (w4) set XO_PROF=cpu, and XO_PROF is part of the front end's key, so
xobuild built twice and the profile it kept was the cold build (48.97 s; Rc
borrow inference 35% of the CPU, ints.str_hash 3.6%). Run 1's profile was a
contaminated build (a direct `xo build`, which uses different flags and
caches), and there hashing and decoding were about a quarter of the CPU.
Taking a quarter of the 5.7 s kept pass as the bound, a resident process
saves at most about 1.5 s per warm compiler edit. To do that it would hold
about 3.3 GB resident, the max RSS of a warm build.

### Lookups and xo serve

| Command (compiler/, cold process each) | Seconds | Max RSS MB |
|---|---:|---:|
| `xo def Checker.unparse_bodies` | 0.30 | 237 |
| `xo refs unparse_bodies` | 0.72 | 350 |
| `xo type compiler/ssa/build.xo:2542:7` | 0.52 | 573 |
| `xo doc Checker` | 0.52 to 0.54 | 348 |
| `xo symbols --dir=compiler/ssa` | 0.20 | 110 |
| `xo check compiler/xo`, XO_NO_SERVE=1 (first, then warm) | 1.96, 0.77 | 1,915, 1,468 |
| `xo check compiler/xo` through `xo serve` (first, then cached) | 0.80, 0.00 | 12 (client) |

def, refs, type, doc and symbols run in process and never go through
`xo serve`, so each lookup checks again from cold (0.2 to 0.7 s). `xo serve`
forwards only check and query, and caches each whole response by the stamps
of the files under the checked directories. A cached check after an edit to
compiler/ssa/build.xo still answered in 0.00 s with the old result. That is
the documented limit at the top of compiler/cli/servers/serve.xo: modules
outside the checked directories are not stamped. It also means a check
through the server misses edits to the compiler's other directories.

### Recommendation for decision 0283

- 0388 is settled enough: separate compilation has been the default since
  2026-10-28 and its ADR is unchanged since 2026-10-30.
- Do not build the resident compile server for builds yet. Fix the cc object
  key (about 8 s) and the dropped first pass (about 2.4 s) first. Those turn
  a 15.9 s warm build into about 5.5 s; a server would then save at most about
  1.5 s, at about 3.3 GB resident.
- Stage 1 of 0283 should be the lookup server:
  1. Route def, refs, type, doc and symbols through `xo serve`, answered from
     a checked session the server keeps per root and directory set.
  2. Stamp the session's whole import closure, every loaded module's
     files, instead of only the named directories. That also fixes the stale
     check.
  3. Measure each lookup cold against warm, and the server's RSS (the
     cold check's 1.5 to 1.9 GB is the expected size).
- Repeat this measurement once both fixes have landed to decide stage 2,
  in-process builds. Stage 2 also needs the driver's roughly 115
  exits and fails turned into returned errors, or a forked child per request.
