# Monomorphization in P1: `xo build --mono` against idiomatic Go generics (2026-10-08)

Question (work queue item 4 of decision 0040): can Xo's P1 compiler, which
emits Go, beat idiomatic hand written Go generics on generic heavy code by
specializing generic code per instantiation instead of relying on Go's GC
shape stenciling?

Answer: on three of five generic workloads, yes or close to it.
`--mono` brings every generic workload from 1.6x to 17.8x slower than Go
down to 0.49x to 2.26x. Xo with `--mono` beats Go on a key function
max_by (0.49x) and on a map/filter/fold chain (0.89x), roughly matches it on
a sorted container of structs (0.96x), and still loses on a sorted container
of Ints (1.14x) and a generic interface method loop (2.26x). Both remaining
losses come from Xo's checked Int arithmetic, not from generics (attribution
below).

Host: darwin/arm64 (Apple M4 Pro), Go 1.26.1. Harness: `bench/perf/run.sh`
with `MONO=1 REPS=5` (best of 5 runs per binary, checksums must agree).

## What `--mono` does

Implementation: `internal/gen/mono.go`, wired into `call.go`, `decl.go`,
`expr.go`; runtime helpers in `std/rt/mono.go`. Default off.

1. **Specialized copies.** A call of a user generic function or method
   whose type arguments are concrete calls `<name>__<types>` (for example
   `Sorted_M_search__int64`, `F_max_by__Item_int64`), a copy of the body
   generated with the type parameters substituted. Copies are deduplicated
   per Go package, requested transitively, and generated into the calling
   package (so a copy of `lib.biggest[Point]` can name the caller's
   `Point` without an import cycle). Methods of generic types become top
   level copies taking the receiver first. The Go generic version is still
   emitted and is the fallback when type arguments are not concrete, when
   a chain of copies is deeper than 8 (polymorphic recursion), or when one
   function has more than 64 copies in a package.
2. **Constraint methods inlined.** Inside a copy, `==`/`<` on a type
   parameter lower as for the concrete type: Go operators on scalars, and
   typed `XoEqT(o T) bool` / `XoCmpT(o T) int` methods (generated under
   `--mono` for every non generic struct and newtype) instead of
   `rt.Eq`/`rt.Cmp`, which convert both operands to `any` and switch on the
   dynamic type. A constraint interface call (`x.area()` with `T: Shape`)
   calls the concrete method directly instead of `rt.Iface[Shape](x)`.
3. **Closure literals inlined into prelude higher order methods.**
   `xs.map/filter/fold/any/all/find(fn ... { ... })` with a literal that
   cannot fail and has no `return` or `?` becomes a loop with the body
   inlined: no closure call, no `rt.Result` per element. Applies in every
   function.
4. **Lambda specialization of user generic functions.** A non capturing
   closure literal passed to a user generic function gets its own copy
   (`F_max_by__Item_int64_lit`) that inlines the literal's body where the
   copy calls the parameter. The parameter stays in the signature, so
   error frames and contracts are unchanged.
5. **Typed checked Int arithmetic.** `rt.AddS` and friends are Go generic
   functions; Go compiles them once per shape with a dictionary, and the
   shape copies are just over the 80 node inlining budget (AddS 84, MulS
   160, DivS 237), so every checked `+` on an Int was a call. `--mono`
   emits `rt.AddI/SubI/MulI/DivI/RemI` (int64, fault path out of line, all
   inline) and `List.AtM` (index fault out of line, inlines).

Go forms (whether a function returns `rt.Result`, where `.V` is taken) are
decided on the generic types exactly as without `--mono`, so a copy has the
same signature form as the generic function and every caller agrees.

## Why each workload lands where it does

Generated code was read and checked with `go build -gcflags=-m=2` in the
build directory and with CPU profiles of a scratch copy.

- **sortpt 5.44x -> 0.96x.** Default: `s.items[mid] < x` on `T = Point`
  is `rt.Cmp(a, b)`, which boxes both Points into `any`, misses the scalar
  type switch, and calls `XoCmp(any)` with a type assertion: two
  allocations and an interface call per comparison. With `--mono` it is
  `(a).XoCmpT(b) < 0`, inlined, with `rt.CmpO` per field. Go calls its
  `cmp` func field indirectly on every comparison; Xo's direct inlined
  comparison pays for Xo's extra checks.
- **sortint 2.20x -> 1.14x.** Default: `rt.Cmp` on Int still converts to
  `any` and switches. With `--mono`, `<` on int64 and typed arithmetic. The
  rest of the gap: the 5,000 sorted inserts take 7.5 ms in Xo against 1.1
  ms in Go (persistent `List.insert` copies the list twice per insert,
  a known runtime gap in toolchain.md), and checked arithmetic keeps the
  LCG and `search` above Go's inlining budget. With the checks stubbed out
  in a scratch copy, `sortint` is 154.7 ms (insert copies remain).
- **hof 2.40x -> 0.89x.** Default: three closure calls per element through
  `rt.List_map/filter/fold`, each returning an `rt.Result`. With `--mono`
  the three loops have the bodies inlined. Both sides still build two
  intermediate lists; Go's `Map`/`Filter`/`Reduce` call their func
  arguments indirectly because they are not inlined into `hofChain`.
- **maxby 1.60x -> 0.49x.** Lambda specialization turns `key(x)` into
  `x.score` in a copy per call site. Go's `MaxBy` calls `key` through a
  func value per element (it is not inlined, so the closure is not
  devirtualized). This is the clearest case where Xo's guarantee
  (non capturing literal, no mutation, known at the call) buys what Go's
  generics do not.
- **iface 17.79x -> 2.26x.** Default: `rt.Iface[Shape](x).M_area(tk)`,
  that is, a conversion to an interface (allocation) and a dynamic call
  per element. With `--mono` it is `v_x.M_area(tk)`. It still loses
  because `Rect.area` (`r.w * r.h`, checked) costs 87 inline nodes: the
  `MulI` fault call alone is about 60, so the method is not inlined into
  the loop. With checks stubbed out the same copy runs in 6.0 ms, 2.5x
  faster than Go (Go dispatches `x.Area()` through the shape dictionary).

Checked arithmetic attribution (scratch copy of the `--mono` build with
`AddI..RemI` and `AtM` replaced by unchecked operations; not a proposed
change, only a measurement):

## Recommendation on the default

Make `--mono` the default for `xo build` and `xo run` after the two
follow ups below land, and keep the flag as an off switch: it never lost
to the default lowering on any workload (generic ones 1.9x to 7.9x faster,
collection ones up to 15 percent faster), compile time does not change,
binaries get smaller, and every golden program, the bench solutions, and
the tests behave the same. The cost is up to 65 percent more generated Go
in generic heavy modules and different Go frame names in fault stacks.
Before flipping:

1. Fix the constraint adapter bug above in both lowerings, so `--mono`
   cannot be blamed for, or hide, it.
2. Run `xo test --mono` in CI for a release cycle (the golden suite already
   runs both ways).

## Next steps, ranked by likelihood of closing the remaining gaps

1. **Panic valued faults for checked arithmetic** (iface, sortint, hof).
   Emit `if overflow { panic(&rt.IntFault{A: a, B: b, Op: '+', At: loc}) }`
   instead of an out of line call; the probe above inlines at cost 60.
   `rt.AsFault` converts the value to a `*FaultErr`; the stack must be
   taken from the frames below `runtime.gopanic` at the first recover so it
   matches today's `stack(3)` at the panic site. Experiment: add the type
   and the conversion in `std/rt/fault.go`, switch `AddI` in
   `std/rt/mono.go`, rebuild `bench/perf/xo` with `--mono`, and compare
   `TestGoldenMono` stack lines.
2. **Fuse chains of inlined higher order methods** (hof). `map` then
   `filter` then `fold` with inlinable literals into one loop with no
   intermediate lists. Order of faults changes (a later stage can fault
   before an earlier stage finishes), so fuse only when the later stages
   cannot fault: comparisons, field reads, no checked arithmetic. Touch
   `hofInline` in `internal/gen/mono.go`: detect a receiver that is itself
   an inlinable call.
3. **In place `List.insert` when the list owns its tail** (sortint inserts,
   7.5 ms vs 1.1 ms). The `used` claim that makes `push` amortized O(1)
   applies to inserts at the end of the owned range; for a middle insert,
   reuse the backing array when `used == len` and no other value can see
   past the insertion point. Benchmark: `WORKLOADS=sortint` with
   `LOOKUPS = 0`.
4. **Typed `AtM` and Int helpers in the default lowering.** They do not
   depend on specialization; they would give most of the collection
   workload gains without `--mono`.
5. **Polymorphic recursion** stays unsupported in both lowerings (Go
   rejects the generic fallback as an instantiation cycle). With `--mono`
   the fallback could be a boxed `any` instantiation instead of a Go
   generic one; experiment in `specForLits` once the depth cap is hit.

## Update 2026-10-08 (later the same day): adapter fix, `--mono` by default, cheaper checked arithmetic

Three changes, each landed with its tests before the next.

### 1. Constraint adapter bug fixed

The bug above (`T: Named` with a method that can fail, `Sq.name() -> Str`
that cannot, faulting with "does not implement the interface") had three
forms, all fixed (internal/gen/adapt.go, std/rt/core.go):

- In a specialized copy the concrete type is known: `toIface` and
  constraint method receivers apply the copy's substitution and build the
  adapter (`ifaceAdapter`) directly.
- Generic Go code (`--no-mono`, and the fallback past the copy depth cap)
  converts with `rt.Iface`, which now consults a registry before giving up:
  package main's new `xo_adapt.go` calls `rt.RegAdapter` for every pair of
  a concrete user type named anywhere in generated code and an interface
  generic code converts a type parameter to, when the type implements the
  interface and needs an adapter. Programs that need none get an empty
  file.
- An interface value converted to an interface with different Go methods
  (`let n: B = a`, `A.name() -> Str`, `B.name() -> Str ! Error`, no
  generics) faulted the same way; it is now wrapped in an adapter around the
  source interface.

Golden program `internal/gen/testdata/golden/iface_adapters` (two modules:
constraint calls, `let n: Named = x` in generic code, generic calling
generic, a generic type `Box[T]`, a constraint with more methods converted
to one with fewer, interface to interface, a generic in another module than
the type, a type whose method can fail) faults at its first line with the
compiler before the fix, in both lowerings, and passes in both after it.
`TestIfaceAdapter` (std/rt) covers the registry.

The build directory hash now carries a layout tag, because older xo
binaries do not remove the new top level file and failed on directories a
newer xo had written (`knowledgebase/gotchas/build-dir-shared-across-xo-versions.md`).

### 2. `--mono` is the default

`xo build`, `run`, and `test` specialize by default; `--no-mono` gives the
previous lowering (`--mono` is still accepted). The unspecialized Go
generic functions are still emitted and remain the fallback for recursion
through type parameters and the instantiation cap. `gen.Options.NoMono`
and `build.Options.NoMono` replace `Mono`. `TestGolden` runs the default
lowering against `want.txt` with Go frame lists dropped; `TestGoldenNoMono`
runs `--no-mono` exactly and is the one `-golden-update` writes with.

Every golden program passes in both lowerings (want.txt files unchanged).
`xo test` on every bench/xo/v0.4 and v0.6 solution (scratch copies, seed 1)
gives the same results with the new default, with `--no-mono`, and with
the compiler before this change: the same passes, failures, messages,
locations, and logs (8 pass; 03-retry-client's contract fuzz finds the
known Duration overflow in `backoff`; 06-job-queue is rejected by XO0410).
The one difference is a Go frame line: 03-retry-client's fault stack no
longer lists `F_backoff-range1 retry.xo:137`, the closure Go made for the
body of a range loop, because range literal loops are now counted loops

### 3. Cheaper checked integer arithmetic

Every operation that can overflow (or divide by zero, or index out of
range) still faults with its values and `file:line:col`; only proofs and
cheaper forms of the same check changed.

1. **Panic valued faults.** `rt.AddI..RemI` and `List.AtM` fault with
   `panic(&arithFault{a, b, op, at})` instead of calling the fault
   function: Go's inliner charges a panic about one node and a call about
   sixty. The message and the stack are built when the panic is first
   recovered, from the frames below `runtime.gopanic`, so fault output is
   unchanged (checked against the old compiler on nested, scoped, task, and
   62 frame deep faults; `knowledgebase/gotchas/panic-valued-fault-stack.md`).
   `AddI` checks the sign of `(a^c)&(b^c)`, `MulI` takes a 32 bit fast path
   before a `bits.Mul64` check. `Rect.area` (`r.w * r.h`) now costs 72
   inline nodes and inlines.
2. **Constant operands.** With a constant operand the check is one
   comparison: `rt.AddIUp`/`AddIDown`/`SubIUp`/`SubIDown`, `rt.MulIK`/`MulKI`
   with bounds the generator computes from the constant, and plain Go `/`
   and `%` by a constant other than 0 and -1 (Go's `%` by -1 is 0, as in
   Xo). `lcg` (`(s * 1103515245 + 12345) % 2147483648`) went from 117 to 63
   inline nodes and inlines.
3. **Range analysis** (internal/gen/ranges.go). Before a body is generated,
   an abstract interpretation computes an interval for every Int value and
   binding (constants, `let`, `var` as the join of its assignments, `for i
   in a..b`, comparisons narrowing the branch they guard, `%` and `&`
   results, `.len()`, sized integers converted to Int) and iterates loops to
   a fixed point, widening to powers of two after two rounds. A `var`
   assigned in a `defer` or closure, or passed as a `var` argument or
   receiver, is not tracked. It also keeps symbolic bounds `v <= m*len(L) +
   c` for lists under a parameter or a `let`/`for` binding, which proves
   `xs[i]` in range in `for i in 0..xs.len()` and in a binary search
   (`List.AtU`, which keeps Go's own bounds check as a backstop). Proven
   operations are plain Go; an operation is plain only if every visit of it
   in the analysis proved it.
4. **Counted range loops.** `for i in a..b` over a range literal is a Go
   counted loop instead of a range over func iterator (a closure call per
   iteration; `knowledgebase/gotchas/range-over-func-loop-cost.md`).

Tests: `TestRangeElision` (which operations become plain and which stay
checked, including `0..=10` fitting and `0..=11` not, a `var` assigned in a
`defer`, a `var` argument, a growing counter), `TestRangeDifferential` (120
generated tests of loops, guards, index loops, binary search, and
arithmetic near the Int bounds, run with the analysis and with every
operation checked; output must be identical; 26 seeds explored locally),
golden `test_range_checks` (elided operations compute the right values;
one past the loop bound, constant multiply on either side, constant add and
subtract in each direction, division of the minimum by -1, and an index one
past the length still fault with values and position, in both lowerings),
`TestConstIntArith` and `TestTypedIntArith` (helpers against the generic
checked operations on edge and random values, results and messages).

- **iface 2.26x -> 0.80x (target met).** 33.9 ms to 15.3 ms from panic
  valued faults (the area method inlines into the loop), to 12.0 ms from
  the cheaper add and multiply tests. Go calls `Area` through the shape
  dictionary.
- **sortint 1.12x -> 1.08x (target not met).** The 3M lookups now run at
  Go's speed: with 30M lookups the two programs take 1,341 and 1,342 ms.
  `lcg` inlines (constant forms), the binary search has no checks left
  (`lo + hi`, `mid + 1` proven, `xs[mid]` proven in range) and its loop
  compiles to the same instructions as Go's, and `contains` inlines the
  search. The rest of the gap is the 5,000 sorted inserts: 7.4 ms against
  Go's 0.9 ms (measured with lookups set to 0), because `List.insert` on a
  persistent list allocates and copies the whole list each time; a single
  copy instead of copy plus shift saves only 0.4 ms (allocation dominates).
  This is a List runtime gap, not a checked arithmetic one.
- **iter 0.56x -> 0.32x** from counted range loops, **sortpt 0.97x ->
  0.87x** and **hof 0.96x -> 0.83x** from constant forms (`x * 3`,
  `x % 2`, `r % 1000`) and counted loops.

### Next steps, ranked by likelihood of closing the remaining gaps

1. **In place `List.insert` behind a version check** (sortint, the only
   target not met). Values sharing a backing array cannot be told apart, so
   an in place middle insert needs readers to detect it. Experiment first:
   add a version word to the backing header in a scratch copy of
   `std/rt/list.go`, compare it in `AtM`/`AtU`/`Items`, and run
   `WORKLOADS=sortint` with the inserts unchanged; if the lookups stay
   within 2 percent, make `M_insert` shift in place when the list owns the
   tail (`used == len`) and bump the version, with stale readers copying on
   first access.
2. **Interprocedural result ranges.** `contains` cannot prove `xs[i]` in
   range because `i = search(x)` is unbounded at the caller. Record the
   interval of each function's returned values (non `pub`, only called
   directly) in `rangeAn` and use it at calls. Experiment: add a
   `results map[*check.FuncObj]ival` to `gen` filled by a first analysis
   pass over every function, then rerun `TestRangeElision` with a
   `contains` case.
3. **Panic valued faults in the generic `rt.AddS` family** (`--no-mono`,
   Int32 and other sized types): a generic `arithFaultG[T Integer]` with
   the same `fault()` conversion. Experiment: change `AddS` in
   std/rt/arith.go, check its shape copy's cost with
   `go build -gcflags=-m=2` in a build directory, and run
   `TestTypedIntArith`.
4. **Drop `_ = v` after declarations of variables the generated code
   reads** (about 2 inline nodes each; `search` 68 -> 59). Needs a reliable
   "read in Go" test, since a wrong drop is a Go compile error.
5. The earlier next steps (fusing chains of inlined higher order methods,
   polymorphic recursion through a boxed fallback) stand.
