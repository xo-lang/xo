# Xo against LLVM, Go, and Rust on main (2026-10-17, evening)

The owner asked for the comparison tables again after the day's work
(the amd64 retarget's layout and fusion, LSE atomics, inlining, fewer
drops, rt.mem_copy_block, Xo lang 4's address fold). Two tables, both
from main ff426087 (xo 0.19.0):

1. bench/results/amd64-vs-llvm-2026-10-17.md's table, rerun: every
   workload of bench/perf/llvm/xo and bench/perf/xo, instructions
   executed on linux/amd64 and linux/arm64.
2. bench/results/rust-baseline-2026-10-16.md's Mac compute table (Go,
   Rust, Xo's two backends), rerun with its script.

## Method

- Linux: a linux/amd64 and a linux/arm64 xo cross built from main with
  the Go backend; every program built in Docker
  (scripts/docker-linux.sh; amd64 under Rosetta) with `--backend=amd64`
  or `--backend=arm64` and `--backend=llvm`, then counted with
  `valgrind --tool=cachegrind --cache-sim=no` (I refs, deterministic).
  Default sizes. Each row's checksum agrees between the native and the
  LLVM build (bench/perf/xo prints its elapsed time too; only the
  workload and sum are compared).
- Mac: bench/perf/llvm/rust.sh (REPS=5, interleaved; best wall time,
  fewest instructions retired, peak RSS) with main's xo, Rust 1.99.1,
  Go 1.26.1. The load average was 13 to 28 (other sessions' builds), so
  the wall times are noisy; the instruction counts are not.
- "before" is the earlier file's own ratio (its Xo against its LLVM,
  morning of 2026-10-17): LLVM's counts moved too (the runtime's memcpy
  is Xo code that LLVM compiles as well), so ratios, not raw counts, are
  compared.

## Where the native backends stand

- arm64 is at or below LLVM's instructions on 11 of 25 workloads (fib,
  sieve, interp, collatz, push, iter, branch, sortint, iface, setat,
  stack) and within 1.25 on 18. The largest gaps left: maxby 1.54,
  update 1.48, strings 1.40, grid 1.35, putget 1.28, copymut 1.23,
  sortpt and insrem 1.21. They are the collection workloads (map
  updates, closures over lists, string building): the shared front
  half, inlining and reference counting, not instruction selection.
- amd64 is 1.27 of LLVM on the geometric mean (1.63 this morning); the
  x86 excess over arm64's own ratio is 1.00 to 1.37. The largest gaps:
  strings 1.79 (LLVM's own strings fell with the vectorized memcpy),
  update 1.61, maxby 1.60, nbody 1.56, putget 1.48, copymut 1.47,
  copyset 1.41. nbody's 1.34 x86 excess is the floating point code
  (the copy before each two operand operation, a load straight into the
  tie's destination); copyset and branch copy 32 bytes an iteration
  (amd64 has two vector scratch registers; 64 is next).
- Against Go (Mac instructions) the arm64 build is ahead on five of
  seven and within 8% on the rest; against Rust it trails on nbody (2.1)
  and by 11 to 21% on fib, sort, interp, and collatz.

## Later: amd64 ties coalesce (2026-10-17, night)

A two operand x86 operation is a copy of its tied operand into the
definition, then the operation on the definition. The operation kept
the tied operand in its uses although its text no longer read it, so
that operand lived past the copy, overlapped the definition, and the
copy never coalesced: a movapd or mov before nearly every operation
(gotchas/amd64-tie-source-in-uses.md). The retarget now drops the tied
operand from a non-faulting operation's uses wherever its text does not
name it, and `a op a` reads the definition twice (`mulsd d, d`). A
loop of four floating point operations went from 15 instructions to
10. Against main 9cbbae78 (Docker cachegrind, millions; LLVM from the

## Later: amd64 shrink wrapping (2026-10-17, night)

The amd64 emitter made the whole frame (rbp and the callee saved
registers pushed) at every entry, so fib's base case ran 14
instructions to return n. The arm64 backend's shrink wrapping (decision
0224, shrink.xo) now runs for amd64 too: the frame is made on the edges
into the blocks that need it, a path without them returns with a bare
`retq` (fib's base case is 4 instructions), a restore block copies the
return past the epilogue, a fault stub in a block without the frame
makes it first, and the frame's unwind rules are given once, where the
frame's blocks start (x86_cfi_frame; the prologue no longer carries
them). Against main 7d0d4a13 (Docker cachegrind, millions; 189 of 189
amd64 goldens, the fault and traceback ones included; every checksum

## Later: a checked product's multiples (2026-10-18)

collatz's `3 * n + 1` kept the add's overflow check on both native
backends; LLVM drops it. A checked Int product by a constant k that did
not fault is a multiple of k within Int, so at most (MAX / k) * k: for
k = 3 that is MAX - 1, and `+ 1` cannot overflow. arm64 isel's range of
a checked Mul (one with a position) by a constant now clamps to those
multiples (ranges.xo range_of). The add becomes unchecked: arm64 `add`
for `adds` + `b.vs`; amd64 `leaq 1(%r10), %rdi` for `addq` + `jo` and
the copy into n. Against main 6a464bc4 (Docker cachegrind, millions;
190 of 190 goldens on darwin/arm64, linux/arm64, linux/amd64; every
other workload unchanged, every checksum the same):
