running at once, so wall clock times are noisy (load average 6 to 11);
counts and sizes are exact. Node 22.22.1 runs the modules
(`selfhost/wasm/run.mjs`: WASI preview1 in a worker, single threaded
GC).

## Sizes

Every module the goldens produced (71): **min 12,230 bytes, median
16,149, max 129,329** (byref_struct: structs of 256 bytes and more are

## Run time

Wall clock, best of 5, including Node's start (an empty module: 70 to
72 ms). The goldens are too short to compare (recursion 91 ms vs 12 ms
native, loops 74 vs 2, rc_recursive 160 vs 28; arith, sort_structs,
lists, strings, generics 74 to 77 ms vs 2 to 3 ms: Node's start). Three
CPU programs (scratch, not committed; same output on both):

| program | wasm (after Node's start) | native arm64 | ratio |
|---|---|---|---|
| fib(32), recursive calls | 106 ms (36 ms) | 8 ms | 4.6x |
| sieve of 2,000,000 ten times, List[Bool] | 531 ms (461 ms) | 43 ms | 10.6x |
| 300,000 structs with Str fields, 100,000 appends to a Str | 96 ms (26 ms) | 10 ms | 2.8x |

The sieve shows the costs of stage 1's lowering: every block is
entered through the dispatch loop's `br_table`, and a checked index is
a call into the runtime; stage 3 (structured control flow, inline

## Step 2: tasks without threads

Function tables for the task entry points and list drops (`funcaddr`),
handles (one i32: a runtime object `{rc, free function, ...}`), and the
task runtime `selfhost/wasm/rt3.xo`: scopes, spawn, await, channels,
select, Mutex, Atomic, cancellation, shields, timers (`clock.sleep`,
`select ... after`, `task.with_timeout` through WASI `clock_time_get`
and `poll_oneoff`), and budgets (`rt.tick`), on one thread under a
cooperative scheduler. A task that waits suspends by unwinding its wasm
stack into a save area of its own and is resumed by rewinding it
(Asyncify's technique, generated by the backend: only functions that can
reach a wait are instrumented). Also `rand` through WASI `random_get`,
`Time.unix` (`floor_div`), `int_wrap`/`int_fits`, `crypto_b64`, and
real-time sections (XO-F007).

**113 pass, 21 unsupported, 0 fail of 134** (28 more than step 1). The
same 20 task goldens (conc_*, fault_tasks, fault_task_exit,
select_arm_order, clock_timers, map_until, task_native, task_budget)
passed three runs in a row: the scheduler runs tasks in spawn order, so
the output is the same every run.

## Step 4: toward the playground (the self hosted compiler as wasm)

What the self hosted front end needs beyond the goldens' runtime is
`selfhost/wasm/rt4.xo`: reading the file system through WASI preview1
(`path_open`, `fd_read`, `path_filestat_get`, `fd_readdir`; run.mjs

of collection types (`const_once`), Time as Unix nanoseconds, and
SHA-256 (checked against Python's hashlib on three inputs). With it
native_bytes passes too: the 114 above. `selfhost/wasm --why` lists every
unsupported construct of a program, `--lax` turns an unsupported runtime
call into a fault where it runs (to see how far a program gets; never
for a shipped module).

| component (Xo lines) | module | build (go backend selfhost/wasm) | run under Node vs the go backend build |
|---|---|---|---|
| selfhost/lexer (1,873) | 199,696 bytes | 0.27 s, 101 MB | 5 files, 40,578 tokens: identical output, 0.39 s vs 0.04 s |
| selfhost/parser (7,946) | 5,990,762 bytes (WAT 38 MB, 2,018,620 lines) | 2.0 s, 597 MB (1.21 GB before the two fixes below) | 3 files, 27,687 lines of AST dump: identical output, 7.3 s vs 0.15 s |

The lexer and the parser of the self hosted compiler run as wasm and
print exactly what their go backend builds print.

Memory of the build is the first obstacle. The first build of
selfhost/check thrashed on the loaded machine (swap 57 GB of 58 GB in
use) and was stopped after 10 minutes; so was a second one after 45
minutes with 4 minutes of CPU. Two fixes: the assembler keeps a token
as three Ints (kind and source offsets) instead of a Str and a list
(assembling parser.wat alone: 988 MB to 578 MB, byte identical output),
and the functions' text is dropped before assembling, with the token
list sized from the text (the parser build: 597 MB to 381 MB).

Every module also carried all of the runtime; now only the runtime
functions the program reaches are assembled (the calls of its code, the
function table, the exports). Sizes of the 114 modules: **min 2,907
bytes, median 11,575, max 358,795** (regexp_table); recursion 7,481
(20,583 before, 16,659 at stage 1), conc_channels 41,067, conc_stress
26,999.

## Step 4: what blocks the checker, and the first fix

The first complete build of selfhost/check (the go backend
selfhost/wasm, `--why`: no unsupported construct left) took 693 s and
14.5 GB of memory and wrote a module of **1,673,077,967 bytes** (WAT
8.85 GB) that no engine loads: 162 of its 1,098 functions have more than
50,000 locals (V8's limit per function; V8 also takes modules of at
most 1 GB), 55,245,104 locals in all, the most 3,548,286
(`Checker.habit_call`; median 220). The cause is the value model of
stage 1: every SSA value got locals of its own for all its leaves, and
the checker's `Checker` struct is 253 leaves, copied by every field
update and returned by every `var c: Checker` call (habit_call: 304
parameters, 253 results).

The fix (`plan_locals` in func.xo): values whose live ranges do not
overlap share locals (SSA liveness, each range widened to one interval
over the blocks in order, then a linear scan per leaf signature); a
field update whose struct dies there is made in place (only the field's
leaves are written); a field read is its struct's locals at the field's
offset (no copy; the struct lives as long as the field). The goldens:
116 pass, 18 unsupported, 0 fail (nested_update caught a first version
that resolved chains of field reads in block order, which is not
dominance order). Sizes of the 116 modules: min 2,898 bytes, median
10,763, max 349,372; byref_struct 120,560 to 30,756.

| | before | after |
|---|---|---|
| selfhost/parser module | 5,990,762 bytes | 2,918,085 bytes |
| its WAT | 38 MB | 19.5 MB |
| most locals in a function | 23,135 | 3,006 |
| build (go backend selfhost/wasm) | 2.0 s, 597 MB | 0.98 s, 326 MB |
| the 3 file parse under Node (identical output) | 7.3 s | 0.40 s |
| selfhost/lexer module | 199,696 bytes | 153,851 bytes |

## Step 4: the self hosted checker runs as wasm

With values sharing locals, selfhost/check builds (go backend
selfhost/wasm, `--why`, through the heavy lock) in **13.0 s and 3.1 GB**
into a module of **40,389,109 bytes** (WAT 254 MB; 1,673,077,967 bytes
before): the most locals in a function 11,457 (none over V8's 50,000),
median 65. Under Node it first died: lazily compiled functions crashed
the worker (SIGSEGV; gotchas/wasm-lazy-compile-worker-crash.md), and
with eager compilation the run printed its output and then hit V8's
incremental marking check (status 133;
gotchas/wasm-busy-loop-crashes-node.md). run.mjs now sets
`--no-wasm-lazy-compilation` and `--no-incremental-marking`, and the
goldens still give 116 pass, 18 unsupported, 0 fail.

The wasm checker (`--each` over seven goldens: recursion,
conc_channels, generics, structs, maps, iface_values, native_json)
prints exactly what the go backend build of selfhost/check prints:
**3,398 lines, identical**; 9.57 s and 5.9 GB under Node (most of it
compiling the 40 MB module at instantiation; the go backend build:
0.06 s, 52 MB). On the recursion golden alone: 277 lines, identical,
8.2 s, 5.0 GB.

What blocks the playground's use of it, in order: the module's size
(40 MB, about 5 GB to compile in V8: a `var` call still passes and
returns all 253 leaves of `Checker`, and the dispatch loop lowering is
verbose; the next steps are large aggregates and `var` parameters by
reference in linear memory, then stage 3's structured control flow),
then the rest of the driver (selfhost/ssa and this backend compiled to
wasm; besides reading files they write the module, and rt4.xo does not
write files yet: `rt.fs_write` is the next WASI call, `fd_write` on a
file opened with `path_open`).

## Stage 3: the self hosted checker's module from 43 MB to 8.9 MB (2026-10-12)

Decision 0179, "Stage 3". Same machine and caveats as above (about ten
agents at once; wall clock is noisy, sizes and counts are exact). Every
build and run went through the machine's heavy lock, from a snapshot
of the worktree per step. Per step: selfhost/wasm built with the go
backend; selfhost/check built with it (`--std=std`, `--annotate` from
step 5 on, which only adds WAT comments); the module compiled alone
under Node (`new WebAssembly.Module`, eager); the checker run under
Node (`run.mjs`, `--each` over the seven goldens of step 4: recursion,
conc_channels, generics, structs, maps, iface_values, native_json)
and its output compared with the go backend build's (3,398 lines);
`go test ./internal/selfhost -run 'TestSelfhostWasm$'`; and a small
program of a 20 leaf `var` struct (t2: a loop of `var` calls returning
`Result`, landing pads, `task.isolate`, a swap of two `var` structs)
against the go backend, with the leak check.

**Where the 43 MB went** (main at 9935b0d, before any change; code
bytes estimated per WAT line, by construct):

| construct | share of code |
|---|---|
| suspension frames (save and restore of every local around calls that can suspend) | 25.1% |
| local.set / local.get not attributed below (struct copies, field updates) | 33.9% |
| releases (`call $drop` and their pushes; 717,676 calls, most of one field of `Checker` each) | 12.2% |
| edge copies into block parameters | 8.2% |
| call arguments and results (a `var` call passes and returns 274 leaves of `Checker`) | 9.4% |
| zero results of fault exits | 3.0% |
| return values | 2.7% |

The task runtime was in because the checker reads the clock; nothing
in it waits, but every function that calls through a function value
saved and restored all its locals around such calls (192 functions; the largest function had 12,173 locals).

**The steps** (goldens: 120 pass, 21 unsupported, 0 fail of 141 at every
step; the checker's output identical at every step; t2 identical with
no leak from step 3 on):

| step | change | module bytes | compile alone (Node) | checker run (Node) |
|---|---|---|---|---|
| main | | 43,193,163 | 0.92 s, 1.15 GB | 10.73 s, 5.94 GB |
| 1 | no frames when nothing waits; one zero result exit | 31,592,083 | 0.84 s, 1.02 GB | 7.15 s, 5.00 GB |
| 2 | unwind exits as fault exits; release runs as one call | 29,873,559 | 0.84 s, 1.06 GB | 7.15 s, 4.74 GB |
| 3 | `var` parameters of 16 leaves or more by reference (home.xo) | 39,993,636 | 0.91 s, 1.19 GB | 8.24 s, 5.35 GB |
| 4 | locals renumbered, most used first | 36,126,826 | 0.93 s, 1.18 GB | 8.18 s, 6.97 GB |
| 6 | exact liveness to give a home up | 24,789,589 | 0.65 s, 0.91 GB | 6.22 s, 4.70 GB |
| 7 | read only homes (`fn (c: Checker)`) | 23,722,025 | 0.62 s, 0.91 GB | 5.78 s, 4.01 GB |
| 8 | field reads of block parameters alias them | 17,936,052 | 0.50 s, 0.92 GB | 6.34 s, 4.78 GB |
| 9 | chains as a greatest fixpoint (loops); `memory.copy` for copies | 12,742,431 | 0.36 s, 0.76 GB | 2.79 s, 3.19 GB |

Step 3 first made the module larger: the analysis used plan_locals'
intervals (widened over blocks in their order, not dominance order),
so a `Checker` used in a loop never "died" at the call that gave it
up, and 1,782 calls copied it into a temporary block and back (2,192
bytes each way). Step 5 (release runs of field reads) changed no byte:
the reads it looked for were behind repeated reads of the call result
(fixed in step 10). Step 13 broke t2 and archive_formats (a snapshot's
locals were reused in a block placed later in the order: the liveness
walk started from the read's block, not the snapshot's) and was fixed
in step 14 before anything was committed
(gotchas/wasm-home-chain-ssa-shapes.md).

Locals: the largest function had 12,173 locals and 300 functions more
than 1,000; at step 14 the largest has 6,937 (`Checker.structural`) and
133 more than 1,000, median 23. Under Node the run needs a 4 MB worker
stack at main and fits in 1 MB at steps 12 and 14.

What is left (step 14, code bytes by SSA opcode): releases 20.2%,
release runs and field reads 14.3%, `list.index` (an element's leaves
loaded whole) 11.1%, calls of functions with homes 9.7%, edge copies
9.5%, branches 4.3%, retains 4.0%.

The build of the checker (go backend selfhost/wasm, `--annotate`):
14.0 s and 3.97 GB at main, 37.5 s and 3.08 GB at step 14 (the
liveness walks per value; noisy machine).

**Where the run's time went** (step 1's module, the same run with V8's
tiers varied):

| node flag | time | max RSS |
|---|---|---|
| default | 7.03 s | 4.83 GB |
| `--no-wasm-tier-up` | 7.28 s | 5.41 GB |
| `--liftoff-only` | 1.80 s | 1.12 GB |

The optimizing tier on the huge functions, not the module's compile,
was the cost (gotchas/wasm-turbofan-tier-up-memory.md).

**In a browser engine.** Headless Chrome 154 (Google Chrome.app, driven
through DevTools), the module fetched over file:// and run in a
dedicated Worker under a WASI preview1 shim over an in-memory file
system (std and the golden directories, base64 in a JSON bundle; the
scripts are not in the repository). `WebAssembly.compile` is lazy in
Chrome: 4 to 13 ms for any of the modules (36 MB at step 4, 8.9 MB at
step 14), instantiation 0 to 1 ms. At step 14 the checker on the
structs golden runs in the worker in 446 ms and prints its 286 lines
exactly as the go backend build does. On the recursion golden (and so
on the seven) it stops with `RangeError: Maximum call stack size
exceeded`: the trace is a cycle of ten checker functions per level of
the program's nested expression. Under Node the same run needs a worker
stack of more than 0.75 MB and fits in 1 MB, so the browser's worker
stack (under 1 MB) is just short. The next step is smaller frames on
that cycle (fewer locals per function: a Liftoff frame holds every
local) or less recursion per expression level.
