# Why the self-hosted compiler is slower than the Go compiler (2026-10-12)

Question: the self-hosted compiler driver xo1 (selfhost/xo, built by the
Go compiler with the arm64 backend) took 313.0 s to build selfhost/xo
where the Go compiler took 142.4 s (selfhost-arm64-2026-10-11.md, "The
fixed point with steps 1 to 6"), and in-place nested updates did not
explain it (nested-update-2026-10-11.md). xo1-perf agent, worktree at
commit df055d5 and later.

Machine: the shared 12 core Mac (24 GB), every run under the heavy lock
with about ten agents working: load averages 6 to 19 during the runs,
noted per run. Wall clock is noisy; instructions retired and cycles from
`/usr/bin/time -l`, and sample counts, are the figures to compare. Each
run is one run.

Summary: the whole gap is in the arm64 emitter (3.8 times the Go
emitter's wall clock; every other phase is at parity or faster). xo1
retires fewer instructions than the Go compiler but at half the
instructions per cycle: reference count updates and allocation around
copies of 200 byte MIR instructions and of inner lists, where Go walks
pointers and collects on other cores. Building xo1 with LLVM removes
about a third of the cycles (code quality), not the rest. Two source
fixes (dce and the register allocator's liveness) cut xo1's cycles by
45 percent with byte identical output; xo1 then ran within 1.18 times
the Go compiler's wall clock in the same run.

## Tools added (commit df055d5)

- `xo1 build|test|asm --phase-times` prints `phase NAME MS ms` on
  standard error for: check (load, lex, parse, check), ssa
  (`build_program`), tz, prune_unwind, add_landings, cleanup, insert_rc,
  inline (with its verification), emit (the arm64 emitter: isel, MIR
  passes, register allocation, text), print or write, cc.
- `XO_PHASE_TIMES=1 xo asmdump` prints the same lines for the Go compiler:
  check, ssa (`ssa.BuildOpts`), verify, insert_rc, verify, inline (with
  its verification), emit, print. `arm64.InlineDone` is the hook that
  splits `arm64.Generate`.

## 1. Phase timings (run 1, load 6.2 to 10.7)

Both compile selfhost/xo to assembly only (no clang): the Go compiler
with `cd selfhost && xo asmdump xo` (G), xo1 with `A asm selfhost/xo`
(B; A built by `xo build --backend=arm64`, 336.4 s with clang). Their
outputs are byte identical: sha256 b299009e...c6be, 13,777,890 lines.

| phase | Go compiler (G) | xo1 (B) |
|---|---|---|
| check | 0.6 s | 0.7 s |
| SSA build | 4.8 s | 1.3 s |
| verify (Go only) | 0.9 + 10.6 s | |
| unwind, landings, cleanup | (inside SSA build) | 0.3 s |
| insert_rc | 29.2 s | 29.5 s |
| inline | 11.4 s | 8.8 s |
| **emit** | **227.1 s** | **860.7 s** |
| print | 0.2 s | 0.4 s |
| wall clock | 285.1 s | 902.7 s |
| user + sys CPU | 313.0 + 160.1 s | 507.0 + 336.7 s |
| instructions retired | 5,791.2 billion | 5,422.4 billion |
| cycles | 1,793.9 billion | 3,270.1 billion |
| page reclaims | 61.5 million | 122.3 million |
| peak memory footprint | 9.9 GB | 15.1 GB |

The second, sampled run (run 2, load 8 to 19) gave the same split: G
emit 183.4 s of 242 s, B emit 564.5 s of 617 s, insert_rc 28.9 s
against 41.3 s.

Findings:

- Everything outside the emitter is at parity or faster in Xo (SSA
  build 3.7 times faster, insert_rc equal). **The gap is the arm64
  emitter alone**: 3.8 times the Go emitter's wall clock in run 1, 3.1
  times in run 2.
- xo1 retires **fewer** instructions than the Go compiler (0.94 times)
  but takes 1.8 times the cycles: 1.66 instructions per cycle against
  3.23. The time goes to memory stalls and the kernel (sys 336.7 s
  against 160.1 s, twice the page reclaims), not to executing more
  code.
- The Go compiler is not single threaded: its garbage collector ran on
  other cores (473 s of CPU in 285 s of wall clock); xo1's reference
  counting runs inline on the one thread.
- Earlier figures for the same command (nested-update-2026-10-11.md:
  271.8 s, 2,586.5 billion instructions) were on a less loaded machine;
  the instruction count here includes kernel work for page faults under
  memory pressure, so compare the two compilers within a run only.

## 2. xo1 built with the LLVM backend (run 3, load 8.8 to 11.5)

L: xo1 built by `XO_LLVM_SPLIT=12 XO_LLVM_JOBS=4 XO_LLVM_LTO=none xo
build --backend=llvm selfhost/xo` (decision 0168's test configuration,
2 to 3 percent slower output than full LTO; the build took 839.2 s,
2,937.6 s of CPU) from the same sources as A.

| | G (Go) | B (arm64-built xo1) | L (LLVM-built xo1) |
|---|---|---|---|
| emit | 227.1 s | 860.7 s | 581.5 s |
| wall clock | 285.1 s | 902.7 s | 615.2 s |
| instructions | 5,791.2 billion | 5,422.4 billion | 4,365.0 billion |
| cycles | 1,793.9 billion | 3,270.1 billion | 2,181.3 billion |
| page reclaims | 61.5 million | 122.3 million | 41.7 million |
| peak footprint | 9.9 GB | 15.1 GB | 17.4 GB |

LLVM code takes a third of the cycles off (3,270 to 2,181 billion) but
stays 1.22 times the Go compiler's cycles and 2.2 times its wall clock.
**The arm64 backend's code quality is about a third of the gap; the
rest is the memory model** (reference counts and allocation, below),
which LLVM does not remove.

L's output is **not** the Go emitter's: its assembly (sha256
f2614dfc...de7f, 13,776,145 lines) differs in 457 of 2,826 functions,
in each case seen the frame size (by reference argument memory missing,
the argument written above the frame). Reproduced on
internal/arm64/testdata/run/byref_var and far_out_slot in under a
second: gotchas/llvm-built-xo1-drops-mem-bytes.md. Its timing stands
(the same work but the frame layout), its output must not be used.

| allocation, list copy and free (`xo_alloc`, `xo_rl_new`, `xo_rl_free`, memmove, ...) | 61,652 (26.6%) | 16,088 (9.8%, mallocgc, memclr, memmove) |

| maps and string compare | 10,361 (4.5%) | 12,012 (7.3%) |

Top self time in xo1: `G.dce` 42,210, the rc helpers 41,848
(`xo_entry` in the profile: the helpers are local labels after it),
`xo_alloc` 30,349, `G.regalloc` 23,728, `xo_rl_free` 14,880, `G.add`
10,763, `merge_sorted` 9,272, `overlaps` 7,661, memmove 7,394,
`xo_rl_new` 5,891, `take_insts` 4,967. In the Go compiler: `regalloc`
16,160, `dce` 9,834, `mergeSorted` 8,412, then the collector.

What the hot code is (from the assembly at the sampled offsets):

- `G.dce` (selfhost/arm64/opt.xo): `for inst in g.blocks[b].insts` over
  a `var g: G` field copies each 200 byte `Inst`: an inline dup of each
  of its eleven heap fields (each a load and store of a count in another
  cache line) and a drop at the end of the iteration, per instruction
  and per pass of the liveness fixed point. The kept list of every
  block was rebuilt even when nothing was deleted and then freed:
  16,891 samples in that drop alone. The Go emitter walks `[]*inst`
  pointers.
- `G.regalloc` liveness: `out[w] | live_in[ti][w]` dups and drops the
  inner list per word of the bit set (quadratic in function size, as in
  Go, but with two count updates per word).
- Allocation: `xo_rl_new` of `[]` per virtual register for `ranges`,
  `fixed`, `partners` (Go's are nil slices); `take_insts` allocates an
  800 byte empty `List[Inst]` per instruction added (the decision 0169
  workaround still in isel.xo); `merge_sorted` builds a fresh list per
  coalesce and per allocation where Go merges in place.

Classified, 44.6 percent of xo1's samples are in the rc helpers (18.0%)
and allocation and freeing (26.6%), and up to another 18.2 percent is
`G.dce`'s own time, mostly inline dups and drops. The Go
compiler pays for the same work in its collector, but on other cores.

## 4. The top two causes and the fixes

1. **Struct elements copied by `for x in g.f[i].list` over a `var`
   receiver** (dce, regalloc, and every MIR pass that walks
   `g.blocks[b].insts`). Fix in the source (done for `G.dce`): pass the
   list to a helper as a parameter, where elements are borrowed (no
   dup), as `dce_mark`, `dce_dead`, `dce_keep` in opt.xo now do, and
   rebuild a block's list only when something is deleted. Fix in the
   compiler (next): borrow the loop element of `for x in <place>` when
   the body does not write the place's root (selfhost/ssa rc.xo
   `insert_rc` and internal/ssa rc.go `inferBorrows`, which today
   borrow parameters only), which would remove these copies everywhere
   without source changes.
2. **An inner list indexed through an outer one (`a[i][j]`) is dup'd
   and dropped per access.** Fix in the source (done for regalloc's
   liveness): `or_into` and `transfer` in regalloc.xo take the bit sets
   as parameters. Fix in the compiler (next): an index of a list loaded
   from a list element, used only for the read, borrows it (a projection
   borrow in the rc pass).

Further, ranked by the samples they would save: replace
`take_insts`/`put_insts` in isel.xo with direct nested updates (decision
0169 made them unnecessary; `take_insts` is 10,743 samples inclusive,
an 800 byte allocation per instruction); make `[]` not allocate (a static empty list
with the immortal count, as string literals have) so the per register
`ranges.push([])` costs nothing; merge `occ` in place (`merge_sorted`
into a list with capacity, as Go's `mergeSorted`).

## 5. The fixes measured (run 4)

A2: xo1 built from the sources with both fixes (`dce_mark`, `dce_dead`,
`dce_keep` in opt.xo; `or_into`, `transfer` in regalloc.xo), by the same
Go compiler (498.2 s with clang). G3: the Go compiler's assembly of the
new sources; B3: A2's. Load 6.9 to 13.1.

**The fixed point holds: G3.s and B3.s are byte identical** (sha256
0bff62c2...0a11, 13,771,642 lines; the new sources, so not B.s's sha).

| | B (run 1, before) | B3 (after) | G3 (Go, same run as B3) |
|---|---|---|---|
| insert_rc | 29.5 s | 28.4 s | 49.1 s |
| emit | 860.7 s | 469.1 s | 329.6 s |
| wall clock | 902.7 s | 509.6 s | 432.5 s |
| user + sys CPU | 507.0 + 336.7 s | 366.5 + 94.7 s | 342.2 + 269.0 s |
| instructions retired | 5,422.4 billion | 3,700.0 billion | 6,023.3 billion |
| cycles | 3,270.1 billion | 1,783.7 billion | 2,253.8 billion |
| page reclaims | 122.3 million | 36.8 million | 83.8 million |
| peak footprint | 15.1 GB | 15.3 GB | 11.0 GB |

The two fixes take xo1's user CPU from 507.0 s to 366.5 s (28 percent),
its instructions from 5,422 to 3,700 billion (32 percent) and its cycles
from 3,270 to 1,784 billion (45 percent). In the same run the Go
compiler took 2,254 billion cycles and 432.5 s: xo1 is now within 1.18
times its wall clock and used fewer cycles. Caveat: B and B3 ran 80
minutes apart on a loaded machine; the kernel share (sys time, page
reclaims) moves with memory pressure from other agents (the Go
compiler's own sys time went from 160.1 s to 269.0 s between the runs),
so the user CPU and instruction drops are the safer figures. One run
each.

   <place>` when the loop body does not write the place's root
   (selfhost/ssa rc.xo `insert_rc`, internal/ssa rc.go `inferBorrows`).

   updates: the 800 byte allocation per instruction added.

   (gotchas/llvm-built-xo1-drops-mem-bytes.md), then measure an LLVM-built
   xo1 with full LTO against the arm64-built one again.
