## Max RSS at 2,000,000 Strs, and why the index sort's scratch is not shrunk (2026-10-24)

Probe: bench/perf/sort/{xo,go} with 2,000,000 keys ("key" plus a number below 100,000,000), `/usr/bin/time -l`, three runs each, xo built at COMMIT 6bb0509e4 (DIRTY empty; its sort has the same peak as the pushed one, 21424 against 21440 kB at 200k). A `gen` mode builds the list and stops.

| mode | Xo max RSS | Go max RSS | Xo / Go |
|---|---|---|---|
| gen (build the list only) | 114.7 MB | 77.0 MB | 1.49 |
| strs (build and sort) | 194.7 MB | 77.0 MB | 2.53 |
| sort alone (strs minus gen) | +80.0 MB | +0 MB | |

Go's `slices.Sort` is an in-place, unstable pdqsort and adds nothing. Xo's `List.sort` is stable and adds exactly 80 MB, which is the 5n words of the index sort (n = 2M, 8 bytes a word): xs 2n, pre n, a n, b n at the merge peak, and xs 2n, a n, out 2n at the gather peak, the same 5n. Dropping lists before the gather therefore does not lower the peak, and a half-size merge scratch lowers it only if the gather also shrinks (at best 4.5n with an in-place gather, 5 to 7% of the 200k bench's 21 MB, which is mostly a 13 MB process floor). Not built.

The build alone is 38 MB over Go (1.49x), before any sort: 2M Strs of 16 bytes in the list plus the string objects. That is a Str object size question (header and size class), not the sort; ADR 0369's finding (every list element is 8 bytes per word) does not cover it.

Next: measure the per-Str heap cost (RSS of 2M `"key${n}"` against 2M bytes of text) and the allocator size class of a 10 byte string.

### Per-Str heap cost (2026-10-24, same probe, `gen N`, max RSS)

| N | Xo | Go |
|---|---|---|
| 1 | 2.7 MB | 4.4 MB |
| 500,000 | 30.7 MB | 22.8 MB |
| 1,000,000 | 58.7 MB | 40.8 MB |
| 2,000,000 | 114.7 MB | 76.8 MB |

Slope 1M to 2M: Xo 56.0 bytes a Str, Go 35.9. Xo's 56 is the 16 byte Str value in the list plus 40 for the string object: a 16 byte object header (count and capacity, obj.xo S_HDR, decision 0252) and the 11 byte text ("key" and up to 8 digits) fit the 32 byte class, plus the allocator's 8 byte block header (`heapstats` counts size + 8). Go's 36 is the 16 byte string header plus about 20 for the text, which its tiny allocator packs without a per-object header. So the per-Str overhead is 24 bytes in Xo (header 16, block 8) against about 4 in Go, and it dominates the build at short keys. Levers, each a runtime or language change to take to the owner first: small strings stored inside the 16 byte Str value (no object for text up to 15 bytes), or a headerless packed class for small immutable strings.

Side finding: `XO_HEAPSTATS=1` prints "on free lists 17592186044415 MB" at exit for a program that never freed (a wrapped subtraction or an uninitialised sum; std/native/llrt/entry.xo heapstats), and no per-class lines since nothing was free, so it cannot show live bytes by class.
