# CI matrix on EC2 (2026-10-09)

The Xo test jobs run on real Linux hardware for the first time: one
linux/arm64 and one linux/amd64 machine, created and destroyed by
`infra/ci-aws/ci.sh` (Terraform, see `infra/ci-aws/README.md` and
toolchain.md, "Linux (EC2, infra/ci-aws)"). This also gives the first
native x86-64 ThreadSanitizer run (Docker on the Mac runs amd64 under
Rosetta, where TSan cannot start).

## Setup

| | arm64 | amd64 |
|---|---|---|
| Instance | c7g.4xlarge (Graviton3) | c7i.4xlarge (Sapphire Rapids) |
| vCPU / memory | 16 / 30 GiB | 16 / 30 GiB |
| AMI | ubuntu-noble-24.04-arm64-server-20261004 | ubuntu-noble-24.04-amd64-server-20261004 |
| Kernel | 7.0.0-1014-aws | 7.0.0-1014-aws |
| Toolchain | go1.26.1 (go.dev), Ubuntu clang 18.1.3, lld, llvm, build-essential, libclang-rt-18-dev | same |

Region us-east-1, default VPC, 60 GB gp3 root, on demand. Each job ran
with its own empty `GOCACHE` (like a separate CI runner); the jobs ran one
after another on each machine and the two machines in parallel. Packages:
`go list -e ./... | grep -v /runs/` (25 packages, 21 with tests).

Jobs:

- **short**: `go vet $PKGS && go test -count=1 -short $PKGS`
- **full**: `go test -count=1 $PKGS`
- **race**: `go test -count=1 -race ./std/rt`
- **sanitizers**: `go test -count=1 -v -run 'Runtime|GoldenThreads|GoldenTasks|Deadlock|ASan|NativeSignal' ./internal/llvm`
  (TSan over the runtime's C tests and the goldens with 1, 2, and per CPU
  workers; ASan and UBSan over net_echo and the http goldens; SIGTERM
  two phase shutdown)

## Failures and fixes

1. **Harness: package list with newlines through `bash -c`** (run 1). The
   job ran `bash -c "go test $PKGS"`; each newline ended the command, so
   only the first package ran and the rest exited 127. Fix:
   `tr '\n' ' '` in `infra/ci-aws/remote-jobs.sh`
   (`gotchas/bash-c-newline-package-list.md`).
2. **Ubuntu's clang has no sanitizer runtimes** (run 1): 82 TSan and 6
   ASan links failed with `cannot find .../libclang_rt.tsan-x86_64.a`.
   Fix: `remote-setup.sh` installs `libclang-rt-18-dev`;
   `build.ClangError` now adds a hint naming the package when a
   `libclang_rt.*` archive is missing (TestClangErrorSanitizerHint)
   (`gotchas/ubuntu-clang-without-sanitizer-runtimes.md`).
3. **Runtime bug: a fault unwinding under ThreadSanitizer crashed**
   (run 2, both architectures). Every golden that faults (fault_unwind,
   fault_tasks, fault_audit, fault_task_exit, http_fault, conc_reentrant,
   conc_reentrant_read, conc_send_closed, conc_await_canceled) died with
   `ThreadSanitizer: SEGV` (pc 0 or a heap address) or `stack-overflow` in
   `_Unwind_Resume` called from `xo_fault_raise`. Cause: `fault_raise`
   kept the `_Unwind_Exception` in its own frame; TSan gives every
   function a cleanup pad that calls `_Unwind_Resume`, which ran after
   that frame was dead and read a clobbered stop function. Fix: the
   exception object lives in `xo_ctx` (`std/llrt/xo_rt.c`). Regression
   test TestRuntimeFaultResume (`std/llrt/testdata/fault_resume.c`): a C
   cleanup that scrubs the stack and resumes; it aborts with the old
   runtime on macOS and Linux and passes with the fix
   (`gotchas/tsan-resumes-fault-unwind.md`). Decision 0085's unwinding
   had never run under Linux TSan: the morning's Docker validation
   predates it, and macOS TSan passed by luck of stack layout.
4. **Test driver leak found by LeakSanitizer** (run 2, both): the
   http_diff driver never freed the per connection response buffer added
   by commit 17fb10f (after the Docker validation). Fix:
   `free(hc.out.p)` in `std/llrt/testdata/http_diff.c`; TestHTTPParseDiff
   is its test (LSan runs only on Linux)
   (`gotchas/http-diff-driver-leak.md`).

Fixes 3 and 4 were verified locally, not on EC2 (the task allowed one
more instance run, already used by run 2): in Docker arm64 (Debian clang
19), the sanitizer set plus every HTTP test passed after the fix and
reproduced the failures before it; the full Docker arm64 suite
(`scripts/linux-test.sh arm64`, vet plus full tests) passed, 21 of 21
packages in 422 s; the host (macOS arm64) vet plus full suite passed in
220 s. Docker amd64
cannot check the TSan fix (no TSan under Rosetta); next step: rerun
`infra/ci-aws/ci.sh sanitizers` on c7i.

Also found while checking locally: `scripts/linux-test.sh`'s default
`./...` failed on the gitignored `runs/` tree, and TestHybridRandom
(added the same morning) had its compilers OOM killed in the 8 GiB Docker
VM even alone; the defaults now exclude `/runs/` and pass `-parallel 4`
(`gotchas/docker-vm-memory-go-compile-killed.md`).

## Cost

Instance lifetime: run 1 about 9.5 min, run 2 about 19 min, so about
0.48 h per machine. At us-east-1 on demand list prices (c7g.4xlarge
about $0.58/h, c7i.4xlarge about $0.71/h) that is about $0.62, plus under
$0.02 for 2 x 60 GB gp3 and two public IPv4 addresses for half an hour.
Total about **$0.65**; one full matrix run costs about $0.45.

## Recommended CI matrix

Two Linux runners (arm64 and amd64), Ubuntu 24.04, with `clang lld llvm
libclang-rt-18-dev` and the host's Go. Times are measured on 16 vCPU
machines with a cold Go cache; a 4 vCPU hosted runner will be slower on
the build heavy jobs (estimate 2 to 3 times, not measured).

| Job | When | Platforms | Expected (16 vCPU, cold cache) |
|---|---|---|---|
| vet + `go test -short` | every push and PR | arm64, amd64 | 2.5 min |
| sanitizers (TSan, ASan, UBSan goldens) | every push and PR | arm64, amd64 | 2 min |
| `go test -race ./std/rt` | every push and PR | amd64 (arm64 nightly) | 2 to 3 min |
| full `go test` | merge to main, nightly | arm64, amd64 | 8.5 to 10 min |
| macOS arm64 full suite | every push (the dev host) | darwin/arm64 | 4 min (host: 220 s warm) |

The PR gate is about 3 minutes of wall time with the jobs in parallel,
plus about 1.5 minutes of machine setup. To bring the full job under 5
minutes, shard it by package: internal/gen, internal/llvm,
internal/arm64 (arm64 only), cmd/xo, and the rest as five jobs; next
experiment: `infra/ci-aws/ci.sh` with a `shard` job per group to measure
each alone. A Go build cache restored between runs (actions/cache on
`GOCACHE`) should also cut the full job substantially; measure with a
warm second run on the same machine.
