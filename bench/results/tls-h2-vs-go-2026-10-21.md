# TLS and HTTP/2 servers against Go's net/http (2026-10-21)

The owner's poll follow-up (lead, 2026-10-21): the same method as the
CRUD gap for the rest of the HTTP side. Harness: `bench/perf/tlsrate`
(`docker.sh XO OUT arm64`: linux/arm64 in Docker, the servers pinned to
cores 0-5 and the Go client to 6-11; `native.sh XO OUT` for the Mac).
Both servers answer `GET /hs` (16 bytes) and `GET /bulk?n=N` (N zero
bytes in 64 KiB writes: chunked on HTTP/1.1, DATA frames on HTTP/2);
the client is Go's crypto/tls and net/http, so only the server side
differs. ECDSA P-256 certificate (RSA 2048 for the rsa row). Two
rounds, interleaved; best round shown.

**Read the ratios, not the absolute numbers.** The machine was loaded by
other agents' gates and a soak during these runs: the same Go server
measured 3,530 MB/s of bulk TLS in one round and 1,648 in another, 10,464
handshakes/s and 2,453. Only a ratio within one round means anything, and
even those swing; a quiet-machine rerun is the next step.

## Before and after the HTTP/1.1 chunk fix (f0aae00e5)

`BodyWriter.write` was bufio's WriteString: a 2 KiB buffer and a chunk
(head, data, CRLF: three TLS records) per 2 KiB, so a body written in
64 KiB pieces made 32 chunks of that. It now follows bufio.Writer.Write
as net/http does: a write larger than the room left goes out whole when
the buffer is empty. Bulk TLS over HTTP/1.1, MB/s, Xo / Go in the same
round:

| workload | before | after |
|---|---|---|
| bulk TLS 1.3 (AES-128-GCM) | 280 / 3,339 = 0.08 | 1,427 / 1,521 = 0.94 (best 0.87 by best) |
| bulk TLS 1.2 AES-128-GCM | 186 / 3,547 = 0.05 | 1,289 / 1,384 = 0.93 |
| bulk TLS 1.2 ChaCha20-Poly1305 | 155 / 892 = 0.17 | 416 / 946 = 0.44 |

HTTP/2 downloads were at parity all along (885 / 805 before; 832 / 950
after), which is what located the problem in the HTTP/1.1 writer rather
than in the TLS record layer.

Note on the handshake rows: the Go rounds ran while the machine was far
busier than the Xo ones (Go 2,453 here against 10,464 in the earlier
run), so their ratio is not meaningful. The CPU per handshake, which does
not depend on how much CPU was free, says Xo's server spends 40% of Go's
CPU per handshake (x25519 188 vs 481 us; RSA 979 vs 2,981 us) and the
earlier run's best rounds had Xo at 1.0 to 1.4 times Go's rate. Server CPU
per request on HTTP/2 with 100 streams: 14 us against Go's 32.

## Where Xo is behind (ranked)

The causes below are hypotheses from the CPU ratios and Go's known
implementation; none is profiled yet (next step: `XO_PROF=cpu` on the Linux
server during each bulk row, and the h2 server's writes counted with
strace).

1. **ChaCha20-Poly1305 bulk: 0.44 of Go**, and 2.2 times Go's CPU per MB
   (2,384 vs 1,080 us/MB). Go has an assembly ChaCha20 and Poly1305 on
   arm64 (NEON); Xo's is the portable algorithm in std/native/llrt.
   Fix: a NEON/vectorized ChaCha20 block function (4 blocks at a time)
   and a 2-limb Poly1305 multiply. std side, no runtime change.
2. **AES-GCM bulk: 0.87 to 0.94 of Go**, 1.46 times Go's CPU per MB (708
   vs 484 us/MB): the GHASH and CTR paths (`aesgcm.hw4`, decision 0202
   history); Go's `gcmAesEnc` interleaves CTR and GHASH in one pass over
   8 blocks. Fix: fuse the CTR and GHASH loops per 128 byte chunk.
3. **HTTP/2 with one stream: 0.52 of Go** (p50 104 us against 45 us in
   the first run): a single request in flight pays the park/wake of the
   scheduler (the same coordination as the CRUD gap, decision 0324) and,
   per request, Xo's h2 server does not write a response's HEADERS and
   DATA in one TLS record when the body is small. Fix after 0324: the
   netpoller change; and coalescing HEADERS+DATA+(END_STREAM) of a small
   response into one write (Go does).
4. HTTP/2 download: 0.88 to 1.1 of Go (parity).

Where Xo is ahead: HTTP/2 with 100 streams (1.9 to 2.7 times Go's
requests per second, half its CPU per request), handshakes (40% of Go's
CPU per handshake).

## The profiles (XO_PROF=cpu, 1 kHz, the Linux arm64 server, same afternoon)

`XO_PROF=cpu XO_PROF_HZ=1000` on the Xo server in the container during
each lagging row (the load client on cores 6-11; the machine was loaded,
so shares, not times). Profiles: ~/xo-lead/notes/Xo Lang 3/ (xo prof
text of each).

**TLS 1.3 bulk (AES-128-GCM), 1,061 samples:** `tlssrv.send_all` 27.7%
(the kernel's sendto; the same call Go makes), `aesgcm.Gcm.ctr_at` 33.0%
cumulative (`aesgcm.enc_at` 23.5% flat, the AES rounds), `aesgcm.ghash_hw`
20.5%, `libcstr.copy_words` 9.9% (a copy of each record's plaintext
before encrypting), shifts 2.6%. So 54% is the cipher (CTR and GHASH
separately, two passes over each record) and 10% a copy: hypothesis 2
(CTR and GHASH not fused) holds, and the copy is new: encrypting in place
from the response buffer into the record buffer, or reading the source
as the CTR input, removes the 10%.

**TLS 1.2 ChaCha20-Poly1305 bulk, 2,304 samples:** `chacha.xor_stream`
56.9% cumulative (792 ms flat, and `chacha.add` 13.0% and `chacha.shr`
2.0% flat), `chacha.absorb` (Poly1305) 16.8%, `chacha.push_xor` 12.1%
(already a word XOR, std/native/llrt/chacha.xo:165, whose `rs_push_word`
call costs 4.3% in `obj.rs_push_word`), `chacha.dot5` 3.3%,
`tlssrv.send_all` 12.4%, `copy_words` 4.4%.

Correction (same day): the first reading of this profile took `chacha.add`
and `chacha.shr` for calls that were not inlined. They are not: the
linux/arm64 server and the Mac's have no `chacha.add` symbol at all
(`strings`/`nm` of the binaries; xor_stream makes 31 calls, none of them
add), so the helpers are inlined and the profiler reports their frames
from the inline information. Their 15% is the quarter-round's additions
and shifts, i.e. the work itself. What remains: the scalar quarter-round
is 32-bit work done in 64-bit registers with a mask per add
(`wrapping_add(...) & M32`; Go's assembly does 4 blocks at a time on
NEON), Poly1305's `absorb` 17%, and the XOR/push 12%. The fix is
therefore vectorization (4 blocks per call, which decision 0323's SLP
pass might produce from a 4-block source) or 32-bit adds, not inlining;
nothing to change in the inliner for this row.

**HTTP/2, one stream, 1,473 samples:** `pool.futex_wake` 20.4% and
`linux.futex` 7.6% (28% of the server's CPU is waking a worker),
`sock.epoll_wait` 6.5%, `sock.read` 5.8%, `tlssrv.send_all` 21.1%. One
request at a time means every request parks and wakes: hypothesis 3's
scheduler part holds (the same cost as the CRUD profile's
`pool.futex_wake`), and decision 0324 (idle workers poll the network
themselves) should remove most of the 28%; remeasure after it lands. The
HEADERS and DATA write coalescing is not shown (no separate send rows
beyond `send_all`); count the sendto calls with strace to settle it.

## After decision 0329 (ChaCha20 four blocks at a time, 7f6e6c203)

The same Docker harness (linux/arm64, `docker.sh XO OUT arm64`, two
rounds interleaved, best / median MB/s; the machine had a soak running,
so compare within a round) on main at 7f6e6c203:

| row | Go | Xo | Xo / Go | server CPU per MB, Go / Xo |
|---|---|---|---|---|
| bulk TLS 1.2 ChaCha20-Poly1305, round 1 | 963 / 953 | 754 / 723 | 0.78 / 0.76 | 1,006 / 1,378 us |
| bulk TLS 1.2 ChaCha20-Poly1305, round 2 | 967 / 949 | 735 / 732 | 0.76 / 0.77 | 1,043 / 1,341 us |
| bulk TLS 1.3 AES-128-GCM, round 1 | 2,230 / 1,991 | 1,393 / 1,141 | 0.62 / 0.57 | 484 / 857 us |
| bulk TLS 1.3 AES-128-GCM, round 2 | 2,555 / 2,415 | 1,472 / 1,352 | 0.58 / 0.56 | 372 / 745 us |
| bulk TLS 1.2 AES-128-GCM, round 1 | 3,363 / 2,477 | 1,222 / 1,222 | 0.36 / 0.49 | 372 / 819 us |
| bulk TLS 1.2 AES-128-GCM, round 2 | 3,503 / 3,185 | 1,309 / 1,225 | 0.37 / 0.38 | 298 / 819 us |

- ChaCha20 went from 0.44 of Go (416 MB/s against 946 in the earlier
  run) to 0.76 to 0.78 (735 to 754 MB/s), and from 2.2 times Go's server
  CPU per MB (2,384 against 1,080 us) to 1.3 times (1,341 to 1,378
  against 1,006 to 1,043). What is left is Poly1305's `absorb` (17% of
  the earlier profile) and the record assembly.
- AES-GCM reads worse than in the first run (0.87 to 0.94 of Go there,
  0.4 to 0.6 here) because Go's own rate swung from 1,521 to 2,555
  MB/s between runs while Xo's stayed at 1,200 to 1,470: the earlier
  ratio was taken against a slower Go round, and the CPU per MB (1.8 to
  2.7 times Go's here, 1.46 times there) is the steadier figure. The
  gap is real and larger than first reported: Go's `gcmAesEnc`
  interleaves CTR and GHASH, and the earlier profile had Xo's two passes
  at 54% of the server's time. This remains the next item for a quiet
  machine.
