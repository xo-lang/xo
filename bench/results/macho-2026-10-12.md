# The self hosted Mach-O assembler and linker (2026-10-12)

Decision 0182. `selfhost/macho`, in Xo, assembles the arm64 emitter's
assembly into Mach-O objects (stage 1) and links them into executables
(stage 2), so xo1 needs no `cc`.

## Setup

- Host: darwin/arm64, macOS 27.0, Apple clang 21.0.0
  (clang-2100.1.1.101), `GOMAXPROCS=4`. About ten agents shared the
  machine, so wall times are noisy; counts are exact.
- The assembler: `selfhost/macho` built by the Go `xo` with
  `--backend=arm64` (`xo build --backend=arm64 -o macho ./macho` in
  `selfhost/`).
- Inputs: the assembly of every arm64 golden (`xo asmdump` of the 133
  `internal/llvm/testdata/golden` and 25 `internal/arm64/testdata/run`
  programs, 158 files, 1,212,359 lines) and of xo1 itself (`xo asmdump
  selfhost/xo`, 13,759,561 lines, 258 MB).
- Comparison: `scripts/macho-compare.py <macho> <files.s>` assembles
  each file with `macho asm --minos=27.0` and `cc -c` (clang -cc1as),
  and compares whole files, each section's bytes, each function's
  `__text` bytes (between consecutive symbols), and the relocation
  tables with symbol numbers replaced by names.

## Stage 1: the assembler

| Input | Objects identical | Functions identical | Sections identical | Relocation tables identical | Object bytes (macho / cc) | Assembly time (macho / cc) |
|---|---|---|---|---|---|---|
| 158 arm64 goldens | 158 of 158 | 3,792 of 3,792 | 904 of 904 | 904 of 904 | 6,596,328 / 6,596,328 | 1.45 s / 9.93 s (all files) |
| xo1 (selfhost/xo) | 1 of 1 | 2,825 of 2,825 | 6 of 6 | 6 of 6 | 57,025,520 / 57,025,520 | 4.92 s / 35.40 s |

Every section (`__text`, `__gcc_except_tab`, `__const`, `__cstring`,
`__compact_unwind`, `__eh_frame`) and every relocation is identical to
the system assembler's on every input. The first version (commit
ad34851) wrote 38 of the 158 golden objects byte identical: the other
120 differed only in the order of the local symbols (and so in the
symbol numbers of relocations and the string table offsets). LLVM
registers a symbol when it is defined or when an instruction or data
directive first names it, whichever comes first, and orders the local
symbols that way; with that rule (and S_ATTR_SOME_INSTRUCTIONS only on
a `__text` that holds instructions) all 158 objects, and xo1's, are
byte identical.
Peak memory on xo1's assembly: 1.01 GB (macho) and 0.98 GB (cc).

## Stage 2: the linker

`macho link` (and `xo1 build --ld=macho`) links the program's object
with the prebuilt runtime of a pack (`xo rtpack`, decision 0157) and,
for std/http, the pack's `libxotls.a` and the Security and
CoreFoundation frameworks.

| Check | Result |
|---|---|
| goldens, xo1 `--ld=macho`, `PATH=/nonexistent` for every xo1 build | 158 of 158 pass (33.61 s script wall time) |
| std/time zones (`internal/gen/testdata/golden/time_zones`), zone data as an object | same output as the cc build (16 lines); 443,826 / 434,200 bytes |
| A (xo1 above, cc linked, 54,938,784 bytes) builds B = xo1 with `--ld=macho`, `PATH=/nonexistent` | 660.3 s, 4.46 GB peak; B is 54,907,856 bytes |
| B builds C the same way | 712.7 s; B and C byte identical, and their assembly too |
| goldens with B, `--ld=macho`, `PATH=/nonexistent` | 158 of 158 pass (28.91 s) |

So the self hosted compiler builds itself to a fixed point and builds
every arm64 golden with no C compiler, assembler, or linker on the
machine's PATH (only the prebuilt runtime pack, and Go's zoneinfo.zip
through `XO_ZONEINFO` for std/time).

Scratch comparison before the xo1 runs (each golden's `xo asmdump`
assembly assembled by macho, linked by cc and by `macho link` with the
same pack object, both run): 152 of 158 outputs identical, the other 6
differing only in the leak check's allocation count, which varies run
to run for concurrent programs (the golden script ignores that line).

| Measure | macho link | cc (ld) |
|---|---|---|
| bytes of the 158 golden binaries | 68,059,326 | 68,127,680 |
| link of the recursion golden (median of 10) | 0.010 s | 0.054 s |
| link of xo1 (57 MB object + runtime) | 0.44 s, 297 MB peak | 0.11 s |
| xo1 binary | 54,167,811 bytes | 54,198,376 bytes |

What the linker does not do that ld does: dead stripping and literal
merging (none was asked for), LC_FUNCTION_STARTS, LC_DATA_IN_CODE,
LC_SOURCE_VERSION, a full exports trie (only `__mh_execute_header`),
checking imports against the SDK's `.tbd` files (a missing import fails
at launch, not at link time).

## Stage 3: ELF for linux/arm64 (2026-10-12)

`macho asm --elf` (`assemble_elf`) writes the emitter's linux/arm64
assembly as an ELF64 relocatable object, and `macho elflink`
(`link_elf`) links it with the linux/arm64 runtime pack into a
dynamically linked executable for glibc; `xo1 build
--target=linux/arm64 --ld=macho` does both from any host.

Setup: the same Mac; inputs `xo asmdump --os=linux` of the 159 arm64
golden directories (134 `internal/llvm/testdata/golden`, 25
`internal/arm64/testdata/run`, 1,346,211 lines; run from each golden's
directory) and of xo1 (`selfhost/xo`, 14,890,287 lines). The reference
assembler is Apple clang 21 with `--target=aarch64-linux-gnu -c` (LLVM's
ELFObjectWriter, as zig cc uses). The linux pack: `xo rtpack
--target=linux/arm64` with Apple clang 21, `--sysroot` of Debian
bullseye's glibc 2.31 and kernel headers, and a GNU format archiver
(gotchas/apple-ar-drops-elf-members.md). Docker Desktop was already
running (not started for this); the containers have no C compiler,
assembler, or linker.

### Objects (`scripts/elf-compare.py`)

| Input | Objects byte identical | Functions identical | Sections identical | Relocation tables identical | Object bytes (macho / clang) | Assembly time (macho / clang) |
|---|---|---|---|---|---|---|
| 159 arm64 goldens | 159 of 159 | 4,159 of 4,159 | 1,193 of 1,193 | 1,193 of 1,193 | 8,569,040 / 8,569,040 | 2.84 s / 16.66 s (all files) |
| xo1 (selfhost/xo) | 1 of 1 | 3,306 of 3,306 | 8 of 8 | 8 of 8 | 67,549,912 / 67,549,912 | 5.81 s / 33.49 s |

Peak memory on xo1's assembly: 0.52 GB (macho) and 1.06 GB (clang);
`xo asmdump --os=linux` of xo1 peaked at 10.8 GB. The first version that
compiled matched clang byte for byte on every input: LLVM's ELF writer
orders local symbols by registration as the Mach-O one does, and the new
rules were few (section symbols only when a relocation names them,
`$x`/`$d` mapping symbols, a CIE data alignment of -4, FDEs padded to 4
bytes and the last to 8, groups after the sections, relocations after
the symbol table).

Each golden's object linked by `macho elflink` with the pack's runtime
variant its assembly selects (and `libxotls.a` for std/http), all 159
run in one container with XO_LEAKCHECK=1, compared with want.txt or the
Go backend's output on the Mac:

Sizes and times are of the version with a `.symtab` (functions and
objects; commit after a027e57); without it the two binaries were 300,088
and 880,168 bytes. Both glibc runs above were repeated with it: 159 of
159 each.

The cc build of arith (same objects) prints the same output.

xo1 with the linker (`scripts/elf-goldens.py <xo1>`): xo1 built by the Go
`xo` at commit cf9ab7e (226.18 s, 9.49 GB peak, other agents running)
built all 159 goldens with `--target=linux/arm64 --ld=macho` and
`XO_RTPACK` set; 133 of the binaries are byte identical to the harness's
above (which passed 159 of 159 in both containers). The run in Docker
did not happen: the Docker daemon had stopped by then (`Cannot connect
to the Docker daemon`; not started again here), so the 26 others are
built but not run. They differ from the harness's binaries because the
harness ran `xo asmdump .` in each golden's directory, which names the
package `.` where xo1 names it after the directory (string data and
symbol names; in contract_ensures and defer_blocks also the frame
layout), not because of the linker. What the
linker does not do that cc's does: a position independent executable
(it writes ET_EXEC at 0x400000), `.init_array` and `.fini_array` (none of the inputs
has one; the link refuses them), GC of sections, checking imports
against the libraries (a missing symbol fails at load time).

## Default linker and zone data (decision 0182 next steps 1 and 2, 2026-10-12)

Commits 9c7bee7 (the default, one SSA per target OS, `rtpack --status`
arch, zoneinfo.zip beside the pack) and 19824630 (the flag scan fix
below). Host: darwin/arm64, Apple M4 Pro, 24 GB, macOS 27.0, Apple clang
21.0.0; about ten agents shared the machine, so wall times are noisy;
counts are exact. xo1 was built by the Go seed (`XO_SELF_DRIVER=0 xo
build --backend=arm64 selfhost/xo`, cc linked, 354 s) into a release
layout (`bin/xo`, `lib/xo/std`, `lib/xo/third_party`,
`lib/xo/rtpack/darwin-arm64` from its own `xo rtpack`,
`lib/xo/zoneinfo.zip` copied from `go env GOROOT`).

The rule (selfhost/xo main.xo `default_ld`): with no `--ld`, the host's
darwin/arm64 link is selfhost/macho's when `--as` is not cc, no `use c`
module is linked, and the pack has the runtime variant of the link's
flags (and the TLS library for std/http); otherwise cc, as before. A
linux host keeps cc until the ELF linker writes PIE (stage 3 next step
1). Which linker made a binary: ld writes LC_SOURCE_VERSION, selfhost/macho
does not (`otool -l`).

### Goldens (`scripts/selfhost-goldens.py`, 133 + 36 = 169 programs)

| xo1 flags | Result | Linked by (LC_SOURCE_VERSION count) | Bytes of the 169 binaries | Script wall time |
|---|---|---|---|---|
| `--ld=cc` (the old default) | 169 of 169 pass | ld: 169 of 169 | 70,509,104 | 28.11 s, 26.54 s |
| none (the new default) | 169 of 169 pass | selfhost/macho: 169 of 169 | 70,435,324 | 25.91 s, 24.54 s |
| none, `XO1_PATH=/nonexistent` (no cc, no Go) | 169 of 169 pass | selfhost/macho | | 24.62 s |

Fallbacks checked by hand with the same xo1: a `use c` program
(internal/selfhost/testdata/ssa/stage6c) links with cc (`phase cc`) and
runs; `XO_RTPACK=off` and `--as=cc` link with cc; a plain program's link
phase is 19 ms with macho against 55 ms with cc.

### The fixed point (`scripts/bootstrap-xo.sh`, stage7-prep's chain)

Seed: the xo1 above; no `go` on PATH; each stage with empty caches.
`XO_BOOTSTRAP_RTPACK=DIR` (new) passes the pack instead of
`XO_RTPACK=off`.

| Run | s1 | s2 | s3 | s2 = s3 assembly | s2 = s3 binary | Linked by |
|---|---|---|---|---|---|---|
| before: `XO_RTPACK=off` (cc; runtime and TLS compiled locally) | 659 s | 586 s | 588 s | identical, 395,441,956 bytes | identical, 79,060,128 bytes | ld |
| after: the pack, default linker (19824630) | 751 s | 587 s | 583 s | identical, 395,441,956 bytes | identical, 79,002,335 bytes; s1 equals s2 | selfhost/macho (s1, s2, s3) |

s3 of both runs reports `xo 0.9.0 darwin/arm64` and builds and runs a
hello program. The macho binary is 57,793 bytes smaller. The stage
times are within the noise of the shared machine (s1 of the second run
started while other agents' heavy runs were finishing); the link itself
is under a second of each stage (0.44 s for xo1, stage 2 above).

A first run with the pack (at 9c7bee7) still linked every stage with
ld: xo1's own assembly holds the names of the `-DXO_TEXT_C` and
`-DXO_STRINGS_C` runtime symbols as string literals (its io_flags
table), and those two scans used a plain substring test, so the link's
flags matched no pack variant and the default fell back to cc (it
reached the same fixed point: assembly 395,442,052 bytes, binary
79,060,864 bytes, s1 601 s, s2 607 s, s3 615 s). 19824630 makes both scans
count only references, in IOFlags and io_flags
(gotchas/runtime-flags-from-string-literals.md).

### Zone data with no Go (decision 0157 next step 1)

With `PATH=/nonexistent` (no Go, no cc) and the release layout above,
`xo build --backend=arm64` of internal/gen/testdata/golden/time_zones
and time_dynamic_zone succeeds and the binaries' output equals want.txt
(16 and 7 lines; 444,567 and 840,302 bytes); with lib/xo/zoneinfo.zip
moved away the same build fails with `zone data: cannot find GOROOT:
NotFound(cmd: "go") (a release has lib/xo/zoneinfo.zip; ...)`.

### Driver gaps from switch point B

- One SSA per target OS: `xo asm --backend=arm64
  --targets=darwin/arm64,linux/arm64` of a program matching on
  `target.os` loads 1 (Darwin) in the darwin assembly and 0 (Linux) in
  the linux assembly; before, both were the host's.
- `rtpack --status` loads the pack of the host's OS and architecture
  (an amd64 host now looks for linux-amd64, as the Go driver's
  `loadRTPack(Host())`); an arm64 link still uses the arm64 pack. Not
  run on an amd64 host here.
