# Rust against Xo: 2026-11-22

Written by bench/perf/rust/run.sh (twins/lib.sh). Ratios are Xo over Rust (below 1: Xo is faster or smaller).

## Machine and versions

- Linux 7.0.14-linuxkit aarch64, host 1 (the linux/arm64 timing host, exclusive lease; label added by hand 2026-11-22, the header of this run left it empty), 12 CPUs, load average at start 0.21
- xo 0.55.0 commit 9599fc7d key ff3b0011426efd26, NOT THIS CHECKOUT (its key is 13809f7545321ed6)
- go version go1.26.11 linux/arm64
- cargo 1.99.1 (5f94df478 2026-08-27), rustc 1.99.1 (58cf8f9c3 2026-10-13)
- crates (Cargo.lock): axum 0.8.9;hyper 1.12.0;serde 1.0.229;serde_json 1.0.154;tokio 1.54.1;
- release profile of every crate: opt-level 3, codegen-units 1, thin LTO, panic abort

Run on the linux/arm64 timing host (host 1) in leases of at most 30
minutes: compute (with a first concurrency pass), then json, then the
concurrency rows again after the rwmutex row of the first pass came out
empty (its own threads lifted the load over xo bench's limit; rwmutex
and pmap now run with --max-load, named in their header). The load line
of each table is its start. The xo is the published 0.55.0 release binary, measured against
the tree at 7609e1f5f6 (the REPEAT counts of task #687), hence the "NOT
THIS CHECKOUT" stamp: the Xo programs are built by 0.55.0 with its own
std. Every program runs its row REPEAT times in one process (the second
argument), so the faster side takes about 1 s; the multi thread tokio
pingpong row runs REPEAT 10, since tokio's multi thread runtime takes
about 3 s a REPEAT on this host. The HTTP rows were not rerun; the
2026-10-23 file still holds them.
