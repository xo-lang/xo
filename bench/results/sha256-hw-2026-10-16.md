# SHA-256 with the CPU's instructions (2026-10-16)

The owner approved a SHA-256 intrinsic (2026-10-16, decision 0231's
SHA-256 section): `cpu.sha256_block`, one block's compression, lowered
to SHA256H, SHA256H2, SHA256SU0, and SHA256SU1 on arm64 (both native
backends), the portable body elsewhere. sha256.xo's block256 and
words256 take it when cpu.hw() has HW_SHA256 (macOS arm64 always, Linux
arm64 by AT_HWCAP), so TLS (transcripts, HKDF, HMAC, certificate
checks) and std/crypto's sha256, hmac_sha256, and PBKDF2 all use it.

## Method

The development Mac, the heavy lock, instructions retired, best of 5.
Before: main bc2068c8 (adc chains on). After: the same with this change.
Handshakes: bench/perf/tls measure.sh, N = 50; client rows are the
client process's instructions over 50 (its start included), server rows
are (N = 50 less N = 0) / 50. PBKDF2: a scratch program (not in the
repo) running crypto.hash_password with 100000 iterations, then 16000
crypto.sha256 calls on 1000 bytes.

LLVM 1130.2M to 239.6M (4.7 times fewer).

## Correctness

- TestSHA256HWDiff (new): the instructions and the body against a Go
  reference compression (edge states and blocks, 200 random), and std's
  SHA-256 one shot and split against crypto/sha256 (lengths 0 to 200,
  1000, 4095 to 4097, 100000), on arm64 and LLVM.
- The first run failed the split cases and every TLS 1.2 golden: the
  raw writes bypassed the state list's copy on write
  (gotchas/raw-writes-bypass-copy-on-write.md); fixed with an index
  store first.
- The crypto and TLS goldens, the TLS, X.509, and crypto diff tests,
  selfhost/macho's encoder table (clang's encodings), the codegen
  patterns (sha256.block256 has sha256h and sha256h2 on arm64 and the
  inline asm on LLVM), TestGoldenRunSpill, -short, the fixed point.
