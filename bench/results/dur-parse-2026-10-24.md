# Duration.parse: one branch a digit instead of four, 3.4% fewer instructions, 2026-10-24

`text.parse_duration` walks the digits of a duration's numbers one byte at
a time. Each digit cost four branches: two for `c < 0 || c > 9`, one for
the magnitude guard, and one for the range guard after the multiply. The
digit loop now takes one branch for the digit test and none for the
guards, and the whole function is 3.4% fewer instructions.

## The change

std/native/llrt/text.xo, the integer part of a duration's number:

- the digit test is `!(c >= 0 && c <= 9)` on the computed digit, which
  the native backends fold into one unsigned compare (`sub`, `cmp #9`,
  `b.hi`), where `c < 0 || c > 9` took two branches and computing the
  digit twice took a second `sub`;
- the per digit magnitude guard (`nv < -2^63/10`) is gone: eighteen
  digits cannot leave the range (10^18 < 2^63 / 10), and a run longer
  than eighteen is read again with the guard, after the loop;
- the second per digit guard (`t < MIN_INT + c`) is gone: with the
  magnitude guard the product is exact, and the one sum that leaves the
  range, the last digit of -2^63, wraps positive, so one test after the
  loop finds it.

The fraction part keeps its guard a digit (a fraction may be longer than
eighteen digits and Go's parse saturates) but takes the same single
range test, into a temporary: the value the loop keeps is the last one
that did not wrap, so a fraction that passes 2^63 keeps the digits it
read, as Go's leadingFraction does.

## The fraction guard, and the bug the merge first shipped

Folding the fraction's two guards into one first kept the wrapped value:
`nf = nf.wrapping_mul(10).wrapping_sub(c)` turned a fraction whose 19th
digit passes 2^63 positive, and the parse then skipped the fraction
entirely, so `1.9223372036854775809s` read 1s where Go reads
1.922337203s (found by Xo Lead reviewing the commit, 2026-10-25). The
loop computes into a temporary and assigns only when it did not wrap,
which is the original behaviour. std/native/llrt/text_test.xo now pins
it (fractions of 18, 19 and 20 digits, at and past 2^63, with and
without a sign), the `time` corpus carries the same rows with Go's
answers, and stdfuzz's time area draws from them; the test fails on the
merged form and passes on the fix.

## A/B, one revision, A = base, B = the change

`xo bench --ab`, 12 rounds, `bench/perf/text`, one xo binary building the
same source with each side's std. B/A below 1.0 is better.

| workload | A instructions | B instructions | B/A | A wall ms | B wall ms | B/A |
|---|---|---|---|---|---|---|
| dur_parse, this change | 148,684,444 | 143,660,045 | 0.966 | 10.09 | 9.799 | 0.971 (interval 0.872 to 1.034, within noise) |
| dur_parse, before the fraction fix | 148,877,955 | 141,418,651 | 0.950 | 18.44 | 17.16 | 0.931 (interval 0.622 to 1.233) |

The second row is the same change with the fraction loop's merged guard,
which read the wrong value (see above): it is 1.7% better only because it
skipped the assignment that keeps the digits Go keeps. The checksum of
the row is identical on both sides. max_rss_kb is 0.984 (4,368 to 4,296);
the measured wall intervals overlap and the instruction row is
deterministic. The two earlier steps, taken alone, were 0.998 (the digit
test) and 0.963 (the guard merge).


## What is left in the loop

Per digit, the loop is now about eleven instructions: the loop test, the
bounds check against the Bytes' length (`cmp`, `b.hs`), the byte load,
`sub`, `cmp #9`, `b.hi`, the multiply, the subtract, the index add, and
the back edge. The bounds check is the next candidate: one check before
the loop with `raw.data` and `raw.byte_at` in the body replaces it.
`raw.data` is view-safe, which std/native/llrt/raw_test.xo now shows
(`byte_at(data(v), 0)` on `str_slice("abcdefghij", 7, 10)` is 104, and a
view of a view reads right too), so the hoist is available.

## Coverage

The `time` and `strconv` corpora on arm64 and llvm, `stdfuzz` area time
(the duration cases), the wasm goldens and the full fixed point.
