# Real-time mode: tick latency and jitter (2026-10-10)

Decision 0133. Program: `examples/realtime-control` (a 32 tap FIR, a PID
controller, a simulated first-order plant, a 4096 entry output ring; every
5,000 ticks a supervisor hands the tick a new setpoint schedule of 20,000
points with a Str label each, and the tick drops the last reference to the
old one). Three versions of the tick:

- **rt**: `uses realtime`, checked by the compiler; the call is a
  real-time section, so the old schedule's 20,001 frees are deferred to
  the section's end (after the tick's output).
- **plain**: the same source without the mark (no section): the old
  schedule is freed inside the tick.
- **alloc**: the controller as written without the rules (a growing
  history sliced each tick, a status line per tick, a log cleared every
  1,000 lines). It does not pass the checker as real-time.

Measured per tick with the monotonic clock (`clock_gettime_nsec_np
(CLOCK_UPTIME_RAW)`, 41.7 ns ticks, through `use c ... uses none` so the
real-time tick can read it): **call** is from before the call to after it
returns (section exit and its deferred frees included); **output** is
from before the call to the tick's last statement, after the actuator
value is written (what a deadline depends on). 200,000 measured ticks
after 1,000 warm-up ticks, 40 swaps; back to back (no sleep), one thread.
Apple M4 Pro, macOS 27.0, normal scheduling (no real-time thread class),
the machine otherwise idle. Command:
`xo build --backend=arm64` (and `llvm`) of `examples/realtime-control`,
then `./ctl <mode> 200000 5000`. Three runs each; all three listed as
`a / b / c`, nanoseconds.

## Reading

- **Deferred frees bound the output latency.** On a swap tick, the plain
  tick frees 20,001 objects before it writes its output: 30 to 114 us.
  The real-time tick writes its output in 166 to 209 ns (one arm64 run
  2.6 us), the same as any other tick; the frees run after it, in the
  section's exit. Over all 200,000 ticks the real-time output maximum
  is 1.2 to 7.8 us, against 39 to 114 us for plain, a 5 to 95 times
  smaller worst case.
- **The work is moved, not removed.** The swap tick's call latency is the
  same or slightly higher in rt mode (llvm 31 to 34 us against 30 us;
  arm64 58 to 79 us against 56 to 57 us): the drain walks the same
  20,001 objects, through the runtime's `xo_rl_free` rather than the
  generated drop helper's inlined first level.
- **The rules matter more than the runtime.** The allocating version's
  median tick is 2.6 us, 60 times the 42 ns of the rt and plain ticks,
  and its p99.9 is 7 to 10 us. Ticks that follow the rules but are not
  marked (plain) are as fast as rt ticks except where a free cascade
  lands in them; the mark is what makes the compiler keep them that way.
- **Section overhead** is below the clock's resolution: rt and plain have
  the same p50 (41 to 42 ns, one clock tick) and the same p99.9 within
  one tick (two calls into the runtime and a thread local depth).
- **Outliers from the OS remain.** One llvm rt run had a 1.32 ms tick and
  one arm64 alloc run a 1.77 ms tick, both on ticks without a swap: the
  process was descheduled. A real-time section cannot prevent that;
  pinning a thread with a real-time scheduling class
  (`pthread_set_qos_class_self_np` on macOS, `SCHED_FIFO` on Linux) is
  the next experiment, with the same program on the Linux machine of
  `linux-2026-10-09.md` under `chrt -f 80`.

## Next experiments

- Pace the loop at a fixed period (1 kHz and 10 kHz, spinning on the
  monotonic clock) and report deadline misses rather than back to back
  latency; the program needs a `--period` argument.
- Make the drain cheaper than the inline free (it is 3 to 40 percent
  slower on the swap tick): free a deferred List of Str with a loop that
  frees the strings directly instead of calling the element drop
  function through a pointer per element.
- Run the same comparison on the Go backend, which checks the rules but
  has no sections: the program needs a clock other than `use c` (which
  is XO1201 there), for example a std `Clock.monotonic_ns` that real-time
  code may call (decision 0133 leaves clock reads for later).
