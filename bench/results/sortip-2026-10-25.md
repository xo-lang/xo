# List.sort_in_place against List.sort on 2,000,000 elements, 2026-10-25

Step 2 of ADR 0374 lands the two mutating sorts, and this is what they
cost today: `sort` builds a second list, so it needs a second element
array, and `sort_in_place` sorts the receiver's own array with a scratch
of at most half a list. The moves still count and release (an assignment
`xs[i] = xs[j]` counts, by design), so this file measures the shape, not
the reference-counting win step 3 is for.

## How it was measured

Probe: `bench/perf/sortip/xo`, built with the tree's `xo` at
`XO_INLINE_STRICT=1`, arm64. On 2,000,000 elements each: Ints below
1,000,000, Strs `"key"` with a number below 100,000,000, and UInt8 over the
byte range. A `gen` mode builds the list and reads it; `sort` and `sort_by`
build and sort with the non-mutating forms (the latter with the identity
key); `ip` and `ipb` build and sort with `List.sort_in_place` and
`List.sort_in_place_by`. Three runs a mode with `/usr/bin/time -l` (wall,
max RSS, instructions retired), the median taken; the sort's cost is the
sorted run's numbers minus its own gen run's. **The wall column is
indicative only:** these runs went under heavy load (load average 15 to 20
while they ran, several agents' builds on the machine), so the instruction
and RSS columns are the ones to read. Every mode printed the same
checksum in all three runs, and the four sorting modes print the same
checksum for the same input (901184094 Ints, 987883420 Strs, 838940239
UInt8; the
Strs value is also the one bench/results/sortstr-inplace-2026-10-25.md
recorded for the same 2,000,000 keys).

`sort_in_place_by` against its own non-mutating form, which is the fair
comparison (both pay a keys array and an index array): **1.12, 1.09 and
1.12 times `sort_by`'s instructions and 0.86, 0.89 and 0.81 of its extra
RSS**; it drops the output array `sort_by` builds and permutes in the
receiver instead. Its wall is worse than `sort_by` (0.44 against 0.23 s on
Ints, 0.96 against 0.78 on Strs, 0.24 against 0.07 on UInt8) and that is
the one place it looks bad: the permutation walks the receiver in cycle
order while `sort_by` writes its output sequentially, so it misses the
cache far more; the instruction counts say the work is nearly the same.
Against the *plain* forms it is much heavier (1.77 against 1.00 billion
instructions on Ints, 46.3 against 16.0 MB more RSS): that is the keyed
path's price for two more arrays, which `sort_by` pays too.

## What the numbers say

- **Step 2 costs instructions until step 3 lands: 1.12 to 1.42 times
  `sort`'s.** Every move in the merge is a store plus a retain and a
  release, and the merge also compares full Strs where the index sort
  compares seven byte prefixes and gathers the Strs once. That is the
  counting ADR 0374's step 3 removes by moving elements with
  `rt.list_swap`, which neither counts nor releases.
- **The memory promise holds, most on Strs.** The second element array is
  gone and the half list of scratch is what is left: 22.7 MB against 80.0
  MB of extra RSS for 2M Strs, 0.28 of it. Ints and UInt8 keep the
  scratch's half list, which is small against their own arrays (0.89 and
  0.85), so the shape only pays where an element is big, which is the case
  0374 was written for.
- **Strs are faster in wall today despite 42 percent more instructions**
  (0.63 to 0.52 s, 0.83, indicative only under the load): the index sort
  gathers through a `List[Int]` of indices in sorted order, so its writes
  and reads are scattered, while the merge walks each run in order. The
  instruction count is the honest metric here; the wall difference says
  the index sort is memory bound.
- Ints and UInt8 are roughly a wash in wall (0.13 to 0.14 s, 0.04 to
  0.04 s) at 12 and 18 percent more instructions; wall at this size and
  timer resolution cannot separate them.

Not measured here: any reference-counting win, which needs step 3 (the
merge's moves as `rt.list_swap` swaps), and the same table on the wasm and
Go backends.
