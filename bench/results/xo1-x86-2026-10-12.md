# xo1 on x86-64 hosts, 2026-10-12 (decision 0178 stage 7, decision 0196)

The self hosted driver xo1 (selfhost/xo) built by the LLVM backend on
x86-64 hosts: how long the build takes and how much memory it needs,
the LLVM goldens built by that xo1, and the bootstrap fixed point with
no Go toolchain (scripts/bootstrap-xo.sh: the LLVM-built xo1 builds
selfhost/xo with `--backend=llvm` (s1), s1 builds it (s2), s2 builds it
(s3); s2 and s3 must write the same IR and the same binary).

Script: scripts/xo1-host-check.sh, run on EC2 by
scripts/remote-xo1-x86.sh and on the Intel Mac by
scripts/intel-mac-test.sh. Steps: `go build ./cmd/xo`; that `xo` with
switch point A on builds a hello program with `--backend=llvm`, which
builds xo1 from its embedded sources first (internal/selfdriver
`buildXo1`, the step measured as "xo1 build"); scripts/selfhost-goldens.py
with that xo1 and `XO1_BACKEND=llvm` (169 programs: 144
internal/llvm/testdata/golden programs against want.txt plus 25
internal/arm64/testdata/run programs against the Go backend's output);
scripts/bootstrap-xo.sh with that xo1 as the seed; the 144 want.txt
goldens again with s3 and no Go (`XO_GOLD_NO_GO=1`, PATH=/usr/bin:/bin).
Peak memory: /usr/bin/time's maximum resident set of the largest process
(`-v` on Linux, `-l` on macOS, which also prints the peak footprint), and
on Linux the machine's peak memory in use (`free -m` every 5 s).
Step logs: bench/results/remote/xo1-x86-<commit>/ (git ignored).

### Why run 1's binaries differed: ThinLTO names promoted locals by module path

Run 1 had the same IR from s2 and s3 and different binaries. A split
LLVM build of internal/llvm/testdata/golden/arith on linux/amd64
(`XO_LLVM_SPLIT=4`, the Go `xo`, two build directories, same output
name):

| LTO | binaries |
|---|---|
| thin | differ in 3,222 bytes: promoted local symbols such as `.str.llvm.5034768877752663559` against `.str.llvm.5079878302894671192` |
| none | identical |

ThinLTO renames each local it promotes across modules to
`<name>.llvm.<hash>` with a hash of its module; the only input that
differed is the module's path (the `.ll` file in the build directory,
which bootstrap-xo.sh gives each stage its own of), so the hash follows
the path (inferred from this experiment, not from LLVM's source). On darwin/arm64 (ld64) the same
experiment gave identical binaries for both modes. Run 1 also showed
the ThinLTO link holding 18.8 GB (gotchas/xo1-thinlto-link-memory.md).
So xo1 is built on amd64 hosts without LTO (internal/selfdriver
`xo1Backend`; scripts/bootstrap-xo.sh and xo1-host-check.sh default to
`XO_LLVM_LTO=none`): run 2.

## What it changed

- selfhost/xo: `host_arch()` (from main's switch point B work) names
  the host for the LLVM path, the Go backend's host target, and the TLS
  library's cache key; `--no-gc` without a backend is LLVM on a non
  arm64 host (as cmd/xo's build.NativeBackend).
- internal/selfdriver: x86-64 hosts (darwin/amd64, linux/amd64) run
  `--backend=llvm` and `--no-gc` builds through xo1; `--backend=arm64`
  there stays with the Go driver. xo1 is built there by the LLVM
  backend split into 12 modules without LTO (`xo1Backend`;
  `XO_LLVM_SPLIT` and `XO_LLVM_LTO` override). `XO_SELF_DRIVER=0` still
  runs the Go driver.
- scripts/bootstrap-xo.sh: the backend is `XO_BOOTSTRAP_BACKEND`, by
  default arm64 on arm64 hosts and llvm elsewhere (with
  `XO_LLVM_SPLIT=12`, `XO_LLVM_LTO=none`).
- scripts/selfhost-goldens.py: `XO_GOLD_NO_GO=1` skips the set whose
  reference needs the Go `xo`.

## What scripts/release.sh will need (not changed here)

release.sh builds the linux/amd64 xo1 with `--backend=go
--targets=linux/amd64` (selfhost/gen and the Go toolchain). After the
Go compiler goes (stage 7 step 4), an amd64 xo1 must come from the
LLVM backend, which builds for the host only. Options, most likely
first:

1. Build each amd64 xo1 on its own host from the previous release's
   xo (or the bootstrap chain): `XO_LLVM_SPLIT=12 XO_LLVM_LTO=none xo
   build --backend=llvm -o bin/xo selfhost/xo` on linux/amd64 (EC2,
   as scripts/remote-xo1-x86.sh does; 2,037 s, 16.5 GB machine peak)
   and on darwin/amd64 (the Intel Mac). release.sh would then fetch the
   two binaries instead of building them; this run proves those
   binaries are the fixed point's.
2. Teach xo1's LLVM path to cross compile (`--target=linux/amd64` and
   `darwin/amd64` from darwin/arm64): clang `--target=x86_64-...` for
   the IR and the C runtime, the target's attributes instead of
   `clang -###` of the host, and a linker (Apple clang links
   darwin/amd64 with the SDK; zig cc 0.15.1 with glibc 2.31, as the
   linux/arm64 pack already uses, for linux/amd64). Decision 0197's
   `LLVMCrossTriple` (windows/arm64 from windows/amd64) is the model.
   Next experiment: `xo1 build --backend=llvm` of the arith golden with
   the IR compiled by `clang --target=x86_64-apple-macos11` on the
   development Mac, run on the Intel Mac.
3. The linux/amd64 glibc floor: an xo1 built on Amazon Linux 2023 needs
   its glibc (2.34); a release built on EC2 needs an older sysroot or a
   zig cc link to keep release.sh's glibc 2.31.
