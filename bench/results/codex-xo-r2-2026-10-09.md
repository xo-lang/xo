# Codex Xo arm rerun after habit diagnostics (2026-10-09)

Rerun of only the Xo arm with Codex (harness path 2b) on toolchain
v0.7.0 (`de24fd9`): habit diagnostics (decision 0087) and the std gaps
Codex reported (decision 0088) in place. Raw outputs, per run snapshots,
and Codex's `SUMMARY.md` are in `runs/codex-xo-r2/` (gitignored). First
run: [codex-2026-10-09.md](codex-2026-10-09.md).

Model: configured `gpt-6.1-sol`, reasoning effort `low` (read from the
Codex config). The first run's settings were not recorded, so effort is
a possible confound between the two runs.

## Why the six first runs failed

| Task | Cause | Diagnostic did its job? |
|---|---|---|
| 01 | Several match arms on one line: XO0175, and parser recovery lost the arms, giving a false XO0301 (missing arms) with a misleading hole fix | Partly; no machine fix, cascade |
| 02, 04 | `}` newline `else`: XO0162 | Yes, with a machine fix, but the loop does not apply fixes |
| 06 | XO0162, and XO0402 inferring the result of a closure that loops forever | XO0402 note was enough, no fix |
| 03 | `http.ClientErr.display()` rejected with XO0601 although the spec says std errors implement Display | No: a toolchain bug |
| 08 | The test assumed an env var to read sources for an architecture (import direction) test; no Xo way to check imports from a test | No diagnostic; a missing feature |

With `xo fix` applied before each check, 02 and 04 would also pass
(6/10). Fixing XO0175's machine fix and the XO0601 bug would add 01 and
03 (8/10).

## Scoring incident

The first scoring attempt failed 03 and 04 with missing Go cache files.
Cause: while it ran, the cache trim was being fixed in this repo and a
manual trim with the new lock based binary removed 88 GB, including
entries Codex's v0.7.0 binary (which takes no lock) was using
(gotchas/go-cache-trim-races-builds.md). The second attempt, with its own
cache, was 10/10 green. Not a Codex or language failure.
