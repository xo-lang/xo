# LLVM backend on darwin/amd64 (Intel Mac), 2026-10-12

Decision 0196 gate: the LLVM backend must build darwin/amd64 programs
that pass the golden suite before the Go compiler is deleted.

## Host

The owner's Intel Mac: x86_64 i7-9750H (12 threads), 16 GB, macOS
26.5.2, Command Line Tools with Apple clang 17.0.0 (clang-1700.3.19.1),
Go 1.26.1 darwin/amd64 unpacked in ~/xo-ci/go. Runs through
`scripts/intel-mac-test.sh` (GOMAXPROCS=6, `XO_SELF_DRIVER=0`, HOME and
the Go caches inside ~/xo-ci/state).

## Where to build

Natively on the Intel Mac, with the Go driver. Not a cross build from the
Apple silicon development Mac, because:

- the LLVM backend builds for the host only (`buildLLVM` rejects other
  `--targets`), and the golden tests must run the binaries, which the
  development Mac cannot (no Rosetta: "bad CPU type in executable");
- the development Mac's default SDK (MacOSX27.0.sdk) does list
  `x86_64-macos` in libSystem.tbd, but its linker rejects the file
  ("tapi error: malformed file ... unknown architecture" at the
  `arm64e.x1-macos` entry); `-isysroot .../MacOSX26.5.sdk` links an
  x86_64 hello there. So a cross link is possible, a cross test is not.
- xo1 (the self hosted driver) is arm64 only; on darwin/amd64 `xo`
  already falls back to the Go driver (internal/selfdriver: the switch
  applies to darwin/arm64 and linux/arm64 hosts), so `xo build
  --backend=llvm` works there with XO_SELF_DRIVER unset (checked: a
  Mach-O 64-bit executable x86_64).

## What darwin/amd64 needed

No emitter or runtime change. The emitted IR carries no target triple or
data layout (clang supplies the host's), `ClangTargetAttrs` reads the
host CPU from `clang -###`, and the C runtime (std/llrt) already had the
x86-64 fiber switch (System V registers, MXCSR and x87 control word)
with Mach-O symbol naming (`XO_ASM_FN` adds the underscore and
`.private_extern` under `__APPLE__`), Darwin's `__ulock` futexes,
kqueue, and `pause` in spin loops. selfhost/llvm has no target handling
to mirror.

The one fix was in the tests: AddressSanitizer and ThreadSanitizer
binaries die with SIGILL before `main` with that clang on that macOS
(gotchas/darwin-amd64-sanitizers-sigill.md), which failed the five ASan
built drivers (TestCryptoDiff, TestJSONParseDiff, TestHTTPParseDiff,
TestHTTPFuzz, FuzzHTTPDiff) at commit ea78d31. `asanFlags` now drops ASan
where it cannot start, as `tsanBuild` already did for TSan.
