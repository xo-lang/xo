# Ed25519 and crypto.equal in constant time Xo (zero-C audit B09)

Date: 2026-10-14. Machine: the Mac (Apple M-series, darwin/arm64), ten
agents running, so counts, not times. Decision 0222.

## What moved

- `crypto.equal` (and verify_password's comparison):
  std/native/llrt/ct.xo `bytes_equal`, words through rt.bytes_word, the
  accumulator through `rt.ct_barrier` every iteration.
- Ed25519 (`crypto.ed25519_public_key`, `ed25519_sign`,
  `ed25519_verify`): std/native/llrt/ed25519.xo. xo_crypto.c goes from
  540 lines (main ed7a7dc8) to 16 (the seed's `xo_ct_barrier`);
  std/native/llrt/cabi_crypto.xo (the SHA-512 export the C called) is
  deleted.

## Method

A program loops one std/crypto operation N times (N = 200; equal
20,000 times on two equal 1,024 byte strings), built with this
checkout's xo for each backend twice: with this branch's std (Xo) and
with the std of main ed7a7dc8 (the C). Instructions retired from
`/usr/bin/time -l`, the run with N = 0 subtracted, divided by N. The
message is 64 bytes.

## How it got there (public_key, Xo / C)

| step | arm64 | LLVM |
|---|---|---|
| straight port of the C (List[Int] workspace with bounds checks, each product as mul, umulh, split at bit 51) | 3.476 | 2.613 |
| workspace through raw memory (decision 0207), carries inlined | 1.842 | 1.144 |
| products as (f << 13) * g: the high word is p >> 51, the low word >> 13 is p mod 2^51 (5 instructions a product, no spills on arm64) | 1.616 | 1.100 |
| squaring with the 15 distinct products, dedicated doubling (dbl-2008-hwcd, 4S + 4M) | 1.321 | 0.978 |
| fixed 4 bit window (64 additions of a masked table lookup instead of 256 additions) | 1.012 | 0.829 |
| scalar reduction in four words with inline borrows, unrolled conditional move | 0.940 | 0.756 |
| SHA-512's input and block buffer by object address, no C call (the final code above) | 0.944 | 0.757 |

The C used the generic addition for doubling and a bit by bit double
and always add ladder; the Xo code does the same field arithmetic with
fewer group operations, so the comparison is of the whole operation,
not of fe_mul alone.

## Constant time checks

- test/codegen/consttime (`xo dev codegen`: the 52 patterns of the
  three test/codegen programs on both backends pass): no conditional
  branch, csel, or cset in the self-hosted arm64 code of ct.mask_nonzero, ct.pick, and
  ed25519.ge_cmov; no csel or cset in ed25519.ge_mul and sc_reduce; the
  LLVM IR keeps the barrier asm.
- internal/llvm TestConstantTimeLLVM: after clang -O2 (Apple clang 21,
  arm64) the barriers survive, ge_cmov has no branch and no select,
  sc_reduce and ge_mul no select. The control (each barrier replaced by
  an add of 0) gives sc_reduce 4 csel: without the barrier LLVM turns
  its masks back into selects.

## Next steps

  then a store and a reload before each multiply) in the first fe_mul,
  which had 28 live values; it has no `madd`, `extr`, or fused shift of
  a multiply's result. Each would shorten fe_mul (185 instructions in
  the arm64 emitter's code, 125 of them the 25 products).
