# The native CPU profile: tests, overhead, first use (2026-10-16, xo-4)

Decision 0238's CPU profile (XO_PROF=cpu, `xo run --profile=cpu`,
`xo test --profile=cpu`), darwin and linux, arm64 and LLVM.

## Correctness

- internal/llvm TestProfCPU: a recursive fib (no backend inlines it)
  is the top function by flat samples, and `go tool pprof -top` reads
  the file, on the LLVM and arm64 backends (Mac); the same program on
  linux/arm64 in Docker: fib 100% flat, the stack fib, main,
  cabi.run_main, entry.run_main, xo_entry on both backends.
- The six bench/perf/conc workloads at XO_PROF_HZ=1000, three runs
  each on both backends (spawn, fanout, pingpong, mutex, rwmutex, pmap:
  tasks on several threads, fiber switches, futex waits): no crash, no
  hang, every profile written.

## Overhead with profiling off

What runs: start reads XO_PROF (and returns), main's end and
os.proc.exit find nothing armed. No timer, no handler, no memory.

- Linux (callgrind, hello, arm64): 148,776 instructions without the
  profiler, 149,018 with it: +242 (the environment lookup 194, start and
  finish 41).
- macOS (instructions retired, hello, 21 interleaved runs): medians
  13.922M against 14.149M (arm64, 1.016x), 13.432M against 13.706M
  (LLVM, 1.020x). The runtime is 53 KB (arm64) to 66 KB (LLVM) larger
  (hello 468 KB to 521 KB, 118 KB to 184 KB) and the process touches 4
  more pages at start; on Linux the same code costs 242 instructions,
  so on macOS this is loading the larger binary (dyld and the kernel),
  not running it. A long program (a recursive fib(38)):
  1,215.9M against 1,216.5M (arm64, 1.0005x), 1,404.9M against
  1,405.4M (LLVM, 1.0004x), within run to run noise.

## First use: bench/perf/conc rwmutex on the Mac

The largest gap of bench/results/rust-baseline-2026-10-16.md, at
XO_PROF_HZ=1000 (arm64):

xo cpu profile: 190 samples (190ms) in 105ms of wall time at 1000 Hz

top 30 by flat
      flat  flat%   sum%        cum   cum%
     120ms 63.16% 63.16%      120ms 63.16%  _ulock_wait
      66ms 34.74% 97.89%       66ms 34.74%  _ulock_wake
       2ms  1.05% 98.95%        2ms  1.05%  pool.steal_round
       1ms  0.53% 99.47%        1ms  0.53%  libcmem.malloc
       1ms  0.53% 100.00%        8ms  4.21%  mutex.rlock

98% of the CPU time is in the kernel's __ulock_wait and __ulock_wake
(the futex of macOS), entered from pool.futex_wait and park_signal:
every contended lock parks its task's thread and every release wakes
one. The locking code itself (mutex.rlock, mutex.lock) is under 5%.
This is the park and wake pass the lead queued next (spin before
parking, hand off without a wake).
