# The Fs operations in Xo on Linux and darwin/arm64 (work item B16, part 1)

Date: 2026-10-14. Work item B16 of
`bench/results/zero-c-audit-refresh-2026-10-13.md` (the POSIX half;
decision 0180's bar: within 5 percent of the C path's instructions on
arm64 and LLVM).

## What moved

- std/native/llrt/fsops.xo (new): directory names, rename, remove,
  set_modified, the system calls under fspath.xo (mkdir, rmdir, unlink,
  the kind of a path, names, the O_EXCL create, getcwd, the status of an
  errno), file handles (open, the 64 KiB buffered read, read_line with
  an eight bytes a step newline search, write, close), copy, mode and
  set_mode, symlink, read_link, and flock locks (exclusive and shared)
  with the polled wait: every 10 ms `rt.clock_sleep_or_cancel` (the C
  runtime's xo_clock_sleep_or_cancel, now declared in rt.xo, so the wait
  is a cancellation point as before and the test world records it) after
  `rt.flush` (xo_flush, as the C's flush_pending). Semantics and
  messages are xo_fs.c's (Go's os package).
- The calls: linux.xo (renameat, unlinkat, mkdirat, utimensat,
  fchmodat, symlinkat, readlinkat, getcwd, flock, getdents64, reads and
  writes at an address) and darwin.xo over new sys_darwin.xo
  declarations (rename, unlink, rmdir, mkdir, chmod, symlink, readlink,
  utimensat, getcwd, flock, opendir, readdir, closedir).
- prelude.xo, internal.xo (std/internal's lock_shared), and fspath.xo
  call fsops.xo instead of `rt.fs_*`.
- Where the C stays: Windows (its kernel32 layer for these calls is
  part 2 of B16, with xo_win.c 542-1029), darwin/amd64 (sysio.layer 0:
  stat, opendir, and readdir there are `$INODE64` symbols that a
  platform declaration cannot name yet,
  gotchas/darwin-amd64-stat-inode64.md), and wasm (its own runtime).
  Because the arm64 emitter lowers every `target` arm
  (gotchas/arm64-match-target-not-folded.md), Linux and macOS builds
  still link xo_fs.c, so no C line is deleted in this part: xo_fs.c
  grows by 23 lines (the int64 record fields fsops.xo reads, and the
  constructors xo_fs_raw_file and xo_fs_raw_lock). It goes with part 2.
- Handles stay C records (xo_fsfile, xo_fslock) made by
  `rt.fs_raw_file` and `rt.fs_raw_lock`: Xo cannot yet make a reference
  counted record whose release runs Xo code, and a dropped handle must
  close its descriptor (and drop its lock). fsops.xo reads and writes
  their words through rt.obj_addr. The status and message of the last
  operation stay the C thread locals (rt.fs_set_err), which the C of
  Windows and darwin/amd64 also writes.
- Seed: no lowering changed (the SSA builders lower no Fs operation
  themselves), so seed 0.10.0-23ce8ce2 builds the branch's xo
  (`XO_SEED=... go run ./scripts/xobuild`, 42 s on the Mac) and no C
  is kept for it.

## Tests

- internal/llvm/testdata/golden/fs_ops_edges (new): lines longer than
  the read buffer and \r\n split by it, reads below and above the
  buffer, read_line then read on one handle, every operation's errors
  (NotDir, NotFound, NotEmpty, IsDir, Exists, Denied, the handle
  states), set_modified before the epoch, links, permission bits, locks,
  and a lock that waits until another task unlocks it. Its output on
  the C path (main 9e3806fc's std) and on fsops.xo is byte identical on
  darwin/arm64 with both native backends (allocations 2,914 C, 3,052
  Xo, all freed, in the program before it became a golden).
- fs_files, fs_cwd_path, fs_native, fs_paths_os, sys_files_clock,
  proc_cmd, native_sql, cancellation, fs_rooting, sql_basic pass on
  darwin/arm64 with arm64 and LLVM.

Every workload is within decision 0180's bar on both backends: the
highest Xo / C is 1.003. read_line is 0.82 (arm64) and 0.68 (LLVM)
times the C path's instructions, probably because the newline search tests eight bytes a
step where the C's memchr is libSystem's, and a line is one string
copied once from the buffer, where the C built it in a growing buffer
and copied it again into the list.
