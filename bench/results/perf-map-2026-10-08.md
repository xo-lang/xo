# Map performance: entry log with claimed ownership (2026-10-08)

Goal: make `Map` (and `Set`, which is a `Map[T, ()]`) fast under update
heavy loops without breaking value semantics (core 5.1, 5.2). Target:
update heavy Map loops within 5x of Go maps, reads and copies not more than
20 percent slower.

Host: darwin/arm64 (M4 Pro), Go 1.26.1. Before: the persistent hash array
mapped trie with an insertion log List (`std/rt/map.go` as of 2026-10-07).
After: `std/rt/map.go` as of this change. Nothing in `spec/`, the checker,
or the code generator changed; the whole change is in the runtime.

## Design

A Map value is a header (table, visible prefix of the table's entry log,
live count). A table is an append only log of entries (hash, key, value,
link to the previous entry of the same key, origin position for insertion
order; tombstones for removals) plus an open addressing index from each key
to its newest entry. A value means "the newest entry of each key below my
log length".

- Write through a header whose log length equals the table's claimed length
  (`used`): claim the next position with a compare and swap and append in
  place (amortized O(1)). This is the claim List already used for `push`.
- Write through any other header (a stale copy): fork, that is, make a child
  table whose parent is the stale header's view. O(1); lookups search the
  child's index, then the parent view. At most 8 fork levels, then the view
  is flattened in O(n).
- Compaction: when a root log holds more garbage (overwritten entries,
  tombstones) than live keys, or a fork's own log outgrows the map, the
  owner flattens it into a fresh table (O(n), amortized against the appends
  that made the garbage).
- Concurrency: index slots, the index pointer, the log array pointer, and
  `used` are atomics, so snapshots can be read on other tasks while the
  owner appends.

Codegen based ownership (transient trie nodes owned by a binding, cleared
when a value is copied out) was rejected: Go copies headers silently
(struct assignment, captures, channel sends, `Mutex.with`, collection
elements), so every copy site would need a hook, and one missed site breaks
value semantics without any failing test.

## Soundness argument

Claim: no operation on one Map value changes the value of another, however
the headers were copied.

1. A header's value depends only on its own log prefix (and, for a fork, on
   the fixed parent view). Entries are never written after they are
   appended.
2. The only writes to a table are: appending at position `used` after
   claiming it, index slot updates, index growth, and log array growth. The
   claimed position is at or past the end of every existing header's view,
   so an append never changes an entry any header sees.
3. The index is not part of any value. A lookup from a view of length L
   takes the entry the index names and follows the prev links (a complete,
   decreasing chain of the key's entries in that table) until it is below
   L, so the result is the newest entry below L whatever the index says now.
4. Copies share a length L. Only one wins the compare and swap from L to
   L+1; the others see `used != L` and fork. So each log position is
   written once, by exactly one value.
5. `Map.update`'s fast path probes once before running the closure and
   writes with that probe only after winning the claim at the same L, so no
   other value can have touched the index in between; it also checks that
   the header is unchanged.

So a header's value is fixed from creation until the header itself is
overwritten. The same argument is in the comment on `Map` in
`std/rt/map.go` and in `knowledgebase/gotchas/map-copy-claims-log.md`.

## Workloads (generated Xo against hand written Go)

`bench/perf/run.sh` (best of 5 runs, milliseconds of the timed part only;
the 50k key map for `get`, `iter`, `copymut`, `branch` is built before the
timer starts). The Go column is from the after run; the before ratios use
the before run's Go time (within 5 percent). Checksums agree between Xo and Go for every workload.

| Workload | Go | Xo before | Xo after | Before ratio | After ratio |
|---|---|---|---|---|---|
| `putget`: 3M `put` over 50k keys, then 3M `get` | 44.9 | 2179.0 | 141.9 | 48.6x | 3.2x |
| `get`: 3M `get` on a 50k map | 17.5 | 82.9 | 47.2 | 4.7x | 2.7x |
| `push`: 3M `List.push`, then a sum | 6.7 | 13.7 | 13.4 | 1.9x | 2.0x |
| `update`: 3M `Map.update` over 50k keys | 25.3 | 2197.7 | 112.2 | 82.6x | 4.4x |
| `iter`: 60 iterations of a 50k map | 17.3 | 70.4 | 9.7 | 4.0x | 0.6x |
| `copymut`: 10 rounds of copy a 50k map, put every key of the copy, read every key of the original | 9.6 | 349.0 | 28.7 | 36.9x | 3.0x |
| `branch`: 2000 one key edits of copies of one 50k map | 201.9 | 220.8 | 0.2 | 1.1x | 0.001x |

Notes:

- Go's `iter` looks each key up in a Go map through an insertion order key
  slice (to match Xo's ordered iteration), so Xo walking its own log is
  faster than that Go version.
- Go's `copymut` and `branch` use `maps.Clone`: Go has no value semantics
  for maps, so a correct Go version pays O(n) per copy. Xo before also paid
  O(n) per branch (the insertion log List copied its backing array on a
  stale push).
- `push` is List and did not change (List already claims its backing
  array the same way).
- Peak RSS for `putget`: 23.9 MB before, 29.9 MB after (Go 8.8 MB). For
  `copymut`: 30.2 MB before, 28.2 MB after.

## Runtime micro benchmarks

`go test ./std/rt -run '^$' -bench 'Map|Set' -benchmem` (ns/op, B/op,
allocs/op):

| Benchmark | Before | After |
|---|---|---|
| MapPutInt (50k keys, update heavy) | 719.7 ns, 1684 B, 8 | 27.6 ns, 82 B, 0 |
| MapPutStr (1k keys) | 216.5 ns, 1047 B, 6 | 28.4 ns, 95 B, 0 |
| MapGetInt | 21.6 ns | 12.7 ns |
| MapUpdate | 738.1 ns, 1692 B, 9 | 33.6 ns, 90 B, 1 |
| MapIter (50k entries) | 981 µs | 88.6 µs |
| MapCopyMutate (copy 50k, 1000 puts, 2 reads) | 693 µs, 1.69 MB | 29.4 µs, 82 KB |
| MapGetStale (read a copy whose sibling overwrote every key) | 21.7 ns | 13.7 ns |
| MapGetFork (read a forked copy, half its keys in the parent) | 22.0 ns | 17.5 ns |
| MapCopy (header copy) | 0.225 ns | 0.225 ns |
| MapBranch (copy 50k, put one new key) | 106 µs, 804 KB | 115 ns, 408 B |
| SetAdd (50k elements, repeated) | 24.4 ns | 14.2 ns |

Reads got faster on every path, including stale copies and forks; copies
cost the same (a 40 byte header now, 48 before). The B/op of `put` is the
amortized log array and index of compaction.

- `std/rt/map_model_test.go`: a random model test (40 seeds; puts,
  removes, `update` with failing closures, copies, dropped writes through
  copies, over a pool of map values, each checked against a Go reference
  for length, every key, and iteration order), heavy rewrite with
  snapshots at every fork depth, hash collisions (every key hashes alike),
  concurrent readers of snapshots while two copies write, Set copies.
  Passes with and without `-race`.
- `internal/gen/testdata/golden/map_value_semantics`: copy then mutate in
  both orders; a map in a struct copied and mutated through the copy (also
  inside a list of structs); a map captured by a closure; maps sent on a
  channel and mutated by sender, receiver, and a spawned task; `update` on
  counts and on nested maps; `Mutex.with` writes from four tasks while
  each reads its own snapshots; insertion order through remove and re-add,
  50 rounds of overwrites (compaction), and 30 branches of one map; Set
  copies. Same output under the old and the new runtime; also in
  `TestGoldenRace` (built with `-race`, no reports).
- `go test ./...`, `go vet ./...`, `gofmt -l internal cmd std`, and
  `.tools/bin/staticcheck ./...` are clean.
- `xo test` on `bench/xo/v0.4`: 01, 02, 04, 05, 07, 08 pass. 03 fails one

  under `--race`.

## Limitations and next steps

1. `Map.update` allocates one word per call (`&v` escapes into the closure
   call). Next experiment: pass a pointer into the claimed, not yet
   published log cell (`&m.es[len].v`) instead of a local, which removes the
   allocation; measure with `go test ./std/rt -run '^$' -bench MapUpdate`.
2. A stale snapshot keeps its whole table alive until the owner flattens.
   If that shows up in services, flatten a fork's parent away early when
   the fork is small (copy the parent view's live keys once).
3. `List[i] = x`, `insert`, and `remove_at` copy the whole list (O(n) per
   write). The entry log technique applies (a write log over the shared
   array with a per value length), at the cost of a version check on each
   List read. Next experiment: add a `List.SetAt` loop workload to
   `bench/perf/xo/main.xo` and prototype an overlay of (index, value) writes
   on `List`.
4. Generated code overhead dominates `get` now (12.7 ns in rt against 15.7
   ns per get in the Xo workload loop): checked `%` and `Option` results.
   Next: profile `bench/perf` `get` with `go tool pprof` on the built binary.
