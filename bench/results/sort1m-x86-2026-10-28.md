# sort1M on x86: placement, the JCC erratum and jump padding (2026-10-28)

The 2026-10-27 file left List[Int].sort at 1.23x Go on the i7-9750H with
the cause parked as "microarchitectural, moves with layout". It is the
JCC erratum: the fused cmp+jcc pairs of pdq_partition's inner loops
straddle a 32 byte boundary or not depending on where the function
lands. Decision 0398 pads them off the boundary in Xo's assembler.
Machine: the owner's Intel laptop (i7-9750H, Coffee Lake, 6 cores,
macOS), Go 1.26 `slices.Sort` as the twin; each sample is one
process's best of 5 sorts of 1M LCG Ints (the tester's micro
benchmark); 7 interleaved rounds per binary; medians.

## The 32 placement sweep, before (xo af342c774)

`XO_ARM64_PAD=K` puts K one byte nops before every function on x86
(after `.p2align 2`), so K=0..31 walks a 32 byte window. The code is
the same in all 32; only addresses move.

| | ms |
|---|---|
| Go | 67 (66 to 69) |
| xo, default placement (pad 0) | 80 |
| xo, best placement (pads 18, 21, 31) | 73 |
| xo, worst placement (pad 27) | 90 |

Per pad, with the offset modulo 32 of pdq_partition's i scan loop
(its j loop is 32 bytes later, the same offset):

| pad | ms | loop offset mod 32 |
|---|---|---|

Offsets 10 to 13 and 19 to 21, where no fused cmp+jcc of either loop
crosses or ends on a 32 byte boundary, are the 73 to 80 group; 2 to 5
and 26 to 29, where the bounds check's cmp+jae or the exit's test+je
straddles one, are 81 to 90. Pads with the same offset agree within 1
to 3 ms (the rest is the other functions' placement).

Moving only pdq_partition (a throwaway `XO_ARM64_PAD_FN` pad on that
function and what follows it, the functions before it fixed): 73 to 88
ms with the same ordering (offsets 19, 10, 20 at 73 to 76; 25 to 28 at
87 to 88).

## Code size

xo itself (compiler/xo) cross built for darwin/amd64 by main's xo
(af342c774) and by the padded one, `size -m`:

| | __text bytes | file bytes |
|---|---|---|
| unpadded | 106,296,832 | 157,450,935 |
| padded | 109,215,304 | 160,356,935 |
| growth | +2,918,472 (+2.75%) | +2,906,000 (+1.85%) |

More than Go's reported fraction of a percent: Xo's code has a bounds
check (a fused cmp+jae) at most list reads. Padding only loops (a jcc
whose target is already defined is a back edge; the jumps between its
target and itself are the loop's) would keep the gain for less, a follow
up noted in decision 0398.

## What the 2026-10-27 file got wrong

Its "Skylake jump erratum" row assembled with clang's
`-mbranches-within-32B-boundaries`; the binary (kept on the laptop,
read back 2026-10-28) was not padded: its hot loop's `cmpq`/`jge`
straddled 0x...55f/0x...560. xo's native amd64 path never runs clang's
assembler (gotchas/amd64-clang-flags-do-nothing.md), so that row
measured the same bytes twice. The file carries a dated note.
