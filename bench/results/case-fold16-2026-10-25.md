# ASCII case folding through a 16 byte lane, 2026-10-25

Follow-up to `case-swar-2026-10-25.md`, the negative result that measured
a std-side unroll of the same words and kept nothing. Decision 0373 takes
the lever that result named: an intrinsic that folds a 16 byte ASCII lane
in one operation, lowered to NEON on arm64, SSE2 on x86_64, a `<16 x i8>`
sequence on LLVM and a byte loop on wasm.

The row this starts from, on main (eec0768d3): arm64 is 1.755 times LLVM's
instructions on `lower` and 1.696 on `upper`, the two largest gaps in
bench/perf/unicode, while the mixed rows are ahead of LLVM (lower_u 0.824,
upper_u 0.849, eqlower 0.843). The fold is 61 percent of `lower`'s 3.05
instructions a byte: 15 instructions per 8 byte SWAR word in the emitted
code, 1.875 a byte.

## What changed

- `rt.case_fold16(dst, src, i, mode)` (std/native/rt.xo): the 16 bytes at
  src from i folded into dst from i, mode 1 lowering and mode 2 raising.
  Every byte outside the case, and every byte at 0x80 or above, is copied
  unchanged; one property carries that (ADR 0373): `(c - first) mod 256`
  is 0 to 25 exactly for the case's letters.
- arm64, nine instructions a lane: one constant held in a register, one
  unsigned compare of the bytes shifted down by the case's first letter,
  and 0x20 a byte built from the all ones mask with `ushr #7` and
  `shl #5`. A64 has no byte wide add, sub, and, orr or bic with an
  immediate (each rejected by clang -arch arm64 and recorded in
  knowledgebase/gotchas/arm64-no-byte-immediates.md), so the lane is
  register operations and shifts throughout.
- x86_64: the same fold in SSE2, constants broadcast from a general
  register.
- LLVM: a `<16 x i8>` lane (load, sub, icmp ule, select, add or sub,
  store). It was written as the SWAR words first; see "What did not
  work".
- wasm: a byte loop over the lane.
- std's `fold_copy_lo`/`fold_copy_up` (std/native/llrt/obj.xo) fold four
  lanes a step before the eight byte and byte loops that stay for the
  tail, and those loops sit behind one `>= 8` test, so a short run pays
  one test as it did before.

## The bar, and what was accepted

The bar for landing was "neither backend regresses": the ASCII rows were
1.755 of LLVM's instructions on arm64 and are now 0.644 of main's, below
main on LLVM too. Two mixed rows remain 0.5 to 0.6 percent above main in
instructions (LLVM eqlower 1.005, lower_u 1.006) with every wall within
noise, and arm64 lower_u 1.000 (+0.005 percent, which the tool prints as
"worse" on the fourth decimal). The lead relaxed that bar for this change
on purpose, with this file as the record: the target rows' gain is worth
a half percent of instructions on two rows nothing in this change targets,
and the alternative was another intrinsic that the measurement below shows
cannot reach them.

## What did not work

- **The LLVM expansion as the same SWAR words.** With step 2's loop
  around it, clang stopped widening the words itself and every LLVM row
  regressed (lower 1.017, upper 1.017, lower_az 1.010, upper_az 1.010,
  eqlower 1.011, lower_u 1.013, upper_u 1.011). Clang's own code for
  main's loop is four lanes unrolled with the constants hoisted; a 16
  byte block is already wide enough that it does not unroll, so each
  block paid its three `movi`s. The lane is a `<16 x i8>` sequence now.
- **Sixteen bytes a step without unrolling.** That fixed the wall and
  left the ASCII rows above main in instructions (lower 1.052, lower_az
  1.033): per block, an address computation for src and one for dst, and
  clang's hoisting lost.
- **Three loop tests a run.** With the lane loop, the word loop and the
  byte loop each testing, mixed text (one and two byte runs between its
  non-ASCII runes) paid two extra tests a run and regressed to 1.014
  (LLVM lower_u, eqlower). The `>= 8` guard, which leaves a short run
  paying the one test it paid before, is what brought those to 1.006.
- **A 64 byte intrinsic** was considered to remove the last 0.5 percent
  and dropped on measurement grounds: a 64 byte chunk never forms in
  mixed text, so it cannot reach the rows that regressed, and the ASCII
  rows would gain only the constants and addressing per 64 bytes.

## What is left

- The fold is memory bound: 0.644 of main's instructions on `lower` is
  0.884 of its wall, and 0366 measured the same shape from the other
  side (2.4 times fewer instructions on a hand written two lane loop,
  1.71 times the wall).
- The mixed rows' remaining 0.5 percent needs a profile of a mixed
  workload (where a run's setup and its 16 to 63 byte tail go), not
  another intrinsic.
- wasm's fold is a byte loop: correct, slower than a lane, and wasm is
  not a backend these rows are measured on.
