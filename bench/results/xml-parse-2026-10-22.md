# xml.parse: plain runs as slices, 2026-10-22

Native Xo (`--backend=arm64`), before and after, and a Go twin (go1.26.1
`xml.Decoder.Token` loop, tokens counted), on the development Mac (Apple M4
Pro). A 20,000 item document (about 1.7 MB: two attributes, two child
elements with text), parsed 8 times. The Xo side also builds the Element
tree; the Go twin only reads tokens.

`xo bench --ab` (9 rounds, interleaved, load 24 to 25 from other sessions):

| metric | before | after | after / before | 95% interval |
|---|---|---|---|---|
| wall_ms | 574.2 | 257.7 | 0.449 | 0.438 to 0.490 |
| cpu_ms | 550.0 | 250.0 | 0.455 | 0.436 to 0.481 |
| instructions | 8,003.9 M | 3,768.2 M | 0.471 | 0.470 to 0.472 |
| max_rss_kb | 51,664 | 41,312 | 0.800 | 0.799 to 0.800 |

Against Go (instructions retired, three runs, the document build removed
from the Go side only as its cost is small): Go 3,760 M, Xo before 8,005 M
(2.1x), Xo after 3,768 M (1.00x).

Changes (std/native/xml.xo): `space` is one loop over the bytes; `name`
returns an ASCII name that a byte below 128 ends as a slice of the text, with
no table search for the usual first byte; `text` returns plain ASCII
character data (printable ASCII, tab, newline) up to `<` or the closing
quote as a slice. Anything else (an entity, `]`, `\r`, a byte over 126, the
end of the text, CDATA) takes the byte by byte path of Go's decoder from the
same position, unchanged. Results are the same (xml corpus and goldens).

Strings in the tree are views of the document text (decision 0330): a
caller that keeps one string of a large document calls `clone()`.
