# Standard output, exit, env, and args in Xo (work item B03)

Date: 2026-10-14. Work item B03 of
`bench/results/zero-c-audit-refresh-2026-10-13.md` (decision 0195),
stage 1 of 3 (stdio; then exit; then env and args). Decision 0180's
bar: no measurable slowdown against the C path, instructions retired on
both native backends.

## What moved

- std/native/llrt/stdio.xo: standard output's 64 KiB buffer, its flush,
  the large text written at once, standard error (unbuffered, after a
  flush), and the test world's fake streams (asked of the C runtime
  once). The state is four process globals (rt.static_word words 3 to
  6: the buffer's address, its length, its lock, the mode). The lock
  (pool.xo's lock word) is taken only once the runtime runs several
  threads: xo_rt_threads_begin calls cabi.xo's `stdio_threads`, as the
  C tested `xo_threaded`. The common case of a print (one thread, room
  in the buffer) is a copy and a store, with the newline of println
  stored directly.
- The SSA builder calls the native prelude's llrt_print, llrt_println,
  llrt_eprint, and llrt_eprintln for Stdio.print and friends (also
  FakeStdio's in tests) and for its own messages (an error main
  returned, a fault's trace), in place of the C runtime's xo_print and
  rt.eprintln; a WASI module keeps its runtime's. std/log writes through
  stdio.xo too.
- cabi.xo exports `print`, `println`, `eprint`, `eprintln`, `flush`,
  `flush_try`, and `stdio_threads`. The C runtime's xo_flush and
  flush_pending (fault exit, deadlock, signals, waits) call `flush`;
  Windows' stack overflow handler calls `flush_try` (it must not wait).
- New layer helpers: linux.xo and darwin.xo `write_at` (an address, not
  a Bytes), windows.xo `std_write_at` (GetStdHandle and WriteFile, new
  in sys_windows.xo; best effort, not run on Windows).
- Deleted C: xo_rt.c's Output section (obuf, olen, out_mu, out_lock,
  out_dirty, flush_locked, print_locked, and the four print bodies: 121
  lines, 39 left: write_all, which other C still calls, the export
  declarations, xo_flush and flush_pending as one line calls, and four
  one line seed shims) and the Windows handler's direct buffer write.
  xo_print, xo_println, xo_eprint, and xo_eprintln stay as one line
  forwards to the exports until the seed has B03: the 0.10.0 seed still
  lowers Stdio.print to them (gotchas/runtime-c-the-seed-still-calls.md).

output and error to /dev/null. `c` is the same program built by the
same xo (this branch's) against the std of 40473c0b (its prelude has no
llrt_print, so the compiler calls the C runtime's xo_print); `xo`

The bar is met: every stdout heavy workload is at or below the C path's
count (0.788 to 1.005; big's 1.005 on arm64 is 344,115 instructions over
5,000 prints, the flush calls). err and mixed are system call bound.

The first version (a CAS lock on every print, `LEN * 8` offsets, checked
sums, the newline as a second copy) was 1.36 times the C on arm64 lines
and 1.10 on LLVM: the arm64 emitter does not fold a product of two
constants in a runtime module (`mov`, `mov`, `mul` per offset) and
checks every `+` (gotchas/arm64-runtime-const-products-and-checked-sums.md).

## Stages 2 and 3: exit, env, args

- std/native/llrt/process.xo: `exit` (os.proc.exit, and the end of a
  program whose main returned an error): standard output flushed, then
  exit_group on Linux, libSystem's exit on macOS, ExitProcess on
  Windows (new in sys_darwin.xo and sys_windows.xo); in a test binary
  the test world's tw_exit (rt.tw_exit), which returns inside
  testing.run_main. `args`, `program`, `env_get`, and `env_vars` read
  argc, argv, and the environment's NAME=VALUE array from three process
  globals (rt.static_word words 7 to 9) that C main hands over through
  cabi.xo's `proc_start` (`environ`; on Windows the C runtime's UTF-8
  copy, xo_win.c xo_w_environ, which the C's own getenv still needs);
  names compare without ASCII case on Windows; env.vars sorts as
  before. A test world that fakes env answers through rt.tw_env_get,
  tw_env_vars, and tw_env_args (one line C wrappers of the test world's
  FakeEnv).
- The SSA builder calls the native prelude's llrt_exit, llrt_env_args,
  and llrt_env_program for Proc.exit, its own error exits, Env.args,
  and Env.program, and redirects the runtime calls rt.env_get,
  rt.env_vars, and rt.eprintln (the native prelude's and std/log's) to
  llrt_env_get, llrt_env_vars, and llrt_eprintln; a WASI module keeps
  its runtime's.
- C: xo_exit is a one line seed forward to cabi.xo's `exit` (9 lines
  to 1). xo_env_get, xo_env_vars (xo_rt.c) and xo_env_args,
  xo_env_program (xo_bytes.c) stay whole, labeled seed compatibility:
  the 0.10.0 seed lowers Env.args and the prelude's rt.env_get to them,
  and the compiler it builds reads its environment through them. They
  go with the first seed that has B03 (about 70 lines with the stage 1
  forwards), after which programs reference none of them.
- Checked on the Mac: a program printing env.args, env.program,
  env.get (set, set with `=` in the value, empty, unset), env.vars, and
  ending with os.proc.exit(3) after a print gives the same output and
  status 3 built by the seed (the C path) and by this branch's xo on
  arm64 and LLVM, and its binaries call no xo_env_* or xo_exit.

The entry itself (C main, `_start` of XO_NOLIBC builds) is work item
B26; with it process.xo will take argc, argv, and envp from the entry
stack (Linux) and `_NSGetEnviron` is not needed (macOS passes envp to
main).
