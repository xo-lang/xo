# Park and wake: deferred wakes, their monitor, no idle spinning (2026-10-16, xo-4)

Decision 0077's addendum, found with the CPU profile (decision 0238;
bench/results/prof-cpu-2026-10-16.md): rwmutex was 98% __ulock_wait and
__ulock_wake (idle workers going to sleep 70%, the Mutex's internal
lock word 29%; wakep 42% of the wakes), spawn at one worker 34% (wakep
per spawn, the root's wait at the scope's close), pingpong a futex wake
per hand off.

## Experiments (Mac, arm64, std only, 9 interleaved rounds)

| Variant | Result |
|---|---|
| lock_slow spins 1000 instead of 100 | no change beyond noise; dropped |
| worker spin rounds 0 instead of 16 | rwmutex 0.85x wall, 0.79x CPU (786M to 617M instructions); mutex at one worker 0.57x CPU; others within noise |
| no wake for a hand off into the next slot, unbounded | pingpong 0.77x wall, 0.45x CPU, but no bound when the waker keeps computing (no preemption): not shipped as is |
| the same with a monitor (sysmon-lite) bounding it | pingpong 0.79x wall, 0.47x CPU; the rest within noise |

## The guarded version (owner's real-time rule, 2026-10-16); the Mutex part rejected

The Mutex deferral as shipped: defer_check on the waker's next runtime
call (50 us, the clock every 16th call, a static fast path when no
monitor runs), XO_DEFER_WAKE=0, and no deferral in a program with a
`uses realtime` function. Against main 2fb2f008 (9 interleaved rounds):

| Workload | Main wall / CPU / M instr | Now | Ratio wall, CPU |
|---|---|---|---|
| rwmutex | 95.5 / 164.0 / 530 | 39.1 / 37.2 / 381 | 0.41, 0.23 |
| mutex | 12.7 / 16.0 / 123 | 12.1 / 13.5 / 136 | 0.95, 0.84 |
| mutex, 1 worker | 10.4 / 9.2 / 104 | 10.6 / 9.7 / 112 | 1.02, 1.05 |
| pingpong | 28.2 / 26.2 / 272 | 29.2 / 27.0 / 289 | 1.04, 1.03 |
| spawn, fanout | | | 0.86 to 1.06 (noise) |

Reading the clock on every check cost pingpong 12% and mutex 37% more
instructions; every 16th check and the static fast path brought that to
6% and 8%. Loaded hand off delays (mutexbusy, handoff) and HTTP:
decision 0077's latency model table.

Decision (lead, 2026-10-16): the Mutex's deferral is not shipped. A
waiter behind a holder that unlocks and keeps working would wait about
1.3 ms (7 ms loaded) instead of 15 us; Xo is for backends. What ships:
defer_check, XO_DEFER_WAKE=0, and no deferral in real-time programs;
rwmutex stays at main's speed until its reader path stops taking the
internal Mutex word.

## rwmutex: a known gap (lead, 2026-10-16)

Without deferring a Mutex's grant, rwmutex stays about 7.5x Go's wall
time. XO_RTSTATS over one run (256K accesses): fiber_park 235K (92% of
accesses wait: writer preference), lock_slow 12K (the internal Mutex
word, 4% of the CPU profile), worker wakes 20K and idle sleeps 19.6K
(the futex calls, 97% of the profile). A bounded spin (4 rounds) for a
worker wakep woke halved the wakes (10K) and changed nothing (rwmutex
1.02x wall, 1.08x CPU; idle server CPU unchanged): the cost is the
migration of granted readers to other workers, which the rejected
deferral avoided (0.40x). Decision 0077's addendum has the analysis.
