# Reference counts shared between threads: cost and tests (2026-10-08)

Decision 0058. Host: Apple M4 Pro (darwin/arm64), macOS 27, Apple clang
from Xcode 26.5 with the MacOSX26.5 SDK. Other agents were building and
testing on the same machine: load averages 10 to 60 during these runs
(`uptime` before and after each). "Before" is commit 0daa33d (plain
counts), "after" is the branch head with this change; both binaries of a
pair were built by the respective `xo` from the same sources
(`bench/perf/llvm/xo/*`) and run interleaved.

### How the first version regressed, and the fixes

The first working version cost strings 12% (wall) on both backends,
4.5 to 6.5% in cycles. Relinking the same generated code with runtime
variants found, in order (`gotchas/native-rc-fast-path-costs.md`):

| Runtime variant, same generated code (strings, arm64) | Mcycles |
|---|---|
| first thread safe runtime | 167.6 (median of 11, load about 50) |
| threaded allocator paths as tail calls (leaf fast paths) | 161.5 (same run) |
| one counter per allocator call, `solo_heap` pointer | 133.8 (min of 21) |
| literal case of `rs_append` tested first (no `.cold` call) | 132.4 (min of 21) |
| plain count runtime, for reference | 130.1 to 132.0 (min of 21, three runs) |

and in the generated code, `ssa.CancelledRelease` in the LLVM backend
(LLVM had folded `retain w` against the release of `Some(w)` itself;
with the branchy shared paths it did not), which took strings LLVM from
+2.7% to +0.1%.

## Correctness

- Share probes (`build.Options.ShareProbes`: every heap value marked
  shared as it is defined): all 37 golden programs give their want.txt
  with no allocation live at exit on LLVM (TestGoldenShared) and arm64
  (TestGoldenRunShared); the Linux assembly with probes (LL/SC loops)
  assembles as ELF.
- Mutation checks of the probes: making the shared release never report
  the last reference leaks in 27 goldens on each backend; making the
  arm64 shared retain add nothing fails 11 goldens (wrong output or
  crash).
- `std/llrt/testdata/rc_threads.c` (8 threads: a shared string retained
  and released, a shared `List[Str]` copied on write by every thread, the
  claim race where the last holder updates in place, appends to a shared
  string, a 10000 box chain marked shared and dropped from both ends,
  a producer and three consumers freeing on their own heaps, immortal
  literals): ThreadSanitizer clean (`-O1 -g -fsanitize=thread`, three
  runs), and clean at `-O2 -DITER=20000` (690438 allocations, 0 live).
  Replacing the shared retain with a plain store makes TSan report 31
  races and the optimized run fail a check and crash.
- Whole programs on four threads at once (`-DXO_RT_TEST_THREADS=4`,
  LLVM IR with probes): the 27 goldens that exit 0 are TSan clean with
  every allocation freed; `recursion` and `rc_closures` run without TSan
  (TSan itself crashes on their depth, `gotchas/tsan-deep-recursion.md`).
- TSan found one real problem in the test setup and one false positive:
  the test read a count plainly where generated code reads it, and the
  release-plus-fence form of the last release
  (`gotchas/tsan-ignores-fences.md`); the release is now one acq_rel
  read-modify-write.

## Not done here

No Xo construct starts a thread on the native backends: `scope`,
`spawn`, channels, `Mutex`, and `Atomic` do not lower to SSA, so nothing
emits `OpShare` outside the probes, and no Xo program shares a value
between threads natively yet. Next, in order: lower `scope`/`spawn` with
captures to SSA (spawn captures get `OpShare`), a thread or work
stealing task runtime in std/llrt that calls `xo_rt_threads_begin`,
channels as a locked queue that marks sent values, then `Mutex`/`Atomic`
handles, then the network effects the HTTP server needs.
