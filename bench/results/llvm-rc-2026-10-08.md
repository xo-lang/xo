# LLVM backend: SSA lowering with reference counting and reuse (2026-10-08)

Question (decision 0040, `llvm-prototype-2026-10-08.md` next step 1):
can the LLVM backend free memory with reference counting and Perceus
style reuse, without losing the prototype's speed, and does that close
the memory gap to Go?

Answer: yes on these workloads. Every allocation is freed by exit
(leak check: 0 live), peak RSS fell to Go's level or below (sieve 136 to
54 MB against Go's 49; sort 150 to 78 against 78; a new string workload
10.4 GB to 16 MB against 28), and times are equal to or better than the
prototype's: against hand written Go the LLVM backend is 0.40x to 1.15x
(faster on sieve, sort, interp, strings; even on fib and collatz; 15
percent slower on nbody, as before).

Host: darwin/arm64 (Apple M4 Pro), Go 1.26.1, Apple clang 21.0.0
(`clang -O2 -flto`).

## What was built

| Part | Path |
|---|---|
| RC insertion, borrow inference, cancellation, uniqueness, reuse | `internal/ssa/rc.go` (`Module.InsertRC`) |
| RC verifier (balance per path, uniqueness of updates) | `internal/ssa/verify_rc.go` (in `Module.Verify` when `Module.RC`) |
| LLVM lowering from SSA | `internal/llvm/fromssa.go` (`GenerateSSA`); `Generate` tries it first |
| Runtime | `std/llrt/xo_rt.c`: size class allocator, RC strings and lists |
| Goldens | `internal/ssa/testdata/golden/*/want.rc.ssa`, `testdata/bench/*.rc.ssa` |
| Tests | `TestVerifyRCMutations`, `TestVerifyRejects` (RC cases), `internal/llvm` `TestGolden` (paths, leak check), `TestLeakCheck` |
| New workload | `bench/perf/llvm/xo/strings`, `llperf strings` |

The rules are decision 0046. In short: ownership is tracked per heap
leaf (Str, List, enum with heap payload) through structs and tuples,
which are values; a field read is an alias, so moving a list out of a
`var` call's result tuple or a struct being rebuilt costs nothing; a
backward liveness pass inserts `retain` before non final consuming
uses, `release` after final borrowing uses and on edges where a value
dies; parameters no path consumes are borrowed (fixpoint over the call
graph); `retain x ... release x` pairs with nothing in between that
could free x are removed; list updates write in place when the list is
provably unique (fresh, never retained, through block parameters) and
otherwise get a run time `reuse` (count check, copy only when shared);
`str.concat` appends in place when its left operand is unique.

### Port of internal/llvm to SSA

`llvm.Generate` builds SSA (`ssa.BuildOpts` with the line root, so fault
positions match), verifies, runs `InsertRC`, verifies again (with RC
balance), and lowers with `GenerateSSA`: every SSA value is an LLVM value,
block parameters are phis, constants are inline operands, enums go
through a stack slot for payloads (SROA removes it). If any step fails,
the whole program falls back to the AST path (`Program.Path`,
`Program.Fallback`, `build.Result.LLVMPath`; `xo build` prints a note).
A per function fallback was not done: functions on the two paths would
disagree on memory layout and ownership (the AST path's lists have a
shared flag and no count).

Which programs take which path (internal/llvm goldens, 29 programs):

- SSA (16): abs_fault, arith, div_zero, float_int_fault, index_oob,
  loops, neg_overflow, overflow_add, overflow_mul, rc_aliasing,
  rc_values, shl_overflow, sort_structs, strings, user_fault, var_alias
  (the test requires these); also the seven bench programs.
- AST fallback (13), with the first missing SSA feature: closure_try and
  closures (closures), enums, recursion, structs (`==` on structs or
  enums), generics and misc (generic functions), interp (`List.last`),
  lists (`List.indexed`), option (the selector `.name`), result (failing
  functions), tuples_consts (converting `()` to `Int`), value_semantics
  (closures).

All bench/perf/llvm programs produce the same output as before (checksums
checked by `run.sh` and `TestLeakCheck`).

## Correctness

- `go test ./internal/ssa`: every golden and bench program verifies after
  `InsertRC` (balance on every path); `TestVerifyRCMutations` deletes each
  of the 92 retains and releases in the RC golden and bench programs, one
  at a time, and the verifier rejects every mutant (writing that test
  found two verifier holes, fixed: a release before `unreachable` and a
  loop block parameter that hid a leak; see `gotchas/rc-verifier-loop-param-leak.md`).
- `go test ./internal/llvm`: each golden builds with the Go backend, the
  LLVM default path, the LLVM AST path, and the AST path without range
  analysis; all four agree with each other and `want.txt` (exit status,
  stdout, fault messages). SSA path programs that exit normally run again
  with `XO_LEAKCHECK=1` and must report 0 live allocations.
  `rc_values` and `rc_aliasing` stress RC: lists of strings, lists of
  lists shared and then written, structs and enums holding lists and
  strings, `var` receivers, `with`, element overwrites, early returns
  from nested loops, `pop` moving elements out, `get` and `??` on
  `Option[Str]`.
- `TestLeakCheck`: the seven bench programs take the SSA path, print
  their checksum, and free every allocation:

retained or released except the strings workload's words.

Control (is the memory win the allocator or RC?): the AST path built on
the new runtime (`XO_LLVM_AST=1`, size class allocator but no frees)
uses the same memory as before: sieve 137 MB, sort 150 MB, strings 10 GB
(best times 100, 230, 1640 ms). The reclamation is what RC adds.

Notes:

- **sieve** frees each 10M element list before the next round: 54 MB
  peak is one list growing by doubling (8 MB to 16 MB with both alive
  during the copy) plus the allocator's chunks. Go: 49 MB.
- **sort** frees each round's million records; 78 MB matches Go (whose
  peak varies between 78 and 96 MB with GC timing). Faster than before
  (213 against 230 ms): the list writes in `quicksort` have no check
  (unique at entry) where the prototype checked the shared flag per
  write.
- **strings** is the allocation workload: 200,000 interpolated strings per
  round pushed onto a list, popped off, and every tenth appended to an
  accumulator, 10 rounds. RC frees each word when it is dropped (2M
  allocations, at most about 200,000 live), the accumulator grows in
  place, and interpolation appends numbers into the string being built.
  The prototype never freed and copied the accumulator on every append
  (10.4 GB). Go uses a `strings.Builder` for the accumulator. Two
  changes found by profiling the first RC version (147 ms, 1.6x of Go):
  appending an Int's text without a temporary string cut allocations 3x
  but only 10 ms; replacing `snprintf("%lld")` with a digit loop cut it to
  36 ms (`gotchas/snprintf-int-formatting-cost.md`).
- **nbody** is unchanged at 1.15x: no RC in its loop; the difference to
  Go is the bounds checks on `bs[i]` (see the prototype report).
- fib, interp, collatz: no heap work in the loop; within run to run
  noise of before.

### Caveats

- One host, arm64, wall clock of whole processes with laptop drift up to
  10 percent (`gotchas/bench-host-timing-drift.md`); single runs (REPS=1)
  include macOS first run latency (`gotchas/macos-first-run-latency.md`).
- The workloads are in the SSA subset; programs with closures, generics,
  or failing functions still use the AST path and still never free.
- Counts are not atomic; there are no tasks in the native backend yet.

## What is left (ranked by likelihood of paying off)

1. **Grow the SSA subset so every LLVM golden takes the RC path**:
   `==` on structs, enums, and lists (an `eq` op lowered to generated
   helpers), `List.first`, `List.last`, `xs.indexed()`, then failing
   functions with `?` (Result return, `from` conversion), generics
   (monomorphize in `ssa.Build` by instantiating `declare` per type
   arguments, as internal/llvm does), closures (an env leaf kind: a
   counted cell of captured values), and recursive types (a box leaf
   kind). Experiment: add `eq` first, then rerun
   `go test ./internal/llvm -run TestGolden -v` and move enums, structs,
   and recursion into `ssaGolden`.
2. **Delete the AST path** once 1 is done (about 4,000 lines), keeping
   `XO_LLVM_AST` until then for comparisons.
3. **Allocation heavy request handling** (the open claim of decision
   0040): port a JSON like tokenizer or word count once Map lands in the
   SSA path, and compare with Go under load; strings here (0.40x of Go,
   half its memory) is the first evidence.
4. **Drop reuse** (Perceus reusing a dying cell for the next allocation
   of the same size): measure first how often `release` of a list is
   followed by `list.new` of the same element type in one block (sort's
   rounds do it once per round); the free list may already make this
   moot.
5. **nbody's 15 percent**: make `list.index` and `list.set` with a proven
   index skip the bounds check (carry the range analysis into SSA as
   `Pos` cleared for proven operations), then `WORKLOADS=nbody`.
6. **Atomic or per task counts** before tasks come to the native backend.

## Update 2026-10-08: every program on the SSA path, AST path deleted

Question: can the 13 goldens that still fell back to the AST path (which
never frees) be lowered through internal/ssa, so that every LLVM build is
reference counted, and can the AST path then go?

Answer: yes. All 29 original LLVM goldens, plus seven new `rc_*`
goldens that stress ownership of the new features, take the SSA path,
and every one that exits normally reports 0 live allocations under
`XO_LEAKCHECK=1`. The AST path (about 4,000 lines of internal/llvm and
its never freeing runtime half) is deleted. The bench programs compile
to the same IR as before (one unused `declare` added), and their times
and memory are unchanged.

What was added, one commit each (design: decision 0048):

| Feature | How | Goldens moved | New goldens (SSA and LLVM) |
|---|---|---|---|
| Failing functions and `?` | Result return, `Ok`/`Err`, `?` on Result (with `from` conversion) and Option, Result methods, `or_fault` | result | failing / rc_failing |
| `==` on aggregates, `is` | `eq`/`ne` on any type, borrowed; per type `xo.eq.T` helpers | enums, structs, tuples_consts | equality / rc_equality |
| `first`, `last`, `indexed` | `list.get`; `(i, x)` per element | interp, lists, option | listmethods / rc_listmethods |
| Closures | `Indirect` Funcs, env `{rc, drop, captures}` as one heap leaf, `closure`/`capture`/`callv` | closures, closure_try | closures / rc_closures |
| Generics | monomorphized in the builder, one Func per type arguments | misc | generics / rc_generics |
| Recursive types | `Box[T]` fields, `box`/`unbox`, worklist drop (`xo_rc_defer`) | generics, recursion, value_semantics | recursive / rc_recursive |

Verification per feature: the SSA golden prints before and after
`InsertRC`; `Verify` checks RC balance on every path of every golden
(the RC mutation test now covers all SSA goldens: deleting any one of
the inserted retains or releases is rejected); the LLVM golden output
equals the Go backend's and `want.txt`; the leak check reports 0 live.
Writing the goldens found one verifier hole the other way (a false
rejection): predecessors of an `unreachable` block need not agree on
what they hold (`gotchas/rc-verifier-stop-block-merge.md`).

Long chains: `rc_recursive` builds and frees a 1,000,000 node linked
list of boxes, `rc_closures` a chain of 100,000 closures each capturing
the previous one. Both are released through the worklist (an object
reaching zero while another is being dropped is queued, not dropped
recursively).

### What is left (ranked by likelihood of paying off)

1. **Carry the range analysis into SSA**: `gen.SafeIntOps`
   (`internal/gen/rangesapi.go`) has no caller since the AST path is
   gone; clearing `Pos` on proven Int operations and `list.index` in
   `ssa.Build` would remove nbody's bounds checks (its 15 percent).
   Experiment: call it in `builder.body` per FuncObj and skip `Pos` for
   nodes in the set, then `WORKLOADS=nbody bench/perf/llvm/run.sh`.
2. **Map and Set in the SSA path**: the largest missing feature for
   request handling programs (decision 0040's open claim). A Map is one
   more heap leaf with element callbacks like List.
3. **Iterative `xo.eq` for boxes**: equality of long recursive chains
   still recurses once per level (an explicit stack in the helper).
4. **Atomic or per task counts** before tasks come to the native
   backend; `xo_rc_defer`'s worklist is a global too.
5. **Drop reuse** (unchanged from above).
