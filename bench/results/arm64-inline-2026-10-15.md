# The arm64 inliner's continuation blocks (2026-10-15)

xo-fa, for the lead's option (a) after the TLS work (tls-perf-2026-10-15.md).

## Question

The arm64 emitter's fusions (add_with_flag, a shifted register operand)
match a value's producer. Through an inlined helper (aesgcm's `shl` and
`shr`, nistec's `ld`) they never fire: selfhost/arm64 inline.xo
inline_call splits the caller's block at the call and hands the callee's
result to a continuation block as a block parameter, so the consumer's
operand is a parameter, not the shift.

## First attempt and its diagnosis

Copying a callee of one block straight into the caller's block (no
split; the result replaces the call's uses) made the TLS workloads far
slower on arm64 (chacha 2500M to 5199M instructions, p256 3984M to
6885M), with calls (`bl`) where there had been inlined code. That looked
like register pressure, but it is not:

- selfhost/xo main.xo uses the inlined module only when it verifies
  (arm64 inline_step_jobs: `!inline_module(m) || verify ok`); otherwise
  it emits the module without any inlining;
- the straight copy failed verification (`edge to b3 holds {v172:1},
  another predecessor {}`): a counted value of the callee, copied into
  the caller's block, is held on one incoming edge of a later merge and
  not on the other; through the continuation's parameter it is not;
- so the whole program lost its inlining, which is the slowdown.

## The two attempts (time boxed by the lead at two)

Copy straight only a callee whose values are all scalars (Int, Float,
Bool, Unit: nothing counted), which is what the hot helpers are; others
keep the continuation. With that the module verifies, and the code is
the same size (chacha.xor_stream 501 instructions against 496). The
next batch makes the fusions use the now visible producers. Each batch is
checked against the whole bench/perf set on arm64 (the perf sweep's
phases), all arm64 goldens, the codegen patterns, -short, and xo built
by the new xo building hello.

### Attempt 1: scalar straight copies (2026-10-15)

Whole bench/perf set on arm64 (the perf sweep's phases: single,
testworld, conc, httpclient, tls, http; 3 interleaved repetitions,
medians, 151 workloads), against the same tree without it (9e8a53b8):
no workload faster beyond its spread except net and text `none` (0.94,
startup noise of 7 to 9%); a few slower beyond it: alloc small 1.048,
text split 1.030, alloc strings 1.026, text lines 1.024, alloc maps
1.023, text int_fmt 1.022 (spreads under 1%). The copies make longer
blocks, and the allocator spills a little more in them.

### Attempt 2: plus shifted register operands for and, orr, eor

The fusion now fires (the shifts are visible), against the same base,
the TLS workloads (M instructions, N=200 or 64 MiB):

| Workload | Base | Attempt 2 | Change |
|---|---|---|---|
| aes128 | 1165 | 1102 | -5.5% |
| chacha | 2533 | 2501 | -1.3% |
| x25519only | 2534 | 2520 | -0.5% |
| p256 | 3989 | 3971 | -0.4% |

## Verdict

Neither pays: 1 to 5% on a few crypto loops against 2 to 5% on the
allocator and text paths. Both reverted; nothing landed. What would
change the verdict: an allocator that does not lose in longer straight
blocks (its live ranges and spill choice in a block of many short lived
values), then the copies and the fusion again. The numbers above are
the baseline for that.
