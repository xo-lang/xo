# xo1 speed: the self hosted compiler on selfhost/xo (2026-10-13)

xo1-speed agent. Goal (owner, 2026-10-13): agents wait for xo1 builds
(5 to 12 minutes) and for the selfhost full tier, whose critical path is
the arm64 emitter on selfhost/xo. Two parts: (1) profile xo1 compiling
selfhost/xo with the arm64 backend and fix the hot spots in selfhost/;
(2) cache the built xo1 on its own inputs (decision 0198).

Measured: `xo1 asm --phase-times` of a fixed input, the selfhost/ and
std/ trees of main at afe4aefb (the base), by xo1 binaries built with
`XO_SELF_DRIVER=0 xo build --backend=arm64 selfhost/xo` from each
commit. Linux figures are from on demand r8g.2xlarge instances (8
vCPUs, 64 GiB, one run per instance, nothing else running) with GNU
`time -v`, `perf record -F 200 -g`, and a 15 s resident set sampler;
the Mac figures are from the shared 12 core Mac under the heavy lock
with `/usr/bin/time -l` and `sample` (other agents running: compare
instructions and cycles, not seconds). One run each.

xo1 compiles selfhost/xo 3.6 times faster on the Mac (588.86 s to
163.83 s wall, 5,520.6 to 2,035.4 billion instructions) in 37 percent
of the memory (26.1 GB to 9.66 GB footprint). The Go compiler's own
build of xo1 is unchanged (Mac: 365.46 s before, 354.43 s after; the
Go side is frozen), so the 5 to 12 minute wait for a new xo1 is cut by
part 2 (fewer rebuilds), and the selfhost tier's Xo arm64 emitter on
selfhost/xo by part 1.

The fixed point holds: on the Mac, `xo1 asm --std=std selfhost/xo` by
the final xo1 and `cd selfhost && xo asmdump xo` (the Go emitter) are
byte identical on the final sources (sha256 ef2988d8...9802,
20,472,741 lines).

## Where the time went (base profile, Linux, perf)

Inclusive shares of xo1's samples: the arm64 emitter 85.3 percent
(register allocation 32.3, instruction selection 24.7, dce 16.2,
live_dce 8.6), insert_rc 11.5. Self time: `xo_alloc` 26.6 percent (21.7
under `xo_rl_new`), the rc helpers 12.5 (7.6 freeing lists in dce),
`merge_sorted` 6.4, `dce_mark` 5.1, `transfer` 4.6, `or_into` 4.4,
`overlaps` 3.7, `new_bits` 3.3. `perf annotate` of `xo_alloc` (new1):
94.7 percent on the two instructions after the load of the free
block's link (a cache miss per pop; gotchas/native-heap-cold-free-lists.md).

## The fixes, in order of the profile

1. **Liveness in regalloc and live_dce** (regalloc.xo `solve_live`,
   `gen_kill`): the round robin over whole bit sets per block
   (`transfer`, `or_into`, a `new_bits` per block per pass in
   live_dce) became path exploration, one register at a time, into
   sorted lists per block; the walks use one bit set that each block
   clears through its own lists; each landing pad's registers are
   added once. Memory and time are those of the live sets.
2. **`[]` allocates nothing** (decision 0198): `Inst` has five list
   fields defaulting to `[]`, and `ranges`, `fixed`, `partners` one per
   register. 5.65 to 2.61 billion allocations with the next two.
3. **dce** (opt.xo `dce_live`): a worklist over each register's
   definition sites instead of passes until nothing changed; a block's
   kept instructions move (pop and push) instead of being copied.
4. **Occupancy** (regalloc.xo `overlaps_sorted`, `insert_ranges`): a
   binary search per range and an insertion, where `merge_sorted`
   rebuilt a register's or slot's whole list per assignment and
   `overlaps` walked it.
5. **Allocation per instruction**: `G.add`, `set_fault`, `checked`,
   `konst` update the block's list in place (decision 0169) instead of
   `take_insts`; `plain` keeps its uses when none is xzr; load and
   store texts are made once per offset; one candidate list per
   register; `push_rng` and `push_int` in place.
6. **insert_rc**: borrow_projections' sites in lists by value instead
   of maps; liveness walks each leaf back once instead of rebuilding
   every block's map per pass.
7. **The allocator prefetches** the next free block's link on each
   pop (std/llrt xo_rt.c): new3 to new4, emit 257.5 s to 221.3 s.

## Memory

The heap by size class at exit (`XO_HEAPSTATS=1`, new2): 14.4 GB of
4 MiB chunks carved, of it 6.2 GB of 256 KiB blocks, 2.2 GB of 128 KiB,
1.8 GB of 64 byte blocks. After the sparse liveness (new3): 4.3 GB
carved. The resident set now grows during insert_rc and inline (6.5 GB
at 90 s of new4) and the emitter adds about 1.5 GB.

`XO_HEAP_MID_MAX` (blocks above it go to malloc, which coalesces) on
new3's xo1: 4096 bytes 8.0 GB, 1024 bytes 7.9 GB, against 8.8 GB, with
the same time (emit 257.7 s and 255.8 s against 257.5 s). The default
stays.

## Part 2: the xo1 cache key

internal/selfdriver `BinaryKey`: the xo version, the host, selfhost/,
and the std modules selfhost reaches through `use` (at 427934aa: 26 std
files of the embedded set, 245 inputs in all). `TestBinaryKey`: a change to
std/toml.xo, std/llrt/xo_rt.c, or third_party/mbedtls keeps the key and
`binary` finds the cached xo1 beside a new source tree; a change to
selfhost/arm64/isel.xo, selfhost/xo.mod, std/native/prelude.xo, or
std/native/http.xo, or another version, gives a new key.

## Next, ranked by expected gain

1. dce is 22.8 percent of new4: moving 200 byte `Inst`s (`dce_keep`
   self 10.8 percent). A runtime compaction of a list by a keep mask
   (memmove, release only the dropped) would remove the moves; or a
   smaller `Inst` (its seven strings are 112 bytes).
2. `xo_alloc` is still 18 percent, mostly the first push into `[x]`
   literals of defs and uses in isel (`load_words` 22.9 percent
   inclusive): defs and uses of one register without a list.
3. Build xo1 with the cached xo1 when one exists (164 s for the asm
   against the Go compiler's 354 s build): a bootstrap step in
   internal/selfdriver, with a decision on when a stale stage is safe.
4. insert_rc (46.8 s) keys leaves by strings (`leaf_key`); integer
   keys would remove the string building and hashing.
