# Where Xo is behind Go: warm builds and xo test memory (2026-11-10, Xo Lang 2)

The two "where Xo is behind" rows of the performance page (release-vs-go-v0.40.0.md: coll's warm
build, xo test's peak memory), measured again on linux/arm64 host 1 (exclusive lease, 12 CPUs)
with the 0.47.0 seed xo (d207dfe20), private HOME and caches, as release-vs-go.sh's compile()
prepares them (cold, std's variants, the records build, then warm). Raw output:
the lead's notes, xo-lang-2/perfgaps-job1.out and perfgaps-job2.out.

## 1. coll's warm build, whole-build cache off and on

| XO_BIN_CACHE | cold | second | warm (7 builds) | warm peak RSS |
|---|---|---|---|---|
| off (the compile path) | 1246 ms, 237 MB | 157 ms, 97 MB | 132 to 177 ms | 63 to 67 MB |
| on (the default: an unchanged rebuild) | 1573 ms, 234 MB | 132 ms, 101 MB | 13 to 14 ms | 14 MB |

So a user's unchanged rebuild of coll takes 13 to 14 ms and 14 MB; the 100 ms / 52 MB row of the page is
the compile path with that cache off.

## 2. Where the warm build's time goes (--phase-times, cache off)

check 14.5 ms (heap peak 35 MB), front end 9.5 ms, SSA 10.6 ms, the passes from their caches about 12 ms,
emit 55 to 58 ms, link 10.5 ms (peak 51 MB). Emit is the largest phase, with every function's passes
read from the caches: a separately compiled program of one part (coll, fewer than 256 functions) got no
function or part cache, since compiler/arm64 function_keys and part_keys return none for a module of one
part, though generate_cached takes such a program through the parts. Fix (branch l2-sepfc): the cache for
a separately compiled program of one part. Mac, the same warm build: emit 48 ms to 4 ms ("cache parts 1/1
reused"), wall about 0.12 to 0.09 s; the binary from a reused part is byte identical to the one from a
generated part, and the program prints the same.

linux/arm64 host 1, `ab-host.sh 44ccf696a7 8844ec574 sepfc -- edit bench/perf/xo` (the warm rebuild, 3 rounds, 0 loaded):

| metric | A (main) | B (the fix) | B / A | 95% interval |
|---|---|---|---|---|
| wall ms | 110.4 | 52.84 | 0.479 | 0.479 to 0.486 |
| cpu ms | 110.3 | 52.34 | 0.475 | 0.475 to 0.481 |
| max RSS KB | 66192 | 64888 | 0.98 | 0.95 to 0.98 |

Check is 14 ms of the warm build, so step 4 of the queue (reuse an unchanged module's check across
builds) is not where the warm build's time goes.

## 3. xo test peak memory (std module tests, cold and edit)

| | cold | edit (3 builds) |
|---|---|---|
| base64: go test -count=1 | 1745 ms, 302 MB | 250 to 256 ms, 106 MB |
| base64: xo test --std-module | 1401 ms, 299 MB | 222 to 257 ms, 202 to 218 MB |
| json: go test -count=1 | 3515 ms, 300 MB | 726 to 738 ms, 156 to 158 MB |
| json: xo test --std-module | 1635 ms, 324 MB | 182 to 224 ms, 220 to 233 MB |

go test's peak is its largest single tool process (-toolexec: the package's compile 106 MB for base64,
158 MB for json; the link 89 and 150 MB). xo test's test binary is already its own process (compiler/xo
test.xo run_test_env); the peak is the compiler's heap: about 155 to 160 MB after check, 203 to 214 MB at
the SSA phase in an edit. A heap snapshot at the end of check (Mac, base64 edit): 130 MB in use, 75 MB of
it parse trees (parser.parse_file), 14.6 MB source bytes. The edit builds 15 std modules from source:
base64 and every std module that imports it, transitively (stdcache.xo std_source_set), whether the test
reaches them or not. The base64 edit also pays the one-part emit of section 2 (92 ms; json's, of several
parts, 3 ms).

Next: (a) build from source only the importers the test program reaches; (b) drop each from-source
module's parse trees after its check (lazy_parse already skips std's bodies); measure peak per phase again.
