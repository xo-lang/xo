# std/x509 changes

## 2026-11-13: security: name constraints are checked in n log n time (native)

- Kind: security
- Commit: this commit
- Found by: the decision 0616 security review of std/x509 (Go advisory sweep: GO-2025-4007, CVE-2025-58187)
- Go reference: crypto/x509 constraints.go (go1.26.1): sorted sets, maps for the wildcard parents and mailboxes
- Affected: Xo 0.50.1 and earlier, native backends
- Test: corpora x509, x509fuzz (Go's PKITS name constraint chains) and std/native/x509_test.xo; x509fuzz seeds 13 and 14 (3000 cases each)
- Timing: an intermediate with 4000 excluded DNS names over a leaf with 4000 names, on the Mac: 62 ms before, 1 ms after (Go 1.27.4: 1.8 ms); 500, 1000, 2000: 1, 4, 14 ms before
- Shipped in: not yet released

Each certificate's DNS and IP constraint sets were sorted by insertion and the wildcard parents and exact mailboxes found by a scan, so a certificate with many constraints, and a leaf with many names under it, cost time quadratic in them. The sets now use a stable n log n sort (the same order) and maps, as Go.

## 2026-11-13: security: a host name is split once per check, and a certificate with 100 or more names is not listed in the error (native)

- Kind: security
- Commit: this commit
- Found by: the decision 0616 security review of std/x509 (Go advisory sweep: GO-2025-4155, CVE-2025-61729; GO-2026-5037)
- Go reference: crypto/x509 verify.go VerifyHostname, splitHostname and HostnameError.Error (go1.27.4)
- Affected: Xo 0.50.1 and earlier, native backends: Certificate.verify_hostname and std/tls's server name check
- Test: std/native/x509_test.xo (certificates of 150 DNS names, 99 DNS names and 150 IP SANs; go1.27.4's texts; fails without the change)
- Timing: none on ordinary certificates
- Shipped in: not yet released

A host name check split the host once per name in the certificate, and the error for a host that matched none listed every name, building the IP list by repeated concatenation, so a certificate with many names made each failed check cost time quadratic in them. The host is now split once, and a certificate with 100 or more names gives `x509: certificate is valid for N names, but none matched HOST` (`N IP SANs` for an IP address), as Go.

## 2026-11-13: security: chain building counts every candidate toward the signature check limit; policy mappings prune once (native)

- Kind: security
- Commit: this commit
- Found by: the decision 0616 security review of std/x509 (Go advisory sweep: GO-2026-4947, GO-2026-4946)
- Go reference: crypto/x509 verify.go buildChains and policiesValid (go1.27.4)
- Affected: Xo 0.50.1 and earlier, native backends (the Go backend follows its Go toolchain: go1.26.1 is affected)
- Test: std/native/x509_test.xo D3 and D4 (self-issued intermediates; go1.27.4's verdicts; D3 fails without the change); corpora x509, x509fuzz (with Go's PKITS policy chains), pemfuzz; x509fuzz seeds 11 and 12 (3000 cases each)
- Timing: none on ordinary chains (the same checks; a crafted pool now stops at the limit)
- Shipped in: not yet released

Chain building counted a candidate toward Go's limit of 100 signature checks only after skipping candidates without a usable key or already in the chain, and went on looking at candidates after reaching the limit, so a crafted pool of intermediates cost much more than the limit allows. Every candidate now counts and the limit ends the whole search, as Go 1.27.4; a pool of 30 self-issued intermediates with no route to a root is now `x509: signature check attempts limit reached while verifying certificate chain` where it was an unknown authority. Policy validation pruned the policy graph after each mapping it deleted; it now prunes once after them, as Go 1.27.4.

## 2026-11-13: security: PEM text is read in linear time, as Go's pem.Decode

- Kind: security
- Commit: this commit
- Found by: the decision 0616 security review of std/x509 (Go advisory sweep: GO-2025-4009, CVE-2025-61723)
- Go reference: encoding/pem Decode (go1.26.1): the first END line, then the last BEGIN line before it
- Affected: Xo 0.50.1 and earlier, native backends: x509.parse_pem, and the PEM std/tls and std/http read (certificates, keys, roots)
- Test: internal/stdtest/pemfuzz_test.go and its corpus testdata/corpus/pemfuzz (1000 PEM texts against Go's pem.Decode and ParseCertificate, and one megabyte of BEGIN lines; go, arm64, llvm)
- Shipped in: not yet released

The native PEM reader searched for each BEGIN line's END line to the end of the text, so a text of many BEGIN lines without an END took time quadratic in its length (one megabyte: 45 s). It now follows Go's pem.Decode: find the first END line, take the last BEGIN line before it, and continue after that END line, so each byte is read a bounded number of times. Its block rules are Go's too (headers, the END line's type and trailing white space, base64 padding), where the earlier reader differed from Go on 156 of the 1000 fuzz texts (it accepted missing padding and other near-PEM).

## 2026-11-13: security: DNS name constraints compare a wildcard SAN case-insensitively (native)

- Kind: security
- Commit: this commit
- Found by: the decision 0616 security review of std/x509 (Go advisory sweep: GO-2026-4866, CVE-2026-33810)
- Go reference: crypto/x509 constraints.go (go1.27.4): newDNSConstraints and query lower-case the parent constraint keys and the wildcard
- Affected: Xo 0.50.1 and earlier, native backends (the Go backend follows its Go toolchain: go1.26.1 is affected, the fix is in go1.27)
- Test: std/native/x509_test.xo (six chains and verdicts from go1.27.4; arm64 and llvm)
- Shipped in: not yet released

Chain verification on the native backends compared an excluded DNS name constraint with a wildcard SAN case-sensitively, so a differently cased SAN was not held to the constraint. Both sides are now lower-cased before the comparison, as Go 1.27.4 does.

## 2026-11-13: fix: ext_key_usage in the extension's order on native

- Kind: fix
- Commit: this commit
- Found by: the decision 0616 fuzz harness internal/stdtest/x509fuzz_test.go, first run (a mutated certificate whose unnamed usage came before anyExtendedKeyUsage)
- Go reference: crypto/x509 parseExtKeyUsageExtension (go1.26.1) keeps two lists, ExtKeyUsage and UnknownExtKeyUsage; spec/std.md 41 gives one list in the extension's order
- Test: internal/stdtest/testdata/corpus/x509fuzz (1000 cases from seed 1, go, arm64 and LLVM)
- Shipped in: not yet released

`Certificate.ext_key_usage` on the native backends listed the usages Go names first and the others after, the order the native verifier reads (Go's two lists); a certificate with an unnamed usage before a named one listed them out of the extension's order, which the spec and the Go backend keep. The parser now keeps both: the extension's order for the field, Go's for verify.

## 2026-11-12: security: certificate and TLS signatures by an RSA key below 1024 bits are refused

- Kind: security
- Commit: this commit
- Found by: the decision 0616 security review of std/crypto's RSA (second reviewer, finding F6)
- Go reference: crypto/rsa checkPublicKeySize (VerifyPKCS1v15, VerifyPSS: below 1024 bits is an error, go1.26.1)
- Test: std/native/crypto_test.xo "rsa: a key below 1024 bits parses but every operation refuses it, as Go" (a 1020-bit and a 1024-bit key and signature from Go)
- Shipped in: not yet released

The native RSA verification std/x509 and std/tls use (a certificate's signature, a TLS peer's handshake signature) refused a key shorter than 128 bytes, so a 1017 to 1023 bit key, which Go refuses, was used to verify. It now refuses below 1024 bits, as std/crypto's own operations already did. Parsing such a key still succeeds, as Go's.

## 2026-11-05: perf: parse_pkcs12's key derivation iterates SHA-1 without allocating

- Kind: perf
- Commit: this push
- Found by: XO_PROF on the 20 parse timing (the per round `sha1.sum` Hasher and padding buffers were about 25 percent of a parse)
- Go reference: crypto/sha1 as golang.org/x/crypto/pkcs12 calls it for each of the (typically 2048) rounds
- Test: std/native/llrt/sha1_test.xo (iterate equals n sums) and the pkcs12 corpus (go, arm64 and LLVM)
- Timing: Mac arm64, 20 parses of a LibreSSL file with a certificate chain, 3 runs: 31.0, 31.6 and 35.1 ms before, 23.4, 24.9 and 23.5 ms after (0.74 of before); Go 15 to 21 ms, so Xo is now about 1.1 to 1.6 of Go (was 1.5 to 2.1). Left: the RSA key import (bigmod, 21 percent) and 3DES (12 percent)
- Shipped in: not yet released

`sha1.iterate(a, n)` applies SHA-1 n times to a 20 byte value with the CPU's SHA-1 instructions, building the block once and compressing it in place; `pbkdf` calls it for its rounds (other CPUs, and values of another size, take n calls of `sum`).

## 2026-11-05: feature: parse_pkcs12 reads .pfx and .p12 files

- Kind: feature
- Commit: this commit
- Found by: the Azure SDK (a certificate credential is a PFX, decision 0006-xo-gaps in the azure repository)
- Go reference: golang.org/x/crypto/pkcs12 v0.58.0 (BSD, Copyright 2015 The Go Authors); crypto/des; the RC2 of its internal/rc2
- Test: internal/stdtest/testdata/corpus/pkcs12 (scripts/stdcorpus pkcs12.go: Go's three test files and two OpenSSL files with passwords, truncations and bit flips, against Go's result) on go, arm64 and LLVM; std/native/llrt/des_test.xo (the FIPS 46 vector) and rc2_test.xo (Go's rc2 vectors)

`x509.parse_pkcs12(data, password)` returns the private key, the leaf certificate and the other certificates of a PKCS #12 file. The native backends run a port in Xo (std/native/llrt/pkcs12.xo, des.xo, rc2.xo: the key derivation, MAC check, 3DES and RC2 decryption and bag walking of Go's package); the Go backend vendors the package (std/rt/xcrypto_pkcs12.go). Deviations: chains and several bags are read where Go's Decode wants exactly one certificate and one key, and the leaf is chosen by localKeyID. Error texts are Go's; a malformed file's asn1 wording differs.

Timing against Go's package (Mac arm64, `ToPEM` against `parse_pkcs12` on a 3 KB chain file with 2048 iteration keys, 20 parses, release build; 2026-11-05): Go 15 to 21 ms, Xo 31 ms, so 1.5 to 2.1 times slower. The profile: RSA key import (bigmod, shared with `crypto.parse_private_key`) 21%, SHA-1 compression 12%, the key derivation's per iteration `sha1.sum` allocations about 25%, 3DES 12%. The 3DES feistel box is built from 128 permutations, not Go's 512. Next: a hashing loop without a Bytes per iteration.

## 2026-10-29: feature: std/x509, certificate parsing and chain verification

- Kind: feature
- Commit: this commit
- Found by: milestone 0.35.0 S5 (public x509 from the parser and verifier TLS already has)
- Go reference: crypto/x509 (ParseCertificate, Certificate.Verify, VerifyHostname, CheckSignatureFrom, SystemCertPool's sources), crypto/x509/pkix (Name, Name.String) (go1.26.1)
- Test: internal/stdtest/testdata/corpus/x509 (scripts/stdcorpus x509.go: every certificate of Go's crypto/x509 and crypto/tls testdata, a fifth of the NIST PKITS certificates, verify_test.go's certificates and truncated and bit-flipped copies, each field and error text against Go's ParseCertificate; verify_test.go's verifyTests rows with roots against Go's Verify chains and errors; Name escapes) on go, arm64 and LLVM; bench/perf/x509 twin

New module std/x509 (spec std.md 41): `parse(der)` and `parse_pem(pem)`
give a `Certificate` (raw DER, version, serial, Go's signature algorithm
name, issuer and subject `Name`s with Go's `display()` and every
`attributes()`, validity, `crypto.PublicKey`, DNS names, IP addresses,
e-mail addresses, URIs, basic constraints, key usages, extended key
usages, key ids and every extension). `Certificate.verify(opts)` is Go's
Verify with explicit roots, intermediates, DNS name, time and key
usages, returning every chain or Go's error text; `verify_hostname`,
`check_signature_from`, and `system_roots(fs)`, the roots std/tls
checks servers against (on macOS the system's anchor certificates). The
native backends wrap the TLS stack's parser and verifier
(std/native/llrt/x509cert.xo, x509verify.xo), which now also keep every
extension, the Go backend Go's crypto/x509.

bench/perf/x509 against Go's crypto/x509 (quiet `xo bench --ab`, 15
rounds, Go as A, wall): parse_pem of a three certificate chain 1.183,
verify 1.002. The PEM scan (std/native/llrt/tlsname.xo find_at, shared
with std/tls and std/http's PEM roots and keys) compares a marker's first
byte before the rest: parse_pem 0.865 of the parent's wall.
