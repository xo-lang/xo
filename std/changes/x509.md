# std/x509 changes

## 2026-11-15: feature: PKCS #1, SEC 1, PKCS #8 and PKIX typed key parsers and marshalers

- Kind: feature
- Commit: this push
- Found by: aws-43's x509 features audit against Go 1.26 (piece 9)
- Go reference: crypto/x509 pkcs1.go (ParsePKCS1PrivateKey, MarshalPKCS1PrivateKey, ParsePKCS1PublicKey, MarshalPKCS1PublicKey), sec1.go (ParseECPrivateKey, MarshalECPrivateKey), pkcs8.go (ParsePKCS8PrivateKey), x509.go (ParsePKIXPublicKey); encoding/asn1 asn1.go (parseField's optional and explicit fields, parseBitString), go1.26.11
- Test: corpus x509keys (arm64, LLVM, Go backends; 385 DERs: every hex key of pkcs8_test.go and sec1_test.go, each key's PKCS #8, PKCS #1 or SEC 1, PKIX and PKCS #1 public encodings, and 400 mutations: a bit, a cut, a trailing byte, a tag, a length, a non-minimal or negative INTEGER), each through the five parsers against Go's; the three marshalers of the 10 keys std/crypto holds against Go's; and round trips. Mutation checks: dropping a hint, the INTEGER minimality rule, the BIT STRING padding rule, the explicit optional skip, SEC 1's curve, or the PKCS #1 public key's slice each fail the corpus; dropping the PKIX trailing data check does not (std/crypto's parse gives the same text)
- Timing: none
- Shipped in: not yet released

`x509.parse_pkcs1_private_key`, `parse_ec_private_key`, `parse_pkcs8_private_key`, `parse_pkcs1_public_key` and `parse_pkix_public_key` each read one key form, with Go's errors: a DER of another form gets Go's hint naming its parser (`x509: failed to parse private key (use ParseECPrivateKey instead for this key format)`), told apart as encoding/asn1 does (optional fields skipped on a tag or an explicit tag's inner type that differs, extra elements at a SEQUENCE's end allowed). The key itself is std/crypto's parse. `marshal_pkcs1_private_key`, `marshal_ec_private_key` (with its curve and public key, as Go) and `marshal_pkcs1_public_key` write Go's bytes; for a key of another algorithm, which Go's types refuse, they return `x509: not an RSA key` or `x509: not an ECDSA key`. Deviations, as std/crypto's: encoding/asn1's own error texts are `x509: malformed private key`, `x509: malformed public key` or `...: malformed DER`; an X25519 PKCS #8 key and a multi-prime RSA key are errors (std/crypto holds neither).

## 2026-11-15: feature: CertPool add_cert_with_constraint, append_certs_from_pem, equal

- Kind: feature
- Commit: this push
- Found by: aws-43's x509 features audit against Go 1.26 (piece 4)
- Go reference: crypto/x509 cert_pool.go (AddCertWithConstraint, AppendCertsFromPEM, Equal), verify.go buildChains (considerCandidate's constraint call)
- Test: corpus x509create (arm64, LLVM, Go backends): "append_certs_from_pem is Go's AppendCertsFromPEM" (10 PEM texts: none, junk, headers, other types, a bad DER, bad base64, duplicates; the result and contents by Go's Equal), "CertPool.equal is Go's Equal" (8 pairs), and "add_cert_with_constraint is Go's AddCertWithConstraint in verify" (11 chains: a constraint that refuses with the chain's subjects, so the hint shows the chain Go passed, one that accepts, one that refuses chains longer than one, on roots and intermediates, beside an expired root and a second root of the name, and duplicates keeping the first constraint).
- Timing: none
- Shipped in: not yet released

`CertPool.add_cert_with_constraint(c, constraint)` adds c with a constraint that verify calls when c is a candidate parent, with the chain so far (leaf first, without c); an Err refuses the chain through c, and its text becomes the unknown authority error's hint, as Go's buildChains does. `append_certs_from_pem` adds each CERTIFICATE block without headers that parses and returns whether one did; `equal` compares the pools' certificates by DER. The native chain search now also keeps an isValid failure as the first hint and clears the level's error when a candidate passes isValid, as Go does; that changes nothing without a constraint. Go's Clone is not needed (an Xo pool is a value), and SetFallbackRoots does not apply (verify takes its roots explicitly).

## 2026-11-13: security: chain building counts every candidate toward the signature check limit; policy mappings prune once (native)

- Kind: security
- Commit: this commit
- Found by: the decision 0616 security review of std/x509 (Go advisory sweep: GO-2026-4947, GO-2026-4946)
- Go reference: crypto/x509 verify.go buildChains and policiesValid (go1.27.4)
- Affected: Xo 0.50.1 and earlier, native backends (the Go backend follows its Go toolchain: go1.26.1 is affected)
- Test: std/native/x509_test.xo D3 and D4 (self-issued intermediates; go1.27.4's verdicts; D3 fails without the change); corpora x509, x509fuzz (with Go's PKITS policy chains), pemfuzz; x509fuzz seeds 11 and 12 (3000 cases each)
- Timing: none on ordinary chains (the same checks; a crafted pool now stops at the limit)
- Shipped in: not yet released

Chain building counted a candidate toward Go's limit of 100 signature checks only after skipping candidates without a usable key or already in the chain, and went on looking at candidates after reaching the limit, so a crafted pool of intermediates cost much more than the limit allows. Policy validation pruned the policy graph after each mapping it deleted; it now prunes once after them, as Go 1.27.4.

## 2026-11-13: security: PEM text is read in linear time, as Go's pem.Decode

- Kind: security
- Commit: this commit
- Found by: the decision 0616 security review of std/x509 (Go advisory sweep: GO-2025-4009, CVE-2025-61723)
- Go reference: encoding/pem Decode (go1.26.1): the first END line, then the last BEGIN line before it
- Affected: Xo 0.50.1 and earlier, native backends: x509.parse_pem, and the PEM std/tls and std/http read (certificates, keys, roots)
- Test: internal/stdtest/pemfuzz_test.go and its corpus testdata/corpus/pemfuzz (1000 PEM texts against Go's pem.Decode and ParseCertificate, and one megabyte of BEGIN lines; go, arm64, llvm)
- Shipped in: not yet released

The native PEM reader searched for each BEGIN line's END line to the end of the text, so a text of many BEGIN lines without an END took time quadratic in its length (one megabyte: 45 s). It now follows Go's pem.Decode: find the first END line, take the last BEGIN line before it, and continue after that END line, so each byte is read a bounded number of times. Its block rules are Go's too (headers, the END line's type and trailing white space, base64 padding), where the earlier reader differed from Go on 156 of the 1000 fuzz texts (it accepted missing padding and other near-PEM).
