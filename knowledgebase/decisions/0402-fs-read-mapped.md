# 0402: Fs.read_mapped, a file mapped read-only as an immutable Bytes

Status: Accepted (2026-10-29; Lang 1; reviewed by Xo Lang 3 for the Fs surface, the writers and the allocator's free path; the Lead chose to land rt.str_at first). Progress: rt.str_at lowered on arm64 and LLVM (7baee065b); read_mapped and the link's use landed 2026-10-30 (see Implementation; an xo built from main after 7baee065b builds it, and the 0.35 seed is cut from it).

## Context

A separately compiled build links against std's store, a 29 to 31 MB file in the backend cache (decision 0388). The darwin link reads all of it on every edit build (`os.fs.read`), and the link's own laps show the read costs 5 ms of fib's 23 ms link (`link.read_store`), while `store_prepare` then uses only the live atoms' bytes, a small fraction of the file. The read also puts the whole 29 MB in the build's heap (peak RSS).

std has no way to map a file: `Fs` reads into a fresh `Bytes`. The runtime calls mmap internally (std/native/llrt libcsys.xo, linux.xo, sys_darwin.xo) for its own needs: heap chunks, stacks, and XO_HEAP_GUARD's guarded blocks.

## Decision

1. **API (std prelude, Fs, a method so the capability check is read's):** `fn (f: Fs) read_mapped(path: Str) -> Bytes ! FsErr uses fs.read`: the file's contents as an immutable `Bytes`, like `read`, with the same errors. On the native backends of darwin and linux it maps the file read-only and private instead of copying it; the pages are read from the page cache as the program touches them. Where mapping is not possible (wasm, the Go backend, Windows until it is wired, a pipe or device, a zero-length file, mmap failing) it is `read`. Callers never branch: the result is a `Bytes` either way and equal byte for byte.

   Plumbing as every Fs method: a native prelude `fs_read_mapped` (compiler/ssa call.xo `fs_${name}`) with read's mode checks (rt.fs_mode, rt.fs_root); only the root Fs maps: every restricted, test or recording Fs (RecFs, UserFs, the testing FakeFs) calls `fs_read`, so a recorded run captures the bytes and a replay never maps. The Go backend: std/rt `Fs.M_read_mapped` is `M_read` (scripts/stdgen, scripts/stdsync for the index). Go reference: none in Go's standard library (golang.org/x/exp/mmap's ReaderAt, syscall.Mmap).

2. **Contract** (spec/std.md and the doc comment in std/prelude.xo, Lang 3's wording): "read_mapped returns the file's bytes like read. On the native darwin and linux backends it may share the file's pages instead of copying them. The program must not truncate the file or change it in place while the Bytes (or a slice of it) is alive; replacing it by rename is safe. Where mapping is not possible it is read." In detail, the file must not be truncated or modified in place while a mapped `Bytes` of it lives: a truncation makes later reads of the cut pages fault (SIGBUS), a modification shows through. Replacing it by rename is safe (the mapping keeps the old inode). The std store qualifies: it is always written to a temporary name and renamed into place (stdcache.xo). The doc comment and spec/std.md state this, and that `read` is the choice for files other processes may change in place.

3. **Representation:** a Bytes is a Str object: a 16 byte header (S_HDR: the count and the capacity word, obj.xo) followed directly by its data. A mapped Bytes is one to every reader. The runtime reserves one page plus the file's size, rounded to pages, puts the header and a mapping record at the end of the first page (a magic word and the mapping's address and size, below the header, as libcmem.xo's guard_large keeps GUARD_MAGIC below a guarded block's prefix), and maps the file at the next page boundary with MAP_FIXED, so the data starts where the header ends. A slice is a view that holds a count on its parent (decision 0330), so a slice keeps the mapping alive and the parent's last drop, reached from a view's drop too, unmaps it.

   **The value is a view, so nothing writes it (draft 3).** A Str or Bytes value is two words, the object and a length word that packs a view's offset (decision 0330: `len | off << 32`, data at `obj + S_HDR + off`), and every in-place writer already refuses a view: obj.reserve's fast path requires `an >> 32 == 0`, since "a view is never unique, whatever its count". read_mapped returns the mapped object as a view at offset 8: the header sits 24 bytes below the page boundary, the file is mapped at the boundary, and the value is `(obj, len | 8 << 32)`, whose data `obj + 16 + 8` is the file's first byte. So no writer can take the in-place path by construction (reserve, Perceus reuse and push_fast all go to the copy path for a view), without a capacity trick (a capacity below the length would make the resize path copy too few bytes). The 8 bytes between the header and the data and the page below hold the mapping record (the magic word, the mapping's address and size) the free path reads. A file of 4 GiB or more cannot be a view (the length word's 32 bits) and is read. The audit below remains, as a check that every writer tests for a view. Xo Lang 3's audit on main (2026-10-29): obj.reserve (both forms) tests `an >> 32 == 0`; reserve_slow requires `off == 0` before rc.claim; rs_push_word and rs_push_words test `an >> 32 != 0`; arm64 push_fast compares `an` against the capacity unsigned, and a view's `an` exceeds any capacity, so it takes the slow path; LLVM compiles the same Xo functions; the other count == 1 users are not Str/Bytes writers (keep_object, lists, u8s_copy_back on a List[UInt8]); BytesBuilder.put_le/put_be see only a builder, and nothing turns a Bytes back into a builder. The value read_mapped returns is (the object, len | 8 << 32): the object pointer, not the data, so a view's last drop releases the object's count and reaches the free path. On wasm slices copy, so read_mapped is read there.

   **Read-only everywhere (the main risk).** The runtime writes in place into a string object whose count is 1 and whose capacity covers the need (obj.reserve, rs_append, rs_push_*, Perceus reuse of a unique buffer, arm64's push_fast), and `Bytes.to_str`/`Str.bytes` share the object, so `s + "x"` on a mapped file's text could store into its read-only pages (SIGSEGV/SIGBUS). A mapped Bytes has its capacity word equal to its length, so every grow takes the copy path; and every unique-object writer in std/native/llrt (obj.xo reserve, rs_push_*, rs_append*; raw.xo's bytes_buf users, fold_copy and the transforms; raw.put; arm64 push_fast) is audited so none writes when the length equals the capacity with nothing to add (a reserve of zero bytes passes `cap >= need`: its callers are checked too). Rule: a string object with count 1 and capacity == length is never written in place.

4. **Free (draft 3, from the allocator's code):** an object's free reads the 8 byte prefix below it (alloc.xo free and free_mt): a negative value sends it to rt.heap_big_release (cabi.xo), which hands a big block to heapos.release(b). A big block is a mapping m (page aligned, m[0] its size), its prefix b = m + 8 (minus the block's size), the object at m + 16; release(b) puts the mapping in heapos's cache for reuse (keep) or unmaps it. A file mapping must never reach that cache (the cache hands its pages out as heap memory). So the mapped object's words below it are laid out as a big block's, with sentinels: the region R (page aligned, one page plus the file rounded to pages, R + PAGE the file's MAP_FIXED mapping), the object at R + PAGE - 24 (its 16 byte header, then 8 spare bytes, then the file at R + PAGE), the prefix b = R + PAGE - 32 holding a large negative sentinel (below -128, so cabi.heap_big_release never takes it for a heap-profile sample), m = b - 8 holding MAPPED_MAGIC in place of a size, and below m the region's base R and length. heapos.release tests `size == MAPPED_MAGIC` before keep and membudget (one load and compare, big blocks only) and unmaps (R, length) instead. heapprof.freed sees a block it never recorded (to check: it must ignore one). A view is never resized in place (reserve copies a view), so large_resize never meets the mapped block. Small frees, the drop worklist and every reader are unchanged.

5. **Bootstrap (corrected, draft 4):** std code cannot make a Str or Bytes value from an object's address without a copy: `rt.obj_at[T]` takes only a List or a handle (compiler/ssa call.xo raw_generic), and `rt.cast` only between types that lower to one type (json.xo). So read_mapped needs one new runtime intrinsic, `rt.str_at(obj: Int, an: Int) -> Str` (the two words as a value, no count taken), lowered on the native backends (and refused or a copy on wasm and Go). The runtime (llrt sysio) is compiled into every program, xo itself included, so the 0.34.0 seed cannot build the runtime that uses it (gotchas/seed-older-than-intrinsics.md, 5c7f4ae61): read_mapped lands after the 0.35 seed is cut, as one change (the intrinsic, the runtime, the API, the link's use), or the intrinsic first and the rest after the seed.

6. **First user:** the darwin link's store read (compiler/xo ld.xo macho_link), then the ELF link's (elf_link); measured by link.read_store and the edit (finalab2.sh's method), each with an --ab.

## Consequences

- An edit build's link reads only the pages of the store it uses: link.read_store from about 5 ms to well under 1 (expected), and the build's peak RSS about 29 MB lower.
- One more case in the allocator's large free path, guarded by a magic word no heap block can hold (as GUARD_MAGIC).
- A program that maps a file another process truncates can fault; the doc and spec say so, and `read` stays the safe default.
- Tests: read_mapped's bytes equal read's on the native backends and on the read fallback (wasm, the Go backend: TestGoldenGoParity and the wasm goldens run a golden that reads a file both ways); the read-only rule (a golden: `let b = os.fs.read_mapped(p)?; let s = b.to_str() ?? ""; s + "x"`, `b.upper()`-style transforms, appends and slices of a mapped file, all copying); a rename over the file while it is mapped (the Bytes unchanged); a mapped Bytes freed, reused and freed many times (no leak: XO_LEAKCHECK counts the mapped block, and the heap profile either counts it or says it does not); a zero-length file and a missing one (FsErr as read); a recorded run and its replay (no mapping).
- std/changes/prelude.md (decision 0276): Kind perf (the headline is the link's speedup), Found by Lang 1 (link.read_store), Go reference none (x/exp/mmap, syscall.Mmap), Test the goldens above, Timing link.read_store before and after and the edit --ab row; and the page cache fact: the first read after the cache is dropped is not faster, only the touched pages are read.

## Alternatives

- **Read only the store's index, then the live atoms' byte ranges** (positional reads): no runtime change, but one read per live atom range (hundreds of syscalls an edit) or a coalescing pass; mapping gives the page cache's granularity for free. Kept as the fallback plan if the allocator change is refused.
- **Keep the store in a long-lived process** (a build daemon): removes the read entirely but is a much larger design (decision territory of its own).
- **A new runtime intrinsic for a mapped Bytes:** cleaner in the compiler, but the 0.34.0 seed could not build a compiler that uses it; the std-code design avoids that.

Free-path review (Xo Lang 3, 2026-10-29): heapos.release is the single hook (alloc.free and free_mt -> rt.heap_big_release -> heapos.release, no other route); test the sentinel in b (Int.MIN: no big block's prefix, below -128 so the sampled-block test skips it) and MAPPED_MAGIC in m first in release(), before membudget and keep(); heapprof.freed on an unrecorded block is already a normal case (confirm by a heap-profile run); bump ALLOCS (when COUNT != 0) at creation so XO_LEAKCHECK stays balanced, nothing for membudget; unmap R when the file's MAP_FIXED fails before falling back to read; a size change between fstat and mmap is the truncation contract. Gate: allocator microbench quiet --ab, alloc unit tests, alloc_threads and rt_probe goldens, TestGoldenRun, the fixed point, the Docker amd64 sample.

## Implementation (2026-10-30)

Where the code differs from the decision above:

- **A free function, not a method:** `read_mapped(fs: Fs, path: Str)`, as `read_text_or` and `read_or`: a new method of `Fs` would stop every type with Fs's methods (core 2.4, decision 0307's user values converted to Fs) from satisfying it. A user value converted to Fs and every Fs in the test world (`testworld.on()`: MemFs, FakeFs, a recording) take `fs.read(path)`, so they never map; the Go backend's Prelude_read_mapped is `fs.M_read`.
- **The mapping is made in llrt sysio.xo** (map_file, beside fs_read), not heapos.xo: heapos imports pool, which imports sysio. heapos.xo release keeps the same two sentinel words (MAPPED_PREFIX, Int.MIN, in the prefix; MAPPED_MAGIC, "XoMapped", where a big block keeps its size) and tests both first.
- **The lead is 64 KiB** (MAP_LEAD), not one page: a multiple of every page size the targets use (4, 16 and 64 KiB), so the MAP_FIXED address is aligned without asking the OS for its page size. The region is mapped anonymous read write first (the object's words live in its first 64 KiB), then the file over it at R + MAP_LEAD.
- **Counts:** obj.count_outside adds one allocation to the calling thread's heap (XO_LEAKCHECK balanced by the free); nothing for the memory budget, as the ADR says.
- **Not mapped:** sanitizer, --race and user-mode heaps (sanhook), wasm, Windows, an empty file or one of 4 GiB or more; each is `read`.
- **First users:** the darwin and ELF links' XO_SEPCOMP_STORE read (compiler/xo ld.xo, through link.xo Ctx.real_fs: xo build wraps os.fs in user Fs values, gotcha read-mapped-wrapped-fs.md); XO_STD_STORE's read (a store packed in place) and the PE link keep `read`.
