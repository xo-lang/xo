Status: Accepted (2026-10-12), stages 1 and 2 implemented in
`selfhost/macho` (asm.xo, enc.xo, cfi.xo, obj.xo, out.xo: the
assembler; lin.xo, link.xo, unwind.xo, sign.xo: the linker; main.xo:

`XO1_PATH` in `scripts/selfhost-goldens.py`; `TestSelfhostMachoXoTests`.
Stage 3 (ELF for linux/arm64) implemented (2026-10-12): elf.xo (the ELF

## Context

xo1 (`selfhost/xo`, decisions 0158 and 0174) writes arm64 assembly and
hands it to the C compiler driver, which assembles it and links it with
the C runtime (a prebuilt pack object, decision 0157). Decision 0157
noted that a compiler with no external tools needs the arm64 backend to
write object files and link them itself. The Go implementation is being
retired (decision 0150 as amended), so this is written in Xo, in
`selfhost/macho`, and xo1 calls it.

What `cc` does for a native arm64 build today (darwin/arm64, Apple clang
21, `cc -v` on `xo build --backend=arm64` of the recursion golden,
2026-10-12), with internal/build's and xo1's arguments
`-O2 -fexceptions -funwind-tables -o BIN -isysroot SDK prog.s RT.o -lm -lpthread`:

1. **Preprocess** the `.s` (`clang -cc1 -E -x assembler-with-cpp`): a
   no-op for the emitter's output, which has no `#` directives at the
   start of a line; `//` comments are dropped.
2. **Assemble** (`clang -cc1as -triple arm64-apple-macosx26.5.0
   -filetype obj -mrelocation-model pic`) into an MH_OBJECT:
   - instructions encoded, branches and `adr` within `__text` resolved;
     `adrp`/`add` with `@PAGE`/`@PAGEOFF` become ARM64_RELOC_PAGE21 and
     ARM64_RELOC_PAGEOFF12 against the target's atom (the nearest
     preceding non temporary symbol of its section, or the section's
     `ltmpN` symbol) with an ARM64_RELOC_ADDEND for the offset, except
     that temporary labels of a `cstring_literals` section stay symbols;
     `bl` to an undefined symbol becomes ARM64_RELOC_BRANCH26;
   - `.uleb128` label differences (call site tables) and `.long` label
     differences (jump tables) computed, ULEB128s minimal;
   - the `.cfi_*` directives become one 32 byte `__LD,__compact_unwind`
     entry per function (LLVM's AArch64 compact encoding: frame mode
     when the CFA is fp with the fp/lr pair at its base and callee
     saved pairs below, otherwise DWARF mode, always DWARF with a non
     canonical personality such as `_xo_personality`), and an
     `__TEXT,__eh_frame` CIE and FDE for every DWARF mode function
     (augmentation `zR`, or `zPLR` with a POINTER_TO_GOT personality and
     a pc relative LSDA; SUBTRACTOR/UNSIGNED pairs for the pc fields);
   - symbol table: locals, then the defined externals and the undefined
     symbols sorted by name; LC_BUILD_VERSION, LC_SYMTAB, LC_DYSYMTAB.
3. **Link** (`ld -demangle -dynamic -arch arm64 -platform_version macos
   26.5.0 26.5 -syslibroot SDK -O2 -o BIN prog.o RT.o -lm -lpthread
   -lSystem .../libclang_rt.osx.a`; `-lm` and `-lpthread` are libSystem
   on macOS) into an MH_EXECUTE (MH_PIE): segments `__PAGEZERO`,
   `__TEXT` (`__text`, `__stubs`, `__gcc_except_tab`, `__const`,
   `__cstring`, `__unwind_info`, `__eh_frame`), `__DATA_CONST` (`__got`,
   `__const`), `__DATA` (`__data`, `__thread_vars`, `__thread_data`,
   `__thread_bss`, `__bss`), `__LINKEDIT`; load commands
   LC_DYLD_CHAINED_FIXUPS (binds of libSystem imports and rebases of
   absolute pointers), LC_DYLD_EXPORTS_TRIE, LC_SYMTAB, LC_DYSYMTAB,
   LC_LOAD_DYLINKER, LC_UUID, LC_BUILD_VERSION, LC_SOURCE_VERSION,
   LC_MAIN, LC_LOAD_DYLIB (libSystem.B.dylib), LC_FUNCTION_STARTS,
   LC_DATA_IN_CODE, LC_CODE_SIGNATURE (ad hoc, required for arm64
   macOS). The runtime object adds what the program's object does not
   use: GOT loads (ARM64_RELOC_GOT_LOAD_PAGE21/PAGEOFF12), thread local
   variables (TLVP_LOAD_PAGE21/PAGEOFF12, `__tlv_bootstrap`),
   PAGEOFF12 on scaled loads and stores, `__literal8`, `__literal16`,
   `__DATA,__const`, `__bss`; 107 undefined symbols, all in libSystem
   (`_malloc`, `_pthread_*`, `__Unwind_*` of libunwind,
   `___chkstk_darwin`, `___stack_chk_guard`, ...).

## Decision

Three stages, each committed with its check, in `selfhost/macho` (a
package xo1 imports, with a command line of its own):

1. **Assembler** (`macho.assemble`): the subset of arm64 assembly the
   emitter writes (the instructions, directives, and relocation
   operators of every arm64 golden and of xo1's own assembly) into an
   MH_OBJECT as in step 2 above. Check: every arm64 golden assembled by
   it, linked by the system `ld` exactly as `cc` links, behaves as the
   `cc` build (`scripts/selfhost-goldens.py` with xo1 using it), and the
   `__text` bytes compared with `as`'s object function by function.
2. **Linker** (`macho.link`): the program's object and the runtime
   pack's objects (and `libxotls.a` members) into an MH_EXECUTE as in
   step 3, with libSystem imports bound through chained fixups,
   `__unwind_info` built from the compact unwind entries, and an ad hoc
   code signature (the format of Go's cmd/link
   `macho_code_signature.go`: a SuperBlob with a CodeDirectory of SHA-256
   page hashes, 4 KiB pages). Check: the arm64 goldens run identically
   with no `cc` on `PATH`.
3. **ELF** for linux/arm64 (section "Stage 3" below).

Choices made on the way:

- **Byte identical objects are the target**, not just equivalent ones:
  the assembler reproduces LLVM's section order (`__text` always
  first), its symbol registration order, its string table, its compact
  unwind algorithm, its FDE grouping and padding, and its odd
  POINTER_TO_GOT personality field (gotchas/
  llvm-symbol-order-and-personality-field.md), so any difference from
  `cc -c` is a bug the comparison shows.
- **The linker concatenates** input sections by name (no atoms, no dead
  stripping, no literal merging), allocates common symbols in
  `__DATA,__common`, moves `__DATA,__const` into `__DATA_CONST`, turns
  TLVP loads of in image descriptors into adds and the descriptors'
  offsets into template offsets, and builds `__unwind_info` with regular
  second level pages of 511 entries (DWARF mode entries hold their FDE's
  offset in the merged `__eh_frame`).
- **Imports without the SDK**: every import binds to libSystem by
  ordinal 1 (it re-exports libsystem_*), or by flat lookup when more
  dylibs are linked (std/http's Security and CoreFoundation). No `.tbd`
  is read, so linking needs no SDK; a missing symbol fails at launch.
- **LC_BUILD_VERSION 11.0/11.0** (as Go's linker writes), the deployment
  target of the pack's objects.
- **xo1**: `--as=macho` assembles in process and lets cc link;
  `--ld=macho` also links, from a pack only (the runtime object cache's
  key needs the C compiler), and writes std/time's zone data as an
  assembled object (`tz_object`) instead of `xo_tzdata.c`.

Programs that still need a C compiler with the linker in place: `use c`
sources. A build without a Go toolchain also needs `XO_ZONEINFO` for
std/time (decision 0157, next step 1).

## Stage 3: ELF for linux/arm64

What `cc` does for xo1's linux builds (decision 0174 step 5): internal/build
and xo1 write the linux/arm64 assembly only when the host is not Linux;
on a Linux host `cc -O2 prog.s RT.o -lm -lpthread` (gcc or clang) links
it with the linux pack's runtime object (decision 0157: built by zig cc
for glibc 2.31 and later, `-fPIC -moutline-atomics`) into a dynamically
linked PIE that loads libm, libpthread, libgcc_s (the `_Unwind_*` of the
runtime's personality), and libc, with crt1's `_start` and libgcc.a's
outline atomics (`__aarch64_ldadd8_acq_rel`, ...) linked in.

Decisions:

- **The same assembler, an ELF mode** (`Asm.elf`): the parser, encoder,
  and unwind directives are shared; ELF adds `.section` with flags,
  types, entry sizes and COMDAT groups, `.type`, `.weak`, `.hidden`,
  `.size`, `.xword`, `.L` temporary labels, `:lo12:`, numeric labels
  (`1:`, `1b`, `1f`, the linux emitter's exclusive loops), and `ldxr`,
  `ldaxr`, `stxr`, `stlxr`, `ldar`, `stlr`. **Byte identical to LLVM's
  ELF writer** is the target, as for Mach-O: the same registration
  order of symbols, `$x`/`$d` mapping symbols, section symbols only when
  a relocation names them, local labels relocated against their
  section's symbol, the CIE/FDE layout of MCDwarf for ELF (data alignment
  -4, pc relative 4 byte pointers, entries padded to 4 and the last to
  8), groups, symbols, relocations, and one `.strtab` in LLVM's order.
- **A dynamic glibc executable, not a static one**: no libc.a exists
  without a toolchain, and the pack's objects call glibc. The linker
  writes an ET_EXEC at 0x400000 (no PIE: no dynamic relocations for the
  program's own pointers), three PT_LOAD segments congruent modulo 64
  KiB (any arm64 page size), PT_INTERP `/lib/ld-linux-aarch64.so.1`,
  PT_DYNAMIC, PT_TLS, PT_GNU_EH_FRAME, PT_GNU_STACK. Imports are called
  through 16 byte stubs that load a GOT slot; every slot is bound at load
  time (`R_AARCH64_GLOB_DAT`, `DF_BIND_NOW`), so no lazy PLT. TLS
  descriptor and initial exec sequences are relaxed to local exec (an
  executable's TLS block is at a fixed offset from the thread pointer).
- **Versioned imports from a table**: no `.so` is read at link time, so
  `glibc.xo` holds the default version of every symbol of glibc 2.31's
  libc, libm, libpthread, and libgcc_s on arm64 (except libc's
  GLIBC_2.17 ones, the default). Unversioned imports would fail to bind
  compatibility symbols such as `__xstat` on glibc 2.33 and later
  (gotchas/glibc-compat-symbols-need-versions.md). NEEDED: libm.so.6,
  libpthread.so.0, libgcc_s.so.1 (when an import comes from it),
  libc.so.6, as Debian's gcc links.
- **Synthesized code assembled by the same assembler**: `_start` (glibc's
  crt1: `__libc_start_main(main, argc, argv, 0, 0, rtld_fini, sp)`) and
  each `__aarch64_{cas,swp,ldadd,ldclr,ldeor,ldset}{4,8}_{relax,acq,rel,acq_rel}`
  the objects call, as load and store exclusive loops.
- **.eh_frame** pieces are concatenated at 4 byte alignment (a gap of
  zeros would end the section for an unwinder), a zero terminator
  follows, and `.eh_frame_hdr` holds the sorted table libgcc's unwinder
  searches through `dl_iterate_phdr`.
- **xo1**: `--ld=macho` with `--target=linux/arm64` assembles and links
  the ELF executable from any host, with the linux/arm64 pack in
  `$XO_RTPACK`; `--as=macho` alone writes the ELF object for cc on a
  Linux host. std/time's zone data is written as ELF assembly
  (`tz_object_elf`).

Stage 3 results (bench/results/macho-2026-10-12.md, "Stage 3"):

- Objects: the 159 arm64 goldens and xo1's linux assembly (14.9 million
  lines) assemble byte identical to `clang --target=aarch64-linux-gnu -c`
  (4,159 and 3,306 functions, every section and relocation table);
  xo1's in 5.81 s instead of 33.49 s.
- Executables: all 159 goldens, linked by `macho elflink` with the pack,
  pass in debian:bullseye (glibc 2.31) and debian:trixie-slim (glibc
  2.41) containers with no C compiler, assembler, or linker.
  xo1 (built at commit cf9ab7e) with `--target=linux/arm64 --ld=macho`
  built all 159 goldens on the Mac with no cc; 133 binaries are byte
  identical to the ones that passed in both containers. The other 26 were
  not run: Docker stopped during that run (it was not restarted), and
  they differ from the harness's because its `xo asmdump .` names the
  package `.` (strings, symbols, and for two programs the frames), not
  because of the linker.
- The binaries are 11 and 6 percent smaller than gcc 14's for the same
  objects (not PIE); a `.symtab` names the functions and objects.

Stage 3 next steps, ranked by likelihood of working:

1. PIE: `ET_DYN` with `R_AARCH64_RELATIVE` for the program's absolute
   pointers (the `.data.rel.ro` and `.rodata` ABS64s), matching cc's
   default on Debian and Ubuntu, then the goldens in both containers.
2. Have `BuildRTPack` refuse an archive with fewer members than it
   archived (gotchas/apple-ar-drops-elf-members.md), or write the TLS
   archive in Go, so the clang fallback of decision 0157 needs no GNU ar.
3. `.init_array` and `.fini_array` (`DT_INIT_ARRAY`), for `use c`
   objects that have constructors, then `use c` objects compiled by a
   cross compiler into the ELF link.

## Consequences

- Stage 1: on the 158 arm64 goldens and on xo1's own assembly (13.8
  million lines), every section, function (3,792 and 2,825), and
  relocation is identical to `cc -c`'s, and all 159 objects are byte
  identical; assembling xo1 takes 4.92 s instead of 35.40 s. xo1 with
  `--as=macho` passes 158 of 158 goldens.
- Stage 2: xo1 with `--ld=macho` and an empty PATH passes 158 of 158
  goldens; xo1 links itself with no cc (B), B links C, and B and C are
  byte identical and pass 158 of 158; std/time zone data links. The
  binaries are 0.1 percent smaller than ld's; a small link is 5 times
  faster (0.010 s against 0.054 s), linking xo1 4 times slower (0.44 s
  against 0.11 s).
- A self hosted toolchain on macOS now needs only the pack, not the
  Command Line Tools; the released `xo` (Go) is unchanged and still
  uses cc (decision 0150: switching is the owner's call).
- Found on the way: a struct named `Target` anywhere in a program breaks
  the native build's predeclared `target` (gotchas/
  struct-named-target-breaks-predeclared-target.md), and the TLS
  library holds common symbols (gotchas/tls-library-common-symbols.md).

Next steps 1 and 2, done (2026-10-12, commits 9c7bee7 and 19824630;
bench/results/macho-2026-10-12.md, "Default linker and zone data"):

- **xo1's default linker on darwin is selfhost/macho** (main.xo
  `default_ld`): with no `--ld`, the host's darwin/arm64 link uses it
  when `--as` is not cc, no `use c` module is linked, and the pack has
  the runtime variant of the link's flags; otherwise cc, as before.
  `--ld=cc` forces cc, `--ld=macho` still fails rather than fall back.
  A linux host keeps cc until the ELF linker writes PIE (stage 3 next
  step 1), the cc default there.
- Goldens through xo1: 169 of 169 pass with `--ld=cc` (all linked by
  ld), with the default (all linked by selfhost/macho, 70,435,324 bytes
  against 70,509,104), and with the default and an empty PATH.
- Fixed point with the pack (bootstrap-xo.sh `XO_BOOTSTRAP_RTPACK`): s1,
  s2, s3 linked by selfhost/macho, s2 and s3 assembly (395,441,956
  bytes) and binaries (79,002,335 bytes) identical, s1 equal to s2;
  stages 751 s, 587 s, 583 s against 659 s, 586 s, 588 s for the cc run
  (`XO_RTPACK=off`; noisy machine).
- Found on the way: the `-DXO_TEXT_C` and `-DXO_STRINGS_C` scans
  matched xo1's own string literals, so xo1 linking itself silently
  fell back to cc (gotchas/runtime-flags-from-string-literals.md).
- **The archives ship `lib/xo/zoneinfo.zip`** (release.sh), which tz.xo
  `shipped_zoneinfo` reads before `go env GOROOT`: time_zones and
  time_dynamic_zone build and pass on darwin/arm64 with no Go and no cc
  on PATH. release-verify.sh checks the default, `--ld=cc`, and the
  time zone golden with no Go.

## Addendum (2026-10-16): selfhost/macho is the darwin/arm64 default again

6faa44cb (2026-10-16 05:20) made cc the default link of a darwin host
that has one, a mitigation while some ad hoc binaries waited at exec
(gotchas/amfi-gatekeeper-macho-layout.md). The two causes found since
are not macho's signature or layout: an XProtect rule matched code
loading the empty list at macho's page offset 0x880 (fixed in
5e2dd938, gotchas/xprotect-false-positive-empty-list.md), and the dev
goldens relinked a binary at a shared path while another session
started it (fixed in f949f3c5). On main at a52d5412 every internal/llvm
golden linked by macho passed three rounds (one serial, two with 8
jobs; 179 of 179 each, no run past 20 s), and none of the 179 macho
and 179 cc goldens nor xo itself linked either way matches the Mac's
XProtect rules (the live 5318 and the older bundle's). So the default
on a darwin host is selfhost/macho again whenever the assembler is not
`--as=cc` and no `use c` source is linked; `--ld=cc` selects cc. The
arm64 backend's darwin builds need no C toolchain by default.

Measured the same day (builds without the binary or back-end caches,
one at a time, other sessions running): the 179 goldens built in 234 s
with macho against 282 s with cc (median 942 ms against 1152 ms), at
1.0055 times cc's bytes (0.988 to 1.024 per program); xo itself took
114 to 122 s of CPU with macho against 154 to 159 s with cc, and 56.9
MB against 56.8 MB. Wall times of the self build varied from 26 to 57
s with the machine's load either way.

## Alternatives

- **Port the assembler and linker in Go first** (internal/arm64): the Go
  implementation is being retired (decision 0150 as amended); a Go
  version would be thrown away.
- **Ship LLVM's `llvm-mc` and `ld64.lld`**: two large binaries per
  host, and still an external tool.
- **Write the object directly from the emitter, skipping text**: the
  `.s` is the emitter's tested interface (byte identical with the Go
  emitter's); assembling it keeps that comparison and lets the
  assembler be checked against `as` on the same input.
