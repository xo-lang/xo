## Context

A REPL lets a person or an agent try a construct, a std call or a
diagnostic in seconds, without writing a program and building it. Xo
already has most of the parts:

- the checker, with stable diagnostics (spec 10);
- `xo serve` (programs kept checked in memory for check and query);
- `xo doc`, `xo type` and `xo def`;
- separate compilation, which rebuilds a one-line edit of a small
  program in well under 100 ms.

What is missing is the loop: take an entry, compile it against the
entries before it, run it, and print the result.

The lead asked for three execution models to be weighed:

1. an interpreter over Xo's SSA;
2. native code loaded into a running process;
3. a hidden rebuild and rerun of a generated program.

The lead also asked for the third to be measured against today's edit
loop. Decision 0283's compile server was never built
(0283-compile-server.md:3-6: "Not started"), so the measured loop is
the one-line edit rebuild through separate compilation.

std on every run, and its support check adds about 70 ms. Lang 4 has
the fix. A REPL checks in process through the build's path, so 12 to
21 ms is its figure.

## Decision

### Execution model: a generated program, rebuilt and rerun (stage 1)

Each session is a hidden Xo module. Its definitions (functions, types,
imports) are top-level items, and each entry so far is a statement of
a generated `main`. For an entry, the REPL:

1. adds the entry to the module;
2. checks it in process, through the same front end and caches as
   `xo build`;
3. builds with separate compilation, so only the session module is
   new;
4. runs the binary, which executes only what the new entry needs;
5. prints the entry's value and output.

The REPL needs no second engine. Entries mean exactly what a compiled
program means, on every backend and target, so an entry tried in the
REPL behaves as it will in a file. The measured cost per entry:

- the build, 66 to 80 ms for a small session;
- the first exec of the new binary: under 1 ms on Linux, and 150 to 200
  ms on macOS, which assesses every new file.

That is about 42 ms on Linux (the measured `xo run` after an edit) and
about 230 ms on a Mac, fast enough for people and for agents. An
agent's own turn takes seconds.

**Why not an SSA interpreter first.** An interpreter would have to
implement every SSA operation and every runtime intrinsic: allocation,
reference counts, strings, maps, the scheduler, and effects through
std/native. It would be a second implementation of Xo's semantics, kept
in step with the compiled one, which progen could fuzz across both. It
is the only model with no new code file per entry, so it would avoid
the Mac's assessment, and it could run in xo.wasm (a playground REPL).
Those gains are real but second order to having a correct REPL now. It
is stage 3, built if stage 1's measured loop proves too slow in use,
with its own measurement.

**Why not native code loaded into the process.** A fresh dylib pays the
same Mac assessment as a fresh binary (161 to 199 ms measured). Writing
code into executable memory instead is the JIT that wasm-and-jit.md
argues against for general use: MAP_JIT and entitlements on macOS, a
compiler inside the process. Not chosen. The narrow development-only
JIT that note allows would need its own ADR.

### State between entries: values carry, effects do not repeat

Rerunning every earlier entry for each new one would repeat its effects
(a file written twice, a request sent again) and its cost. Value
semantics avoids both:

- **Pinning.** After an entry runs, each binding it made whose type is
  plain data is printed by the program in a machine form and becomes a
  pinned binding: the next program starts with `let x = <literal>` in
  place of the entry. Plain data means scalars, `Str`, `Bytes`, `Time`,
  `Duration`, structs, enums, and lists, maps and sets of those, the
  same boundary values record and replay keeps (spec 11.3). The
  expression is not run again, so neither are its effects.
- **Bindings that hold a handle** (a file, a connection, a task, a
  closure) cannot be pinned. Their entry runs again in each later
  program, and the REPL says so once per binding, as replay reports a
  call that runs again: `re-running entry 3 for f (a File handle)`.
  `:pin off` makes every entry rerun, for a session that wants that.
- **Rebinding.** The spec makes shadowing in one block an error (core.md:1346), and a
  session is not one block. `let x = ...` for a name the session
  already binds replaces that binding: the old entry leaves the
  generated program, and later entries see the new `x`. The REPL notes
  the replacement once.
- **Redefining a function or a type** replaces its definition in the
  module. Every entry is checked again against the new definitions (in
  process, about the build's check phase). A pinned binding whose type
  was redefined and no longer fits is dropped with the checker's
  diagnostic and a note naming the entry that made it. Values computed
  with the old function keep their values, as in GHCi.
- `var` bindings pin their latest value, so assignment across entries
  works.

### Effects: all of Os by default

The generated `main` receives the full `Os`, as any program does, so an
entry may use any capability. `--effects=LIST` (for example
`--effects=stdio,clock` or `--effects=none`) declares the entries'
function with `uses (LIST)`. An entry that needs more is then rejected
by the checker's existing effect diagnostic, with no new code. Agents
trying constructs pass `--effects=stdio` to stay off the file system
and network.

### Commands and input

- An expression prints its value and type. A statement or definition
  prints nothing unless it fails.
- `:type EXPR` prints the checker's type with no run. `:doc NAME`
  prints `xo doc NAME` in the session's scope.
- `:load FILE` adds a file's definitions to the session.
- `:defs` lists the session's definitions and pinned bindings.
- `:undo` drops the last entry, `:reset` starts over, and `:save FILE`
  writes the session as an ordinary Xo program.
- `:quit` ends the session.
- **Multi-line input:** an entry continues while the parser reports an
  unexpected end of input (an open brace, bracket or string). A blank
  line ends it.
- **Errors** are the checker's own diagnostics (codes, spans, fixes),
  with spans mapped to the entry's lines. The session does not change
  when an entry fails to check. A fault while running is reported as a
  program's would be, and the entry is not kept.

### Agents: --eval and a JSON line protocol

- `xo repl --eval 'EXPR or entries'` runs entries non-interactively,
  prints the results and exits. With `--session=FILE` the session (its
  module and pinned bindings) is read from FILE and written back, so an
  agent's successive calls build on each other.
- `xo repl --json` reads one JSON object per line and writes one per
  entry:

      {"in": "..."}
      {"ok": true, "value": "...", "type": "...", "out": "...", "ms": N}
      {"ok": false, "diagnostics": [...]}

  The diagnostics use the existing JSON form (spec 10), and the
  commands above are `{"cmd": "type", "arg": "..."}`.

### Stages

1. **Prototype, `xo repl` marked experimental:**
   - expressions, `let` and `var`, function definitions and std calls;
   - pinning of plain data;
   - `--eval` and `--session`;
   - the commands `:type`, `:doc`, `:reset`, `:undo` and `:quit`;
   - tests: an `--eval` golden in cmd/xo, plus xo unit tests of the
     session module generator and pinning.
2. **The rest:**
   - a warm-up at the start of an interactive session (done
     2026-11-08, compiler/cli/repl warm_start), while the person types:
     `xo dev stdcache --conc=0` and `--conc=1` (std's two variants, in
     the foreground), then a build, in its own directory, of a session
     program with one entry, with XO_SEPCOMP_BG=0. The first entry
     waits for it, and XO_REPL_WARM=0 turns it off. A plain build as the
     warm-up was not enough: a fresh xo misses std's variants, and the
     build starts their build in a detached child that the first entry
     raced (host 1: 0.26 to 0.73 s, rising across sessions). Measured
     with scratch replwarm.sh: the first entry's build with every cache
     empty and the entry typed 2 s after the start (no session waited
     for the warm-up), 5 sessions per row:

     | | Mac (gate class) | linux/arm64 host 1 (exclusive) |
     |---|---|---|
     | no warm-up | 1,203 to 1,284 ms | 1,153 to 2,073 ms |
     | warm-up | 71 to 99 ms | 80 to 127 ms |
     | caches warm from a session without the warm-up | 209 to 236 ms | 226 to 348 ms |
     | caches warm from a session with it | 49 to 71 ms | 47 to 71 ms |

     (A session without the warm-up leaves std's variant build running
     in the background, so the next session's entries race it; host 1's
     no warm-up row is noisy for the same reason.) `--eval` starts no
     warm-up, since nothing overlaps it. cmd/xo TestReplWarmup covers
     it;
   - type definitions and redefinition. Done 2026-11-09: a definition
     replaces the session's earlier one of the same name (session.xo
     def_name: `sq`, `Point.area` for a method, `Point`). A type defined
     again unpins the bindings of the old type, whose entries run again
     with the new one; when earlier entries still do not check, the
     bindings of the type and the definitions whose text mentions it are
     dropped, each with a note ("dropped `p`: its type P changed", "dropped
     the definition of `mk`: ... define it again"), and the entry is tried
     once more. A failed redefinition leaves the session as it was.
     cmd/xo TestRepl covers a fn, a struct with bindings and a fn that
     uses it;
   - handle bindings that rerun. Done 2026-11-09: a binding whose type
     is not plain data (a handle, a closure) gets one note when it is
     bound: "`f` is a TYPE, not plain data: its entry runs again before
     each later entry (its effects too)". cmd/xo TestRepl covers it;
   - `:load`, `:save` and `:defs`. Done 2026-11-09: `:defs` prints the
     session's use lines, definitions and `let NAME: TYPE` for each
     binding; `:save FILE` writes the kept entries as typed, a blank line
     between them; `:load FILE` runs a file's entries as if typed
     (split_entries), stopping at the first that fails with the ones
     before it kept. With it, a `use` line no entry refers to yet is kept
     (its path is checked; the only error, XO0110 unused import, is not
     one here), and the session program includes a use line only once an
     entry refers to its module (before, `use` alone failed the entry).
     cmd/xo TestRepl covers them;
   - the JSON protocol;
   - `--effects`;
   - editor-style input (history, multi-line editing). Done 2026-11-09
     (the first stage 2 step, in the owner's order): on a terminal the
     REPL sets raw input (decision 0581's `Stdio.raw_input`) and edits
     each entry with compiler/cli/repl/line.xo, a key decoder and editor
     over bytes (line_test.xo runs it with no terminal): moves by
     character, word and line, kills and yank, up and down between an
     entry's lines and then through the history with a prefix search,
     Enter running a complete entry and continuing an open one, ctrl-c,
     ctrl-d, ctrl-l. Raw input is off while an entry runs, so ctrl-c
     interrupts it. The history file is `<config dir>/xo/repl_history`,
     NUL separated so an entry keeps its lines, the last 1,000;
     XO_REPL_HISTORY=off keeps none. Not a terminal: lines, as before.
     A line wider than the terminal wraps, which the redraw does not
     follow yet. cmd/xo TestReplLineEditing drives it under script(1).
     It needed seed 0.45.0, the first that knows `Stdio.raw_input`.
3. **The SSA interpreter,** only if stage 1's loop proves too slow in
   use, measured against it. It would also serve a REPL in xo.wasm.

## Consequences

- No new engine: every entry is compiled Xo, on any backend. A fix to
  the edit loop (the check cache, the link, Lang 4's work) speeds the
  REPL too.
- On macOS each entry pays about 150 to 200 ms for a new binary. The
  Developer Tools listing does not remove it (measured 2026-11-08: 149
  to 164 ms in the owner's listed terminal, 181 to 251 ms in an agent's
  shell and through heavy.sh), nor does a RAM disk or an ad hoc
  re-sign. Loading code into a running process does: a MAP_JIT copy of
  1 MB took 0.35 ms (gotchas/darwin-new-binary-first-exec.md). A
  resident runner that maps each entry's linked code that way would take
  a Mac entry to about the Linux figure; it needs a loader for xo's
  objects (relocations against the runner's runtime), its own ADR before
  any code.
- Pinning makes the session state visible and portable: `:save` writes
  it as an ordinary program, and `--session` files are plain data an
  agent can read.
- An entry with a handle is not free to repeat. The REPL says when it
  reruns one.

## Alternatives

- **An SSA interpreter first:** see above. It is the better engine for a
  wasm playground and for entries under 10 ms, and a much larger,
  second implementation of Xo. It is stage 3, if needed.
- **Native code loaded into the process (dlopen or a JIT):** a fresh
  dylib costs the same on macOS, and a JIT is what wasm-and-jit.md
  argued against. Rejected.
- **Rerun every entry from the start, with no pinning:** simplest, but
  effects repeat and the cost grows with the session. Rejected; it
  remains `:pin off`.
- **A REPL over the Go backend's record and replay:** that would answer
  effects from a trace, but it needs the Go toolchain. Native record is
  not built yet (spec 7.4, "xo run --record still uses the Go
  backend"). Rejected for now. When native record exists, it could
  replace the rerun of handle entries.
