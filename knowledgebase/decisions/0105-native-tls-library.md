# 0105: Native TLS on Mbed TLS 4.1 (not BoringSSL)

Status: Accepted (2026-10-09). Implemented in `third_party/mbedtls`
(vendored library, `mbedtls.tgz`, configuration in `xo/`),
`internal/build/tls.go` (archive cache, link flags), `std/llrt/xo_tls.c`
(certificates, roots, server and client connections, Go's error texts),
hooks in `std/llrt/xo_http.c`, `std/native/http.xo` and `rthttp.xo`.
API and behavior: decision 0106, std.md 4.6. Tests: TestTLSLibrary
(internal/build), TestArchive (third_party/mbedtls), TestTLSDiff and the
`http_tls` golden (internal/llvm, also internal/arm64's TestGoldenRun).

## Context

The native backends (arm64, LLVM, `--no-gc`) had std/http without TLS
(decision 0074); an `https` URL was XO1201 (0083). Decision 0089 made
native TLS optional for 1.0 but wanted. The runtime is one C translation
unit (`xo_rt.c` including the std files) compiled by the host's clang or
cc for darwin/arm64, linux/arm64, and linux/amd64 (native builds are
host only; Linux runs in containers or on EC2). BoringSSL was the plan.
The library has to give TLS 1.3 and 1.2, verification against the
system's roots and a custom CA with host names, ALPN (HTTP/2 later), a
license compatible with shipping it in every binary, a build the Xo
toolchain can run itself on each host, a small size, and maintenance.

## Measurements (2026-10-09, M series Mac, darwin/arm64, Apple clang 21)

Candidates fetched as release tarballs and checked by SHA-256: Mbed TLS
4.1.1 (`3359a349...375c98c`), BoringSSL at commit
`3b39936f376ed568431fd3f95c3421f5b0726e70` (2026-09-12, tarball
`54b11560...2a422`), BearSSL 0.6 (2018-08-14, `6705bba1...ff14`).

| | Mbed TLS 4.1.1 | BoringSSL (main) | BearSSL 0.6 |
|---|---|---|---|
| TLS 1.3 / 1.2 | yes / yes | yes / yes | no / yes |
| Verification, host names, ALPN, SNI | yes | yes | yes (no TLS 1.3) |
| Post quantum key exchange (Go's default X25519MLKEM768) | no | yes | no |
| License | Apache-2.0 (or GPL-2.0+) | Apache-2.0 | MIT |
| Language, build | C99; compile every `.c`, no generator (the tarball ships generated files) | C++17 since 2025 (every file `.cc`), CMake or Bazel, per platform assembly, libc++ in every link | C; make |
| Build time, all cores | 2 to 3 s (114 files) | 8.4 s (336 files) | not built |
| Hello TLS client + server (C, stripped) | 639 KB (default config) | 1.91 MB plus libc++ | not built |
| Added to an Xo std/http program (stripped) | 250 KB (LLVM), 340 KB (arm64), Xo configuration | not built into Xo | not built |
| Handshakes/s, client and server in one process, ECDSA P-256, TLS 1.3 | 449 (default config, before other load); 575 with Everest X25519 | 665 (same conditions as 449) | not built |
| API stability, maintenance | LTS branch, maintained to March 2029 | "not intended for general use", no API stability, track main | last release 2018 |

The handshake numbers were taken on a shared machine whose load average
went from about 5 to over 30 during the session (another agent's test
suites): under load the same binaries gave 97 to 119 (Mbed TLS) and 428
to 527 (BoringSSL), so only same run comparisons mean anything.
BoringSSL's ECC is assembly (P-256, X25519); Mbed TLS's is portable C.

Through the Xo HTTP benchmark (`bench/perf/http/run.sh`, users CRUD, 32
keep alive workers, 5 s, medians of 3, the same loaded machine):

| Config | HTTP req/s | HTTPS keep alive req/s | HTTPS, a handshake per request: req/s, server CPU us/req |
|---|---|---|---|
| xo (Go backend) | 91672 | 99259 | 15172, 225 |
| xo-llvm | 82952 | 81073 | 6273, 1081 |
| xo-arm64 | 86600 | 92771 | 7289, 1012 |

Over kept alive connections TLS costs little on any backend (AES-GCM in
hardware). A full handshake costs the native server about 4.5 times the
CPU of Go's (Go: assembly P-256 and X25519).

## Decision

1. **Mbed TLS 4.1 (LTS), vendored** in `third_party/mbedtls/src`
   (unmodified, `scripts/vendor-mbedtls.sh` checks the pinned SHA-256)
   and embedded in the xo binary compressed (`mbedtls.tgz`, 1.3 MB,
   regenerated by `go generate`, checked by TestArchive).
2. **Built by the toolchain on first use** per C compiler, compiler
   version, sysroot, host, and sanitizer flags into
   `<user cache>/xo/mbedtls/4.1.1-<key>/libxotls.a`, and linked (with
   `-DXO_TLS` and its headers for `xo_tls.c`) only into native programs
   whose generated code calls std/http's server or client; other programs
   compile `xo_tls.c`'s stubs. Sanitizer builds get an instrumented
   library (ThreadSanitizer found a race inside it,
   `gotchas/mbedtls-ciphersuite-list-race.md`).
3. **Configuration** (`xo/xo_tls_config.h`, `xo/xo_crypto_config.h`):
   TLS 1.2 and 1.3, ECDHE (X25519, P-256, P-384, P-521), ECDSA and RSA
   certificates, AES-GCM, ChaCha20-Poly1305, AES-CBC (Go's default
   suites), threading on, no DTLS, PSK, session tickets, renegotiation,
   debug, error texts, or file I/O. HACL* X25519 (Everest) is on: 25
   percent more handshakes than the generic ladder in the same run.
4. **System roots**: Linux reads Go's bundle files and directories
   (`SSL_CERT_FILE`, `SSL_CERT_DIR`); macOS verifies through the Security
   framework as Go does (`SecTrustEvaluateWithError`, same error mapping),
   with the framework's anchors loaded as Mbed TLS's chain.
5. Fibers: Mbed TLS calls the runtime's socket functions through its bio
   callbacks, which park the fiber while the socket is not ready, so a
   handshake waits like any socket operation and no thread blocks
   (except in the macOS verifier, as Go's does).

## Consequences

- `https` works natively on darwin/arm64, linux/arm64, and linux/amd64
  (TestTLSDiff and the goldens pass on all three, linux/amd64 under
  emulation); XO1201 for `https` literals is gone.
- The first native std/http build on a machine (and per sanitizer flavor)
  takes 2 to 3 s more; the xo binary grows 1.4 MB.
- Native handshakes cost about 4.5 times Go's CPU. Next steps if that
  matters: Mbed TLS's p256-m driver cannot coexist with other curves in
  TLS (config check error, tried), so either P-256 only builds or a
  faster P-256 (BoringSSL's or fiat-crypto's) behind Mbed TLS's PSA
  driver interface; session resumption (tickets) to skip full
  handshakes for returning clients.
- No post quantum hybrid key exchange (Go offers X25519MLKEM768 first;
  natively X25519 is agreed). Mbed TLS has ML-KEM on its roadmap; a
  switch to BoringSSL stays possible behind `xo_tls.c` (about 1500
  lines).
- Ed25519 certificates are not supported natively.

## Alternatives

- **BoringSSL**: fastest handshakes and post quantum key exchange, but
  C++ throughout (libc++ in every native binary and C++ exceptions next to
  the runtime's own unwinding, decision 0085), no stable API by design, a
  CMake or Bazel build with per platform assembly the toolchain would
  have to reproduce, and three times the size.
- **BearSSL**: smallest and MIT, but no TLS 1.3 and no release since 2018.
- **OpenSSL 3**: Apache-2.0 and complete, but a Perl configured build and
  several MB per binary. LibreSSL is the same shape.
- **wolfSSL**: GPL-3.0 or commercial: not shippable in every binary.
- **s2n-tls**: Linux only, needs a libcrypto. **rustls-ffi**: needs a
  Rust toolchain at build time.
- **Linking the system's TLS** (Secure Transport, OpenSSL `.so`):
  different behavior per OS and machine, and no static binaries.
