## Context

The owner's direction of 2026-10-30 (knowledgebase/wasm-and-jit.md,
"Direction"): Xo should fit uses that are or could be popular, and wasm
is popular for backends at the edge and in serverless platforms, as
plugins inside other systems, and in browsers. Xo compiles programs to
`wasip1/wasm` today, a WASI preview 1 core module, with its own backend
(compiler/wasm, decision 0179):

- The emitter writes WAT and asm.xo assembles it: no external tool.
- Values are flattened into wasm values (multi-value), memory is
  reference counted, and faults unwind through landing flags.
- Tasks, channels and timers run on one thread under a cooperative
  scheduler (compiler/wasm rt3.xo). It suspends by unwinding and
  rewinding the stack, as Asyncify does but generated by the backend.
- The imports are `wasi_snapshot_preview1` (fd_write, args, environ,
  random_get, clock_time_get, poll_oneoff). The module exports `_start`
  and `memory`.
- Sockets are not available: preview 1 has none, and `net_*` calls are
  refused or fault.

The serverless and edge platforms that run wasm as a backend have
mostly moved to WASI preview 2 and the component model, or are moving
there:

- A component wraps one or more core modules and declares typed imports
  and exports in WIT. The host and the component exchange strings,
  lists, records, variants and resource handles through the canonical
  ABI.
- `wasi:http` defines the HTTP server interface. In WASI 0.2 (released
  2024-01-25) the `wasi:http/proxy` world exports `incoming-handler`:
  the host calls `handle(request, response-out)` once per request.
- WASI 0.3.0 was ratified and released on 2026-06-11, with 0.3.1 on
  2026-08-11. It moves async into the component model (`async func`,
  `stream<T>`, `future<T>`) and removes `wasi:io`. Its `wasi:http/service`
  world replaces `proxy` and exports an async `handler(request) ->
  result<response, error-code>`.
- Wasmtime 46 and later runs 0.3 components by default. `wasmtime serve`
  runs both, falling back to `wasi:http/proxy` for a component that does
  not export the 0.3 world.

Where the platforms stand. Facts checked against the sources listed
below are marked; the rest are leads to confirm before stage 1:

| Platform | What it runs | Source and confidence |
|---|---|---|
| `wasmtime serve` | `wasi:http` 0.2 `proxy` and 0.3 `service` components | wasi.dev release page (checked) |
| Fermyon Spin | components with `wasi:http` 0.2 (Spin 3); a 0.3 fork existed before 0.3's release | Fermyon's "looking ahead to wasip3" post (checked); current 0.3 status unconfirmed |
| wasmCloud | components; Go via TinyGo `wasip2` and `wasi:http/incoming-handler@0.2.0` | wasmcloud.com Go docs (checked) |
| Fastly Compute | core modules with Fastly's own host calls; component support was "planned, no timeline" in a 2024 forum post | community.fastly.com (dated); 2026 blog claims of WASI 0.2 by default are unsourced |
| Cloudflare Workers | wasm called from JavaScript; WASI "experimental, only some syscalls" | developers.cloudflare.com Workers WebAssembly page (checked); no component support found |
| Envoy proxy-wasm | the proxy-wasm ABI over core modules, not components | to confirm |
| Extism | core modules with Extism's host functions (its PDKs) | to confirm |
| Browsers, Node | core modules; components through jco's transpilation | wasi.dev (jco supports 0.3) |

So the field splits in two:

- Component platforms: wasmtime serve, Spin, wasmCloud, and jco for
  JavaScript hosts. They need a component that speaks `wasi:http`.
- Core-module ABIs: Fastly's host calls, proxy-wasm and Extism. These are
  import and export conventions on a core module, closer to today's
  `wasip1/wasm` than to components.

Other languages:

- TinyGo has emitted WASI 0.2 components (`-target=wasip2`) since 0.34;
  its `wasi:http` handlers come from third-party packages
  (ydnar/wasi-http-go) or framework SDKs.
- Standard Go builds `wasi:http` components through componentize-go
  (go.bytecodealliance.org/wasi: a sync 0.2.8 `incoming-handler`, or an
  async 0.3 handler). Native `wasip2` in the Go toolchain is still
  described as upcoming.
- Rust has `wasm32-wasip2` with `cargo component`.

## Decision (proposed)

Add a second WASI target, `wasip2/wasm`, beside `wasip1/wasm`. Programs
built for it are components. The first world is `wasi:http` 0.2
`proxy`, so a program's `http.Router` serves requests from wasmtime
serve, Spin and wasmCloud. `wasip1/wasm` stays as it is:
- `xo.wasm` (decision 0405) stays a preview 1 module, because Node's
  WASI and the browser playground take only preview 1.
- The core-module platform ABIs (proxy-wasm, Extism, Fastly) build on
  `wasip1/wasm`, each a later decision of its own.

### What the backend needs

1. **The component binary, written by Xo.** asm.xo learns the component
   sections:
   - the core module itself;
   - the imported instances and their types;
   - `canon lower` for each import and `canon lift` for each export;
   - the exported instance.

   Xo's build stays free of external tools, as decision 0179 chose for
   the module. `wasm-tools validate` and `wasm-tools component wit` are
   test oracles on the host, never build steps.
2. **The canonical ABI.** Each import and export needs a lowering:
   - Strings and lists as (pointer, length) in Xo's memory, copied in
     and out. UTF-8 strings match Xo's Str.
   - Records and tuples flattened to wasm values, as the backend already
     flattens leaves. Past 16 flat parameters they go through memory,
     the canonical ABI's limit.
   - Variants, options and results as a discriminant plus a payload.
   - Resources as i32 handles, with `own` and `borrow`, and
     `resource.drop` when Xo's reference count frees the wrapper.
   - The module exports `cabi_realloc`, the canonical ABI's allocator,
     which the host uses to write into the module's memory, and a
     post-return function per export to free results.

   The backend's existing leaf flattening and `home` calls (stores
   through memory past the wasm result limit) are close to what the
   canonical ABI needs. Its parameter and result limits differ: 16 flat
   parameters and 1 flat result, not 1000. So exports and imports get
   thunks that adapt Xo's calling convention to the ABI's.
3. **The WASI 0.2 imports in place of preview 1.** A component may not
   import `wasi_snapshot_preview1`. The runtime's few imports move to
   `wasi:cli` (stdout, stderr, environment, exit), `wasi:clocks`,
   `wasi:random` and `wasi:filesystem`. The scheduler's waits move from
   `poll_oneoff` to `wasi:io/poll` over pollables.

   The Bytecode Alliance's preview 1 adapter, a separate module that
   implements preview 1 over preview 2, is the shortcut. It is rejected
   for shipped programs: it is one more module in every program and a
   third-party binary in the output. It is allowed as a stage 1
   experiment if writing the imports directly would delay the first
   number.
4. **The `wasi:http` handler.** The component exports
   `wasi:http/incoming-handler`. The generated `handle` export:
   - reads the request's method, path, authority and headers through the
     `incoming-request` resource;
   - builds an `http.Request` and calls the program's router through
     `Router.call`, std/http's in-process dispatch (spec std 4.1);
   - writes the `Response` through `outgoing-response`, `outgoing-body`,
     its `output-stream` and `response-outparam.set`.

   Request bodies are read from the `incoming-body` stream. A
   `handle_stream` route maps onto that stream directly, with no
   copying of the whole body first.
5. **How a program says it is a handler.** wasmtime serve and Spin
   instantiate a component per request (or reuse one), and they never
   call `_start`. Three ways the program could hand over its router:

   | Option | What the program writes | Notes |
   |---|---|---|
   | (a) recommended | `main` builds the router and calls a std function, e.g. `http.serve_component(r)` | the runtime stores it and the export calls it; main runs once per instance, before the first request; programs read as they do today; the router's capability capture (std 4.1) still happens in main |
   | (b) | an exported function, `pub fn handle(req: Request) -> Response` | needs a convention the checker knows |
   | (c) | a `world` declaration | follow-up, for components with interfaces other than wasi:http |

   Option (a) means a program changes one line to move between
   `http.server(l, r).serve()` on native and a component.
6. **Effects map onto imports.** Xo's capabilities line up with what a
   component imports:
   - `net.dial` (an outgoing HTTP client) imports
     `wasi:http/outgoing-handler`;
   - file reads import `wasi:filesystem`;
   - a program with neither imports neither.

   The world a component declares follows from its effects, so a host
   can see what a program can touch, as `xo vet` and `xo doc` show it
   for native programs.
7. **Tasks.** One instance serves one request at a time under 0.2's sync
   ABI. Tasks inside a handler (a fan-out of outgoing requests, a
   timeout) keep the cooperative scheduler, and its waits become pollable
   subscriptions.

   WASI 0.3's async ABI later maps onto the same unwinding. A handler
   that would wait returns to the host with the waitable it waits on
   (the ABI's callback form), and the host calls back in. That is the
   backend's suspend and resume, with the host as the scheduler.

### Why 0.2 first, then 0.3

- The platforms run 0.2 today: Spin, wasmCloud and `wasmtime serve`.
  0.3 support beyond wasmtime 46 and jco is not confirmed.
- 0.2's sync ABI needs no async canonical ABI, so the first component
  is smaller.
- 0.3 is where the standard is going. wasmtime serve runs both worlds,
  so a 0.2 component keeps working while the 0.3 world is added as a
  stage of its own.

### Staged plan

The owner decides after each stage. Every stage reports its numbers on
the linux/arm64 offload host.

1. **Hello world under `wasmtime serve` (the first measured step).**
   - A `wasi:http` 0.2 component built by Xo. Its handler returns 200
     and "hello" from a fixed router.
   - Validated by `wasm-tools validate`, run under `wasmtime serve`, and
     run under Spin if it is available on the host.
   - Measured against TinyGo (`-target=wasip2` with a `wasi:http`
     package) and Rust (`cargo component`) handlers of the same program:
     the component's size, the time to instantiate and serve the first
     request, requests per second and p50 and p99 latency under a fixed
     load (`oha` or `wrk`, `xo bench --ab` for the Xo builds).
   - Prerequisite: wasmtime, wasm-tools, TinyGo and Rust's wasm32-wasip2
     target installed on the linux/arm64 host (the lead's call: an
     infrastructure change). Neither wasmtime nor wasm-tools is on the
     Mac today.
2. **std/http over the handler.**
   - Routing, headers, query, request and response bodies (streamed both
     ways), and middleware.
   - Goldens run under `wasmtime serve` with a request script, beside
     the native goldens of the same programs.
3. **The rest of WASI 0.2.**
   - `wasi:cli`, `wasi:clocks`, `wasi:random` and `wasi:filesystem` in
     place of preview 1.
   - `wasip2/wasm` added to `--targets` and the spec's target list.
   - `wasi:http/outgoing-handler` for std's HTTP client.
   - The wasm goldens rerun on the new target.
4. **Sockets.** `wasi:sockets` TCP and UDP for std's `Net`, so database
   drivers and other clients run under wasmtime. Tasks wait on many
   pollables at once.
5. **WASI 0.3.** The `wasi:http/service` world with the async canonical
   ABI, over the existing suspension. Streams for bodies.
6. **Core-module ABIs.** proxy-wasm, Extism and Fastly's host calls, each
   an ADR of its own on `wasip1/wasm` if the owner wants that reach.

## Step 1 results (2026-11-01, Xo Lang 4)

The hello program (a router with `GET /` answering "hello") as a `wasi:http`
0.2 component under `wasmtime serve`, against Rust (`wasm32-wasip2`, the
`wasi` crate 0.14.7's bindings) and TinyGo (ydnar/wasi-http-go), on the linux/arm64
offload host, alone on it:

| component | bytes | first request, median of 5 (ms) | req/s | p50 (ms) | p90 (ms) | p99 (ms) |
|---|---|---|---|---|---|---|
| Xo | 275,013 | 15.9 | 75,620 | 0.363 | 0.703 | 1.417 |
| Rust | 79,127 | 15.2 | 85,410 | 0.320 | 0.629 | 1.296 |
| TinyGo | 2,910,541 | 23.6 | 28,109 | 1.080 | 1.727 | 2.673 |

- All three pass `wasm-tools validate`, answer 200 with the body "hello", and
  ran with 0 errors. Load: 0447's loadgen, 32 connections, 20 s, one run per
  component, so these are a first reading, not an A/B. First request: serve's
  start to the first 200, curl polling every 5 ms, so its resolution is coarse
  and most of it is wasmtime's own start.
- wasmtime serve makes an instance per request, so Xo runs main, and builds the
  router, for each request. That is in its req/s.
- Xo's 275,013 bytes are its core module, 250,019 bytes, wrapped with the
  Bytecode Alliance's preview 1 adapter (proxy variant), the stage 1 experiment
  this decision allows. wasm-tools wrote the component, not Xo: Xo does not yet
  write the component sections.
- The module's imports are named `@0.2.0`, and the host's WIT is 0.2.12. For this
  measurement the names were rewritten to 0.2.12 in the text form before the
  wrap (the functions used are the same). Pinning the WIT itself to 0.2.0 failed
  on its `@since` feature gates.
- Beyond the plan: the request's method, path, query, fields and body reach the
  router, and the response's status, fields and body go back. A response
  body is written in pieces and a request body read to its end; a `handle_stream`
  route still gets it whole.
- internal/selfhost TestWasmComponentHTTP covers this without wasmtime: a stub
  `wasi:http` host under Node, written from the canonical ABI, with an instance
  per request and with one instance for every request (the scheduler freed its
  task list without clearing it, so a reused instance trapped on its third
  request; fixed in rt3.xo).

Not done, for the owner's decision on the next stages: the component sections
written by Xo, WASI 0.2 imports in place of preview 1 (dropping the adapter),
streaming a route's body, outgoing requests, Spin (not tried).

## Next stage results (2026-11-01, Xo Lang 4)

A program that calls `http.serve_component` builds as the component itself
(with `--backend=wasm` at the time of this table, `--targets=wasip2/wasm` since). No wasm-tools and no adapter are on the build path; both
tools are test oracles only. The same hello program, setup and host as step 1,
now 3 rounds, alone on the host (medians of the rounds; first request is the
median of all 15 starts):

| component | bytes | first request (ms) | req/s | p50 (ms) | p90 (ms) | p99 (ms) |
|---|---|---|---|---|---|---|
| Xo | 257,324 | 14.2 | 81,681 | 0.347 | 0.632 | 1.270 |
| Rust | 79,127 | 14.0 | 89,238 | 0.315 | 0.584 | 1.201 |
| TinyGo | 2,910,541 | 24.4 | 29,038 | 1.062 | 1.645 | 2.347 |

- All three validate, answer 200 "hello", and ran with 0 errors. Round ranges of
  req/s: Xo 80,831 to 81,757, Rust 88,798 to 89,499, TinyGo 29,011 to 29,397.
- Xo is 8.5% below Rust in req/s, and 3.3 times Rust's size. Xo runs main and
  builds the router for each request; that cost has not been separated from the
  rest of the gap.
- The component is 6.4% smaller than step 1's adapter-wrapped 275,013 bytes.
  Step 1's 75,620 req/s was one run, and Rust also read higher today (85,410
  then), so this table does not show a speedup from dropping the adapter.
- `wasmtime serve` runs it with its default imports, without `-Scli` (the
  measurement above kept step 1's `-Scli`, TestWasmComponentServe does not). The
  component names WASI `@0.2.0`; wasmtime 50 and wasm-tools 1.263 accept that, so
  step 1's rewrite of the names to 0.2.12 is gone.

How it is built:

- `compiler/wasm/component.xo` reads the core module's imports and writes the
  component around it. It declares the interfaces it may need from
  `wasi:io`, `wasi:http/types`, `wasi:cli`, `wasi:random` and `wasi:clocks`, and
  imports an optional one only when the module uses it. An import with no
  matching interface is a build error, not a broken component.
- `canon lower` with memory and cabi_realloc needs the instance that is being
  instantiated, so as wit-component does, a shim module calls through a table,
  the program is instantiated against it, and a fixup module fills the table.
- `compiler/wasm/rt6.xo` defines the preview 1 functions the runtime calls, with
  their signatures, over WASI 0.2. stdout, stderr, the clocks, sleep and random
  work. Arguments and the environment are empty. A file operation compiled in
  returns ENOSYS (XO1515 stops a program that reaches one). proc_exit traps. A non-component build is unchanged.
- TestWasmComponentServe builds testdata/wasm_http_serve, runs `wasm-tools
  validate`, and drives `wasmtime serve`: a body past the 4096 byte write piece, a
  100,000 byte request body, a header, sleep, clocks, random, stdout and stderr, a
  404, and a route that faults, followed by a served request. It skips where the
  tools are absent, so it runs on the linux/arm64 offload hosts and not on the
  Mac; TestWasmComponentHTTP still runs the core module under Node.

## Targets, diagnostics and goldens (2026-11-01, Xo Lang 4)

The gaps the section above left, closed the same day at the lead's request.

- `--targets=wasip2/wasm` builds the component and is named alone, not in
  `all`. `--backend=wasm` alone and `--targets=wasip1/wasm` stay a preview 1
  module, so such a build of a `serve_component` program is XO1514, not a
  silent component.
- XO1515: a wasip2/wasm program that reaches files, processes or sockets. The
  module holds only what the program reaches, so a std function nothing calls
  does not count. The message names the call and a chain of functions to it.
- XO1516: a wasip2/wasm program that never calls `http.serve_component`.
- TestWasmComponentGoldens runs native goldens both ways: the golden's source
  with its main replaced, natively and under `wasmtime serve` after `wasm-tools
  validate`, with one request script for both. Status, body and header fields
  must match, except Date, Connection, Transfer-Encoding and Content-Length, and
  a gzip body compares decoded. 18 goldens run, 16 from
  internal/llvm/testdata/golden and 2 whose router is in main, ported to
  testdata/wasm_goldens; the 28 others with a router are listed with a reason
  in the test (client, connection, TLS, HTTP/2, upgrade, trailers), and
  TestWasmComponentGoldensListed fails on a new one with neither.

This found what the first version of serve_component got wrong, all fixed:
repeated fields (the second Set-Cookie was lost); `req.path` left escaped; no
host (wasmtime leaves Host out of the fields and gives it as the request's
authority, now imported); a Content-Type invented in place of the server's
sniffing, on a 204 too; `http.stream` routes answering 500; and `req.body` full
in a handle_stream route.

The hello program after these fixes, same setup as the table above, 3 rounds:

| component | bytes | first request (ms) | req/s | p50 (ms) | p90 (ms) | p99 (ms) |
|---|---|---|---|---|---|---|
| Xo | 281,733 | 22.3 | 83,339 | 0.341 | 0.616 | 1.262 |
| Rust | 79,127 | 14.0 | 89,794 | 0.313 | 0.581 | 1.187 |
| TinyGo | 2,910,541 | 24.1 | 29,114 | 1.057 | 1.644 | 2.378 |

Xo is 7.2% below Rust in req/s and 3.6 times its size; the fixes cost 24,409
bytes (9.5%), and the size has not been broken down by cause. Round ranges of
req/s: Xo 83,009 to 83,690, Rust 89,705 to 90,883, TinyGo 28,982 to 29,234. Xo's
first request is bimodal, 13 to 15 ms or 22 to 27 ms (one start 83 ms), so its
median moved from 14.2 by which side the middle start fell on; Rust's starts
are nearly all in the low group. The cause is not traced, and these starts do
not show that the fixes slowed it. 83,339 against the earlier 81,681 is not a
speedup claim either: Rust also read higher.

What a component still does not do:

- `http.stream` runs when it is called and its response goes out whole, so a
  flush reaches the client only at the end. A stream's function also runs before
  the handler returns.
- Arguments and the environment are empty, and `proc.exit` traps (the host
  answers with an error, and the next request gets a new instance): the proxy
  world has neither wasi:cli/environment nor wasi:cli/exit, checked in its WIT
  0.2.12.
- `os.stdio.read_line` faults, a 500 from a handler: std's stdin reader is the
  native runtime's, and it faults on wasip1/wasm too (`rt.sys6` at stdin.sysread). The world has wasi:cli/stdin, so this can be done, but in
  that reader rather than in rt6.xo's `fd_read`.
- The wasm goldens are not rerun on the new target, as stage 3 of the plan
  says: without a router they cannot be components (XO1516), and this decision's
  first world is wasi:http. They would need a wasi:cli/run world.
- Spin and wasmCloud have not been tried. The only real host so far is wasmtime.

## Consequences

- Xo becomes deployable to the component platforms (wasmtime serve,
  Spin, wasmCloud) with its own toolchain. `xo build --targets=wasip2/wasm`
  writes the component; nothing else is installed.
- asm.xo grows a component writer and the backend an ABI layer. That is
  a new binary format to keep correct, so `wasm-tools validate` is
  required in every component golden.
- Two WASI targets to keep working. `wasip1/wasm` stays the target of
  `xo.wasm` and of the core-module ABIs.
- New diagnostics:
  - for a program built for `wasip2/wasm` that uses what the target does
    not have, e.g. `proc.run`;
  - for a component program whose main never hands over a router.

  Each gets a new XOnnnn code, never a changed one.
- Unknown until stage 1 measures it:
  - the hello world's component size;
  - the per-instance start cost: Xo's runtime and std initialization
    plus main building the router, paid on every request where the host
    instantiates per request;
  - how both compare with TinyGo and Rust.

  A large per-instance cost would favor precomputing the router at build
  time, or instance reuse where the host allows it.

## Alternatives

- **Componentize with external tools.** `wasm-tools component new` with
  the preview 1 adapter turns today's core module into a component. That
  is the fastest way to a first component, but every program then
  carries the adapter, and the build depends on a third-party tool,
  against decision 0179. Kept as a stage 1 fallback and a test oracle.
- **The LLVM backend for `wasm32-wasip2`.** Use wasi-sdk's clang, wasi
  libc and `wasm-component-ld`. That reaches components through a large
  external toolchain and a libc, and the native wasm backend already
  carries Xo's runtime. Rejected for the same reason the wasm backend
  exists (decision 0179).
- **Stay on `wasip1/wasm`.** The core-module platforms remain reachable,
  but wasmtime serve, Spin and wasmCloud do not, and those are where
  `wasi:http` handlers run.
- **Start with WASI 0.3.** It is the standard's direction, and wasmtime
  46 runs it, but the deployed platforms are on 0.2. 0.3 comes after 0.2
  in the plan.

## Outgoing requests (owner chose this stage, 2026-11-01; done 2026-11-02)

`Client.send` and `Client.open` on wasip2/wasm reach
`wasi:http/outgoing-handler` through three runtime calls (rt5.xo
`wasi_http_send`, `wasi_http_resp_headers`, `wasi_http_resp_body`).

- **One redirect loop.** The exchange is an arm inside `http1.client_do`, so
  redirects, Authorization stripping, Referer, Net.only per hop and gzip have one
  home with native. Writing a second loop was rejected: those are security
  rules. The host follows no redirects and decodes no gzip itself.
- **Imports follow reach.** A component imports the handler and the client's
  resources only when it calls `wasi_http_send`, so TestWasmComponentHTTP's stub
  host, which has no handler, still instantiates the others.
- **The effect stays `net.dial`.** A Client keeps its declared effect, so `xo vet`
  shows what it did; sockets of its own stay XO1515.
- **Limits, recorded not hidden:** a request blocks the instance

### Sockets in a command (2026-11-03)

A command reaches the network through `wasi:sockets` 0.2 (`network`,
`instance-network`, `tcp`, `tcp-create-socket`, `ip-name-lookup`), the
first of two steps (R1; R2 is HTTP, TLS, UDP and DNS records over it): TCP listen, accept, dial
(`Net.dial`, `Net.dial_timeout`), read, write, close, connection
deadlines, `Net.lookup_host`, and `Net.only`.

- The logic that must match the native runtime is Xo:
  std/native/llrt/netwasi.xo checks Net.only (netpolicy), parses
  addresses, tries a host's addresses in turn, and records NetErr's
  status and the native runtime's texts (`listen tcp ADDR: bind: ...`,
  `dial tcp ADDR: i/o timeout`, Refused, Canceled). In a wasm module the
  SSA builder calls the native prelude's `llrt_wasi_<name>` in place of
  `rt.net_listen`, `rt.net_dial`, `rt.listener_*` and `rt.conn_*`
  (ssa/conc.xo sock_rt), so wait_call, net_result and Stream's dispatch
  are unchanged; `Net.dial_timeout`, `Net.lookup_host` and the
  set_deadline methods take a `target.arch` arm of the prelude.
- compiler/wasm rt9.xo marshals the canonical ABI and waits: a call that
  would block (accept, finish-connect, a read with no data, a write the
  stream cannot take, a lookup in progress) subscribes to its pollable,
  records it, and suspends the task; when no task can run, the scheduler
  polls every recorded pollable with `wasi:io/poll.poll` (and a clock
  pollable for the next deadline), drops them, and wakes the waiters,
  which repeat their calls. A write keeps its progress in the connection.
  Closing a listener or connection drops its waits and wakes its tasks,
  whose calls then fail with `use of closed network connection`.
- The network is granted from the component's imports, not its source:
  a component that imports `wasi:sockets/tcp` (or udp) runs with
  `wasmtime run -S inherit-network=y`, one that imports
  `wasi:sockets/ip-name-lookup` with `-S allow-ip-name-lookup=y`, and
  one that imports neither gets neither (TestWasmCommandGoldens'
  wasmNetFlags reads `wasm-tools component wit`). `xo run` builds only
  for the host, so the rule is the test runner's and the docs' until it
  runs wasm.
- Differences from native: no Unix domain sockets (`unix:` addresses
  fail with Io), no service-name ports, a wildcard listen (`:PORT`) is
  IPv6 only under wasmtime (which sets IPV6_V6ONLY) with an IPv4 bind as
  its fallback, and a canceled listen is not checked before it binds.
- TestWasmCommandGoldens now tries every golden, those wasm_unsupported.txt
  skips on wasip1 too; wasm_cmd_unsupported.txt lists the ones a command
  cannot run yet (HTTP servers and clients over raw sockets, TLS, UDP, DNS
  records: the R2 step).

### http.Server in a command (2026-11-03, R2a)

The lead approved serving HTTP in a wasip2/wasm command on one condition:
no second server that can drift from the native one. So the whole native
server runs on wasm (http.xo, http1's parsing, header handling, response
writing and error texts, which are the observable output), and only the
layer under it changes, in llrt's hconn and hserve behind
`target.arch == TargetArch.Wasm32` arms:

- Connection I/O: hconn's recv_raw, send_at and send_until read and write
  R1's wasi:sockets connection (netwasi hc_recv and hc_send, deadlines as
  relative timeouts); shut_wr does nothing (wasi:sockets shutdown is not
  imported yet); there is no idle parking (park_ready, hc_park), no peer
  address (remote_ip is empty), and no HTTP/2 (hc_h2, hc_h2c return 0).
- Records: the server, connection and sink records are wasm objects
  (rt.wasi_handle_new, with the cabi_http free hook's table index from
  rt.wasi_hook), counted by rc.inc, rc.dec and tasks.h_release's wasm
  arms (rt.wasi_rc_inc, wasi_rc_dec, wasi_h_release over the wasm object
  header: a 4-byte count and the free entry's index); obj.alloc_obj and
  free_obj use the wasm runtime's blocks (rt.heap_large, which now reuses
  freed blocks, R2a-0), and a record's hook ends with obj.free_rec.
- Tasks: Server.serve wraps its accept scope in an outer scope; on wasm
  each connection is a foreground task of that scope's group, so a stop
  ends accepting while requests in flight finish and the scope's end
  waits for them (natively hserve's connection scope and srv_wait).
- Clock: sysio.mono_ns reads the task runtime's monotonic clock
  (rt.wasi_mono_ns).

The drift test is the goldens: the same want.txt on native and on the
wasip2 command. Only http_wire, http_multipart_stream and
http_stream_body drive the server without http.Client; the other HTTP
goldens wait for the client in a command (R2b).

### http.Client in a command (2026-11-03, R2b)

A wasip2/wasm program is a wasi:http component when it calls
http.serve_component, else a command, and the client must take wasi:http
in the one and wasi:sockets in the other. The wasm backend knows the
world (`g.comp`) only after the SSA build, when the functions only the
other world's arm calls are already in the module and the backend lowers
every function. So the SSA builder decides it, as it decides
`concflag.built()` and `prof.supported()`: `native/llrt/wasiworld.component()`
folds to `Builder.wasi_comp` and only the taken arm is built. The first
build guesses a command; when it finds http.serve_component (the
backend's own test), build_program_fe builds again with the flag set, as
it rebuilds for need_conc, so only a component pays a second build. The
front end cache keys bodies by it (`comp=` in fe_own_flags).

In a command the client is the native one over R1's sockets: hclient's
wasm arms dial through netwasi.dial_addr and read and write with
netwasi's hc_recv and hc_send, so its requests and its handling of
responses are the native client's. Not on wasm yet: https (an error that
says so), HTTP/2, the connection pool (each request dials).

### TLS in a command (2026-11-03, R2d and R2e)

Crypto and the TLS protocol code already ran on wasm (their goldens pass
on wasip1); what was native only was the glue to sockets. The server's
TLS stays behind hconn.xo's ops table (srvtls.xo), which keeps TLS out of
a plain HTTP program's binary: on wasm its entries are rt.wasi_hook table
indexes, and rt.call_c2 and call_c4 lower to a call_indirect of
(i64 x 2 or 4) -> i64, so every cabi_tls entry takes exactly the Ints its
call passes and returns an Int (harmless under the C ABI natively). A TLS
read waits on a socket, so the call can suspend: it is emitted as a call
through a function value (resume point, call_indirect, suspend check),
and find_susp counts C ABI exports' FuncAddrs as targets and a call_c's
Ints as its key. (Setting Func.indirect on them instead broke rc.xo,
which takes an indirect function's first parameter for a closure's.)
tlssrv.xo and tlsio.xo read and write the connection through netwasi's
hc_recv and hc_send (their pd is the Conn on wasm); a timed read keeps
the connection's own deadline (a user's) and restores it after. The
client: hclient.start_wasm runs tlsio.client_with over the dialed Conn
(ALPN http/1.1 only), and std/tls's client takes a command's Conn
(tls.xo client_wasm) with an upgrade mark in a word of the runtime's
connection record that rt9 leaves alone (offset 44) and the connection's
deadlines for the handshake. No system roots on wasm (no store): a
client without roots verifies against none. HTTP/2 stays off on wasm
(srvh2c.fill does nothing; hc_h2 returns 0).

### Full duplex in a command (2026-11-03, R2c)

The native client sends a streamed request body from a task of a server
record's detached scope (hserve.srv_new, tasks.scope_detached), so the
response head can come before the body ends. R2a's wasm server record had
no scope (Server.serve's own scope runs the connections), so R2b sent the
body first, and hserve.srv_group, which read the missing scope, faulted.
The wasm task runtime now has a detached scope: rt.wasi_scope_new is
rt3's $scope_open under the root node (it outlives the client call that
made it) that leaves the caller's node unchanged; rt.wasi_scope_group is
its group; rt.wasi_scope_close (blocking) cancels and waits for its tasks
and restores the caller's node. srv_new stores one in SR_SCOPE on wasm,
srv_group returns its group, and srv_close and srv_free close or release
it, so Client.open's duplex path is the same on both backends. Server.serve
keeps its own scope for connections on wasm (they are foreground tasks
there, waited for by the scope's end). hserve.hc_new also sets the
connection's peer address on wasm (rt.wasi_sock_peer, tcp-socket's
remote-address), so Request.remote_addr and the proxy's X-Forwarded-For
match native.

### HTTP/2 server in a command (2026-11-03, R2f)

The native HTTP/2 connection fiber (h2srv.xo H2Conn.wait) waits for any
of three things at once: the socket's input, a stream task's wake (its
park), or a deadline (poll.pd_wait_or_signal). A wasm task can block on
one pollable, and its scheduler had no park. R2f adds the smallest pieces
that make that wait possible without changing the scheduler:

- rt3.xo wasi_park_wait(p, deadline) and wasi_park_signal(p): a park is a
  word in memory; signal stores 1 and wakes the blocked tasks (they
  retry), wait returns 1 (and clears the word) when it is set, 0 when the
  deadline passed, -1 when the task is canceled (llrt's poll.canceled
  reads a native context, so the wasm arms take cancellation from here).
- rt9.xo wasi_sock_try_read (error 105: nothing yet, never waits) and
  wasi_sock_readable (waits for input on the connection's stream under
  its read deadline, reading nothing); netwasi hc_try_recv and
  hc_readable.
- A reader task per HTTP/2 connection (h2srv.reader_wasm, started by
  http.xo h2_loop with spawn_background): it waits until the socket is
  readable, signals the fiber's park, then waits on a second park until
  the fiber has read everything (the fiber signals it before each wait).
  The fiber's reads are non-blocking (hconn.h2_read through
  hc_try_recv, and tlssrv's nb_read through the same call for TLS), as
  natively.
- Park words in the records: C_WPARK and C_WREAD in the connection
  record, S_WPARK in the stream record (wasm only, after the native
  record's end). wake, signal_stream, wait_backlog and the body read's
  wait use them on wasm in place of poll.park_of and pool.park_reset.
- A wake resumes every blocked task on wasm, so a waiting socket call
  keeps its pollable across wakes for others (the wait table's
  generation and the wait's deadline in the task record, words 208 and
  216, checked by $sk_reblock in every repeatable call; a close or a new
  deadline ends the connection's waits through $sk_unwait, which clears
  the tasks it finds in their wait table entries): subscribing on
  each wake filled the handle table (gotchas/
  wasm-wake-resubscribes-pollables.md). The park words are wasm only:
  h2srv's c_size and s_size add them after the native record's end, so
  native records keep their sizes (704 and 416 bytes).
- h2srv's connection lock (slot_cas) is never held across a wait or a
  socket write (the output is swapped out first), so on one thread it
  never contends.
- hserve.hc_h2c and hc_h2 serve HTTP/2 on wasm; srvtls.install's wasm
  table gains TO_H2 and TO_NB_READ and srvh2c's entries; R2e's filter
  that kept h2 out of the wasm TLS server's ALPN is gone. hconn.stream
  makes a stream's connection handle with rt.wasi_handle_new (a
  rt.fn_addr there faulted the first run).

The client: the native client sends one request at a time on a
connection, and its reads already wait on the socket on wasm (R2b's
fill), so it needs no reader task. hclient.start_wasm offers h2 by ALPN
(as native, unless the caller's protocols leave it out) and takes prior
knowledge (h2c), handing the dialed connection to conn_new and an
exchange as start does; there is no pool on wasm (pool_put closes the
connection, conn_free closes it through wasi_sock_close), so each
request dials, as R2b's HTTP/1.1 does.

### Connection pool in a command (2026-11-03, R2g)

http.Client in a command keeps idle connections as natively (decision
0303's HTTP/1.1 pool and the HTTP/2 one: hclient's pool at ctx.svc()'s
SV_H2_POOL, under pool.lock, which never contends on one thread since no
wait holds it). start_wasm takes an idle connection for the key before it
dials, end_keep and pool_put keep connections on wasm, and idle_ok, which
peeks the socket natively, reads one byte without waiting on wasm
(hc_try_recv: nothing there means usable; a byte, the end or an error
means the server closed or broke it, and the connection is dropped
anyway). The idle connections are not closed at exit on wasm
(atexit.set_streams takes a native function address; the instance's
sockets end with it).
