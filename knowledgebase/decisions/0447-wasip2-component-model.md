# 0447: Xo programs on WASI preview 2 and the component model (wasi:http)

Status: Accepted, direction and step 1 (owner, 2026-10-30): the hello-world wasi:http measurement first, later stages decided on its numbers; the owner approved installing wasmtime, wasm-tools, TinyGo and Rust's wasm32-wasip2 target on the linux/arm64 offload host. Proposed by xo-lang-4 the same day

## Context

The owner's direction of 2026-10-30 (knowledgebase/wasm-and-jit.md,
"Direction"): Xo should fit uses that are or could be popular, and wasm
is popular for backends at the edge and in serverless platforms, as
plugins inside other systems, and in browsers. Xo compiles programs to
`wasip1/wasm` today, a WASI preview 1 core module, with its own backend
(compiler/wasm, decision 0179):

- The emitter writes WAT and asm.xo assembles it: no external tool.
- Values are flattened into wasm values (multi-value), memory is
  reference counted, and faults unwind through landing flags.
- Tasks, channels and timers run on one thread under a cooperative
  scheduler (compiler/wasm rt3.xo). It suspends by unwinding and
  rewinding the stack, as Asyncify does but generated by the backend.
- The imports are `wasi_snapshot_preview1` (fd_write, args, environ,
  random_get, clock_time_get, poll_oneoff). The module exports `_start`
  and `memory`.
- Sockets are not available: preview 1 has none, and `net_*` calls are
  refused or fault.

The serverless and edge platforms that run wasm as a backend have
mostly moved to WASI preview 2 and the component model, or are moving
there:

- A component wraps one or more core modules and declares typed imports
  and exports in WIT. The host and the component exchange strings,
  lists, records, variants and resource handles through the canonical
  ABI.
- `wasi:http` defines the HTTP server interface. In WASI 0.2 (released
  2024-01-25) the `wasi:http/proxy` world exports `incoming-handler`:
  the host calls `handle(request, response-out)` once per request.
- WASI 0.3.0 was ratified and released on 2026-06-11, with 0.3.1 on
  2026-08-11. It moves async into the component model (`async func`,
  `stream<T>`, `future<T>`) and removes `wasi:io`. Its `wasi:http/service`
  world replaces `proxy` and exports an async `handler(request) ->
  result<response, error-code>`.
- Wasmtime 46 and later runs 0.3 components by default. `wasmtime serve`
  runs both, falling back to `wasi:http/proxy` for a component that does
  not export the 0.3 world.

Where the platforms stand. Facts checked against the sources listed
below are marked; the rest are leads to confirm before stage 1:

| Platform | What it runs | Source and confidence |
|---|---|---|
| `wasmtime serve` | `wasi:http` 0.2 `proxy` and 0.3 `service` components | wasi.dev release page (checked) |
| Fermyon Spin | components with `wasi:http` 0.2 (Spin 3); a 0.3 fork existed before 0.3's release | Fermyon's "looking ahead to wasip3" post (checked); current 0.3 status unconfirmed |
| wasmCloud | components; Go via TinyGo `wasip2` and `wasi:http/incoming-handler@0.2.0` | wasmcloud.com Go docs (checked) |
| Fastly Compute | core modules with Fastly's own host calls; component support was "planned, no timeline" in a 2024 forum post | community.fastly.com (dated); 2026 blog claims of WASI 0.2 by default are unsourced |
| Cloudflare Workers | wasm called from JavaScript; WASI "experimental, only some syscalls" | developers.cloudflare.com Workers WebAssembly page (checked); no component support found |
| Envoy proxy-wasm | the proxy-wasm ABI over core modules, not components | to confirm |
| Extism | core modules with Extism's host functions (its PDKs) | to confirm |
| Browsers, Node | core modules; components through jco's transpilation | wasi.dev (jco supports 0.3) |

So the field splits in two:

- Component platforms: wasmtime serve, Spin, wasmCloud, and jco for
  JavaScript hosts. They need a component that speaks `wasi:http`.
- Core-module ABIs: Fastly's host calls, proxy-wasm and Extism. These are
  import and export conventions on a core module, closer to today's
  `wasip1/wasm` than to components.

Other languages:

- TinyGo has emitted WASI 0.2 components (`-target=wasip2`) since 0.34;
  its `wasi:http` handlers come from third-party packages
  (ydnar/wasi-http-go) or framework SDKs.
- Standard Go builds `wasi:http` components through componentize-go
  (go.bytecodealliance.org/wasi: a sync 0.2.8 `incoming-handler`, or an
  async 0.3 handler). Native `wasip2` in the Go toolchain is still
  described as upcoming.
- Rust has `wasm32-wasip2` with `cargo component`.

## Decision (proposed)

Add a second WASI target, `wasip2/wasm`, beside `wasip1/wasm`. Programs
built for it are components. The first world is `wasi:http` 0.2
`proxy`, so a program's `http.Router` serves requests from wasmtime
serve, Spin and wasmCloud. `wasip1/wasm` stays as it is:
- `xo.wasm` (decision 0405) stays a preview 1 module, because Node's
  WASI and the browser playground take only preview 1.
- The core-module platform ABIs (proxy-wasm, Extism, Fastly) build on
  `wasip1/wasm`, each a later decision of its own.

### What the backend needs

1. **The component binary, written by Xo.** asm.xo learns the component
   sections:
   - the core module itself;
   - the imported instances and their types;
   - `canon lower` for each import and `canon lift` for each export;
   - the exported instance.

   Xo's build stays free of external tools, as decision 0179 chose for
   the module. `wasm-tools validate` and `wasm-tools component wit` are
   test oracles on the host, never build steps.
2. **The canonical ABI.** Each import and export needs a lowering:
   - Strings and lists as (pointer, length) in Xo's memory, copied in
     and out. UTF-8 strings match Xo's Str.
   - Records and tuples flattened to wasm values, as the backend already
     flattens leaves. Past 16 flat parameters they go through memory,
     the canonical ABI's limit.
   - Variants, options and results as a discriminant plus a payload.
   - Resources as i32 handles, with `own` and `borrow`, and
     `resource.drop` when Xo's reference count frees the wrapper.
   - The module exports `cabi_realloc`, the canonical ABI's allocator,
     which the host uses to write into the module's memory, and a
     post-return function per export to free results.

   The backend's existing leaf flattening and `home` calls (stores
   through memory past the wasm result limit) are close to what the
   canonical ABI needs. Its parameter and result limits differ: 16 flat
   parameters and 1 flat result, not 1000. So exports and imports get
   thunks that adapt Xo's calling convention to the ABI's.
3. **The WASI 0.2 imports in place of preview 1.** A component may not
   import `wasi_snapshot_preview1`. The runtime's few imports move to
   `wasi:cli` (stdout, stderr, environment, exit), `wasi:clocks`,
   `wasi:random` and `wasi:filesystem`. The scheduler's waits move from
   `poll_oneoff` to `wasi:io/poll` over pollables.

   The Bytecode Alliance's preview 1 adapter, a separate module that
   implements preview 1 over preview 2, is the shortcut. It is rejected
   for shipped programs: it is one more module in every program and a
   third-party binary in the output. It is allowed as a stage 1
   experiment if writing the imports directly would delay the first
   number.
4. **The `wasi:http` handler.** The component exports
   `wasi:http/incoming-handler`. The generated `handle` export:
   - reads the request's method, path, authority and headers through the
     `incoming-request` resource;
   - builds an `http.Request` and calls the program's router through
     `Router.call`, std/http's in-process dispatch (spec std 4.1);
   - writes the `Response` through `outgoing-response`, `outgoing-body`,
     its `output-stream` and `response-outparam.set`.

   Request bodies are read from the `incoming-body` stream. A
   `handle_stream` route maps onto that stream directly, with no
   copying of the whole body first.
5. **How a program says it is a handler.** wasmtime serve and Spin
   instantiate a component per request (or reuse one), and they never
   call `_start`. Three ways the program could hand over its router:

   | Option | What the program writes | Notes |
   |---|---|---|
   | (a) recommended | `main` builds the router and calls a std function, e.g. `http.serve_component(r)` | the runtime stores it and the export calls it; main runs once per instance, before the first request; programs read as they do today; the router's capability capture (std 4.1) still happens in main |
   | (b) | an exported function, `pub fn handle(req: Request) -> Response` | needs a convention the checker knows |
   | (c) | a `world` declaration | follow-up, for components with interfaces other than wasi:http |

   Option (a) means a program changes one line to move between
   `http.server(l, r).serve()` on native and a component.
6. **Effects map onto imports.** Xo's capabilities line up with what a
   component imports:
   - `net.dial` (an outgoing HTTP client) imports
     `wasi:http/outgoing-handler`;
   - file reads import `wasi:filesystem`;
   - a program with neither imports neither.

   The world a component declares follows from its effects, so a host
   can see what a program can touch, as `xo vet` and `xo doc` show it
   for native programs.
7. **Tasks.** One instance serves one request at a time under 0.2's sync
   ABI. Tasks inside a handler (a fan-out of outgoing requests, a
   timeout) keep the cooperative scheduler, and its waits become pollable
   subscriptions.

   WASI 0.3's async ABI later maps onto the same unwinding. A handler
   that would wait returns to the host with the waitable it waits on
   (the ABI's callback form), and the host calls back in. That is the
   backend's suspend and resume, with the host as the scheduler.

### Why 0.2 first, then 0.3

- The platforms run 0.2 today: Spin, wasmCloud and `wasmtime serve`.
  0.3 support beyond wasmtime 46 and jco is not confirmed.
- 0.2's sync ABI needs no async canonical ABI, so the first component
  is smaller.
- 0.3 is where the standard is going. wasmtime serve runs both worlds,
  so a 0.2 component keeps working while the 0.3 world is added as a
  stage of its own.

### Staged plan

The owner decides after each stage. Every stage reports its numbers on
the linux/arm64 offload host.

1. **Hello world under `wasmtime serve` (the first measured step).**
   - A `wasi:http` 0.2 component built by Xo. Its handler returns 200
     and "hello" from a fixed router.
   - Validated by `wasm-tools validate`, run under `wasmtime serve`, and
     run under Spin if it is available on the host.
   - Measured against TinyGo (`-target=wasip2` with a `wasi:http`
     package) and Rust (`cargo component`) handlers of the same program:
     the component's size, the time to instantiate and serve the first
     request, requests per second and p50 and p99 latency under a fixed
     load (`oha` or `wrk`, `xo bench --ab` for the Xo builds).
   - Prerequisite: wasmtime, wasm-tools, TinyGo and Rust's wasm32-wasip2
     target installed on the linux/arm64 host (the lead's call: an
     infrastructure change). Neither wasmtime nor wasm-tools is on the
     Mac today.
2. **std/http over the handler.**
   - Routing, headers, query, request and response bodies (streamed both
     ways), and middleware.
   - Goldens run under `wasmtime serve` with a request script, beside
     the native goldens of the same programs.
3. **The rest of WASI 0.2.**
   - `wasi:cli`, `wasi:clocks`, `wasi:random` and `wasi:filesystem` in
     place of preview 1.
   - `wasip2/wasm` added to `--targets` and the spec's target list.
   - `wasi:http/outgoing-handler` for std's HTTP client.
   - The wasm goldens rerun on the new target.
4. **Sockets.** `wasi:sockets` TCP and UDP for std's `Net`, so database
   drivers and other clients run under wasmtime. Tasks wait on many
   pollables at once.
5. **WASI 0.3.** The `wasi:http/service` world with the async canonical
   ABI, over the existing suspension. Streams for bodies.
6. **Core-module ABIs.** proxy-wasm, Extism and Fastly's host calls, each
   an ADR of its own on `wasip1/wasm` if the owner wants that reach.

## Consequences

- Xo becomes deployable to the component platforms (wasmtime serve,
  Spin, wasmCloud) with its own toolchain. `xo build --targets=wasip2/wasm`
  writes the component; nothing else is installed.
- asm.xo grows a component writer and the backend an ABI layer. That is
  a new binary format to keep correct, so `wasm-tools validate` is
  required in every component golden.
- Two WASI targets to keep working. `wasip1/wasm` stays the target of
  `xo.wasm` and of the core-module ABIs.
- New diagnostics:
  - for a program built for `wasip2/wasm` that uses what the target does
    not have, e.g. `proc.run`;
  - for a component program whose main never hands over a router.

  Each gets a new XOnnnn code, never a changed one.
- Unknown until stage 1 measures it:
  - the hello world's component size;
  - the per-instance start cost: Xo's runtime and std initialization
    plus main building the router, paid on every request where the host
    instantiates per request;
  - how both compare with TinyGo and Rust.

  A large per-instance cost would favor precomputing the router at build
  time, or instance reuse where the host allows it.

## Alternatives

- **Componentize with external tools.** `wasm-tools component new` with
  the preview 1 adapter turns today's core module into a component. That
  is the fastest way to a first component, but every program then
  carries the adapter, and the build depends on a third-party tool,
  against decision 0179. Kept as a stage 1 fallback and a test oracle.
- **The LLVM backend for `wasm32-wasip2`.** Use wasi-sdk's clang, wasi
  libc and `wasm-component-ld`. That reaches components through a large
  external toolchain and a libc, and the native wasm backend already
  carries Xo's runtime. Rejected for the same reason the wasm backend
  exists (decision 0179).
- **Stay on `wasip1/wasm`.** The core-module platforms remain reachable,
  but wasmtime serve, Spin and wasmCloud do not, and those are where
  `wasi:http` handlers run.
- **Start with WASI 0.3.** It is the standard's direction, and wasmtime
  46 runs it, but the deployed platforms are on 0.2. 0.3 comes after 0.2
  in the plan.
