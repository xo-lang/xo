# 0576: std/url gains Go's URL type (Parse, String, ResolveReference, JoinPath)

Status: Accepted (owner, 2026-11-08, on the lead's recommendation). Proposed (Xo Lang 3, 2026-11-08; owner decides, design only: no code until the owner answers)

## Context

std/url (decision 0279) has net/url's escaping and `Values` but no URL type. Two other places fill the gap:

1. **polarbearblog `libs/sanitize/neturl.xo`** (465 lines plus a 128 entry table): Go 1.26's `url.Parse` and `URL.String`
   (BSD-3, attribution kept), written for the bluemonday port. It has `Url{scheme, opaque, user, host, path, fragment, raw_query,
   raw_path, raw_fragment, force_query, omit_host}`, `parse_url` (Go 1.16 colon rule, `urlstrictcolons=0`) and `parse_url_strict`
   (Go 1.26's default), `escaped_path`, `escaped_fragment`, `string`. Proven against net/url on two generated corpora of 2,987 URLs
   each (parse result, `String`, scheme, host, raw query; with and without `urlstrictcolons`). Its header says "kept until std/url
   grows a URL type".
2. **std/http's `Url`** (`http.parse_url`, decision 0358): `{scheme, host, port: Int?, path, query: Map[Str, Str]}`. It serves the
   HTTP client and reverse proxy, and is lossy for anything else: no userinfo, no fragment, no opaque form (`mailto:`), the query
   is a `Map` (repeats and order are lost), the path is decoded with no raw form, so it cannot write back what it read.

Every port of Go code that touches URLs (the Azure and AWS SDKs, the blog's sanitizer, goversioninfo's links) needs the Go
type: `u.Hostname()`, `u.Port()`, `u.Query()`, `u.ResolveReference(ref)`, `u.JoinPath(...)`, `u.IsAbs()`, `u.Redacted()`,
`u.RequestURI()`.

## Decision (proposed)

Add to std/url (declaration `std/url.xo`, implementation `std/native/url.xo`, listed in `std/go_compiled.txt`):

- `struct Url` with the fields above (Go's `URL`; `user: Userinfo?`), `struct Userinfo {username, password, password_set}`,
  `struct ParseErr {op, url, msg}` displaying as Go's `parse "x": ...` (and `Url`'s methods on it as Go does).
- `url.parse(raw: Str) -> Url ! ParseErr`, `url.parse_request_uri(raw)`, `url.join_path(base: Str, elem...)`.
- Methods: `string`, `redacted`, `is_abs`, `query() -> Values`, `hostname`, `port`, `request_uri`, `escaped_path`, `escaped_fragment`,
  `resolve_reference(ref: Url) -> Url`, `parse_ref(s: Str) -> Url ! ParseErr`, `join_path(elem...) -> Url ! ParseErr`,
  `set_path`, `set_fragment` (the raw form kept, as Go's `setPath`).
- The code is the sanitize port moved in (its corpora move with it, regenerated by `go run ./scripts/stdcorpus url` against
  net/url, Go's `url_test.go` cases ported with attribution), plus what it lacks: `ResolveReference`, `JoinPath`, `Redacted`,
  `RequestURI`, `Hostname`, `Port`. Fast paths as Go has them (the `shouldEscape` table lookup, `String`'s builder), and a
  timing row against Go's `net/url` beside the corpus.
- `libs/sanitize` imports std/url and deletes `neturl.xo` and `neturl_table.xo`; the Go backend compiles the module from the
  native source.
- `http.Url`, `http.parse_url`, `UrlErr` stay as they are (their decision, 0358, and every caller); a later decision can
  make the client take `url.Url`. No behavior of an existing std module changes.

## Questions for the owner

1. **The colon rule.** Go 1.26 rejects a host with several colons unless the scheme is postgres (`urlstrictcolons=1`); a program
   built with `go 1.16` in go.mod gets the old rule (the blog's). Recommendation: `url.parse` is Go 1.26's strict rule, and
   `url.parse_loose` (the sanitize port's `parse_url`) is kept for ports that must match an older go.mod; no GODEBUG emulation.
2. **Naming.** `url.Url` (Xo's `Request`, `Url` style, as `http.Url`) against `url.URL`. Recommendation: `Url`.
3. **http.Url.** Keep as is (recommended, nothing breaks), or deprecate it in favor of `url.Url` once the client accepts one?
4. **Scope.** `UnmarshalBinary`, `MarshalBinary` and `url.Userinfo` constructors (`UserPassword`) are left out; say if a port
   needs them. `JoinPath`'s `path.Join` cleaning needs std/path's `clean`, which exists.

## Consequences

- One URL implementation in std instead of the sanitize copy, and the SDK ports stop hand rolling `Hostname` and `Port`.
- Cost: about 500 lines of std moved from the blog, the new methods (about 250 lines), a corpus and a `std/changes/url.md`
  entry; spec/std.md 20 gains the type and its methods.
- Risk: Go's `String` and `JoinPath` have many corner cases (opaque URLs, `//` paths, leading `./` segments); the corpus
  against net/url is the proof, as for the sanitize port.

## Alternatives

- **Leave it in the blog's library** (status quo): each port copies 465 lines.
- **Grow `http.Url`**: it is shaped for the client (decoded path, `Map` query, `port: Int?`); adding raw forms and userinfo
  changes a type every client and proxy caller uses, for a type that is not Go's.
- **Wrap Go's `net/url` through `use go`**: only the Go backend; native and LLVM would have no URL type.
