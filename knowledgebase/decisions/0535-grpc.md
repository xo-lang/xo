# 0535: std/grpc, gRPC over std/http's HTTP/2

Status: Accepted (owner, 2026-11-06; built in part: unary and streaming calls, deadlines, grpc-go interop; open items in std/changes/grpc.md)

## Context

The owner approved (2026-11-06, relayed by the Lead) gRPC as the second of three std modules after protobuf (decision 0530):
unary and the three streaming modes, status codes, metadata, deadlines carried through task cancellation, with interop
against grpc-go. OTLP export for std/trace and metrics follows and needs both. Xo has HTTP/2 in std/http (client and
server, trailers, h2c) and structured tasks with cancellation (std/task), which are the two things gRPC needs.

## Decision (proposed)

1. **std/grpc** has a client and a server over one HTTP/2 stream per call, using std/http's h2 streams (no new transport):
   `application/grpc` content type, the 5 byte message frame (compressed flag plus big endian length), request headers
   `te: trailers`, `grpc-timeout`, `grpc-encoding`, `grpc-accept-encoding`, custom metadata as headers (`-bin` values
   base64), and `grpc-status`, `grpc-message`, `grpc-status-details-bin` in the trailers (or in the headers of a Trailers-Only
   response).
2. **Status**: `grpc.Code` is the 17 canonical codes (OK to UNAUTHENTICATED) and `grpc.Status{code, message, details}` the
   error of every call; HTTP statuses map to codes as grpc-go does for non gRPC responses.
3. **Calls**: unary, server streaming, client streaming and bidirectional streaming. A stream is a value with
   `send(m)`, `recv() -> M? ! Status` (None at the end of the stream) and `close_send()`. Messages are any type that derives
   `Proto`; a method is described by its path `/pkg.Service/Method` and the two message types.
4. **Deadlines and cancellation**: a call runs under a `task.Group`. `with_timeout` sets `grpc-timeout` and the server
   cancels its handler's group at that deadline (DEADLINE_EXCEEDED); cancelling the client's group sends RST_STREAM
   (CANCELLED) and cancels the server handler.
5. **Services from a .proto**: `xo proto gen` (decision 0530) writes, for each `service`, a client struct and a server
   interface plus a `register` function, so a handler is a plain Xo function.
6. **Out of scope for the first landing**: compression other than identity and gzip, load balancing and name resolution,
   interceptors beyond a simple middleware list, reflection, health checking (a small follow up), TLS beyond what std/http
   already offers.
7. **Maturity** (decision 0461): Solid on all three axes. Interop is the differential: a grpc-go server and client (own Go
   module under internal/stdtest/grpcref, like protoref) exercise every call shape, status code, metadata case and a
   deadline, both directions; the frame and trailer parsers are fuzzed; a timing row compares unary and streaming
   throughput with grpc-go.

## Consequences

- gRPC needs protobuf's `derive Proto` and std/http h2 trailers, both present once 0530 lands.
- Streams hold an HTTP/2 stream and a flow control window: back pressure is the stream's, a slow receiver blocks `send`.
- A new std module with a change log, a coverage row and an `xo proto gen` extension.

## Alternatives

- **Hand rolled framing over raw h2 in each user program**: rejected; every service would repeat the trailer rules.
- **Port grpc-go whole**: rejected; its balancer, resolver and interceptor machinery is far larger than the wire protocol
  the owner asked for.
