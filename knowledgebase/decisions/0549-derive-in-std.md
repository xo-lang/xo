# 0549: derive Proto and derive Xml expand in std modules

Status: Accepted (owner, 2026-11-11; low priority: after ADR 0603 stage 1 and the std coverage work). Was: Proposed (Xo Lang 3, 2026-11-07; a later item, after ADR 0546's hand written std/protowkt and std/protodesc)

## Context

`compiler/check/load.xo` expands `derive` clauses only for modules that are not std (`!c.mods[m].is_std`, in `parse_into` and in the loader of decision 0388's records closure): a std module's `derive Proto` or `derive Xml` struct gets no generated functions (XO0427 at the caller). So std cannot hold generated message types. ADR 0546 therefore hand writes std/protodesc (descriptor.proto's messages) and std/protowkt (the well known types), and std/otlp writes its encoder by hand. The owner prefers generated over hand maintained code.

## Decision (proposed)

1. Expand `derive` in std modules like any module's: the expansion is part of the module's records (decision 0388) so a build that loads std from records sees the generated functions.
2. std/protowkt and std/protodesc convert to `derive Proto` structs (generated by `xo proto gen` from google/protobuf/*.proto and descriptor.proto, checked in), their hand written codecs deleted once the corpora (byte for byte against protobuf-go) pass unchanged.
3. std/otlp may use message structs instead of its direct builder writer only if the timing row does not regress.

## Consequences

- Compiler change: selfbuild, codegen and wasm gates; the records format may need the expansion's declarations (cache key bump).
- Removes hand maintained codecs (about 600 lines for protodesc, the WKTs' codecs).

## Alternatives

- Keep hand written codecs: works, but each new std message type costs a codec and its tests.
- Generate the codecs with a script into std/native files: a second generator beside `derive`, rejected for duplicating compiler/check/derive.xo.

## Progress

- 2026-11-11 (Xo Lang 3), items 1 and 2 for std/protowkt: compiler/check/load.xo
  expands `derive` in every non signature file, std modules included (both
  sites: parse_into and the records closure's loader); the expansion is
  re-made from source when a build loads std from records, so the records
  format is unchanged (no cache key bump). A probe module with a `derive
  Proto` struct encoded and decoded the same on arm64, llvm and the Go
  backend, cold, warm, and after an edit. std/protowkt's Timestamp,
  Duration, Empty, FieldMask, Any and the nine wrappers derive Proto;
  their hand codecs are gone (encode_NAME and decode_NAME call
  protobuf.marshal and unmarshal). The fields protobuf-go types int32 or
  uint32 became Int32 and UInt32, since derive Proto maps Int to int64
  and the hand reader's int32 truncation had no other place; std/protojson
  (the one user) converts. The corpus gains a WIDE table of wire Go never
  writes (wide varints, Empty with unknown fields), which the hand Empty
  failed. Struct, Value and ListValue stay by hand: Value is a oneof enum
  holding the other two, a message with one oneof field and no other,
  which a derive struct would wrap in a new type. Next: std/protodesc
  (item 2's second module), then item 3 (std/otlp, only if its timing row
  does not regress).
- 2026-11-11 (Xo Lang 3), item 3: std/native/otlp's trace export writes
  derive Proto structs (ExportTraceServiceRequest to AnyValue, the value
  a oneof enum that itself derives Proto); bench/perf/otlp traces 0.869
  of the hand writer's wall time on linux/arm64 host 1, the same bytes
  (bench/results/otlp-derive-2026-11-11.md), so the condition holds.
  Metrics export stays on the writer for now (next: the same for it,
  with its own timing row).

## Owner decision, 2026-11-11

std/protodesc stays hand written (option a): proto2 presence as derive Proto would express it (Option fields) would break protoparse, protojson and gRPC reflection. protowkt and the rest of this decision proceed.
