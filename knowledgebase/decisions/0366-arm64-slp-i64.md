# 0366: two-lane Int word loops on arm64 (a widening pass for SWAR map loops)

Status: Proposed (Xo Lang 1, 2026-10-24; for the owner via the lead;
nothing built)

## Context

The native-vs-LLVM instruction sweep of bench/perf on main 9706c67e4
(2026-10-24, one xo, every measure.sh with arm64 and llvm; notes
sweep-native-vs-llvm-2026-10-24.txt) has unicode upper at 1.956 and
lower at 1.914 times LLVM's instructions (wall 1.50 and 1.51 on a busy
machine), upper_az and lower_az at 1.57: the largest gaps left. The std
is the same on both sides, so the gap is code generation.

Where the time goes (XO_PROF, the upper workload run 100 times longer):
native spends 92 of 199 ms in obj.fold_copy (inlined into
rs_append_bytes; there is no call per rune: obj.subw is an inlined
line), LLVM 51 of 136 ms in the same function. fold_copy's loop reads a
word of the source, finds its ASCII letters with a SWAR range test
(between8 on the seven bit copy, the high bits masked), adds or
subtracts 0x20 at each letter byte, and stores the word to the
destination. LLVM's loop vectorizer runs it 64 bytes a pass: `ldp q`,
the range test as `add.2d`, `sub.2d`, `bic.16b`, `and.16b`, `ushr.2d
#2`, a select, `stp q`; about 52 instructions for 8 words, 6.5 a word.
Native runs it a word at a time, 21 instructions a word.

slp_f64 (decision 0323) pairs isomorphic Float operations on adjacent
lanes in straight line code, with a wide V register class (its stage 1,
built: G.wide, q loads and stores, wide spills, regalloc). It finds
nothing here: fold_copy's loop body has one load and one store, so
there is no pair until the loop itself is widened.

## Decision (proposed)

A MIR pass, `widen_i64`, in compiler/arm64 (passes.xo, after
instruction selection, before register allocation, beside slp_f64),
that widens a counted word map loop to two lanes, reusing 0323's wide
vreg class.

1. The loop shape: a one block body (its fault paths cold) of a loop
   whose induction variable i steps by 8 while at least 8 bytes remain,
   with loads `ldr x, [src, i]` and stores `str x, [dst, i]` at the
   same i, and only Int operations between them from the set add, sub,
   and, orr, eor, bic, lsl/lsr/asr by a constant, mvn, and selects on a
   loop invariant condition (fold_copy's mode, unswitched first); no
   call, check, or other memory access. A store base that may overlap
   a load base is refused, unless the loop is guarded by an overlap
   test (rs_append_bytes' overlaps, the case here) or the bases are the
   same and each lane reads its own word before writing it.
2. The widened loop steps by 16: `ldr q`, each operation's `.2d` or
   `.16b` form (add.2d, sub.2d, and.16b, orr.16b, eor.16b, bic.16b,
   ushr.2d, shl.2d, sshr.2d, mvn.16b), loop invariant words broadcast
   once before the loop (`dup v.2d, x`), `str q`. The scalar loop stays
   after it for a last single word, and the byte tail stays as it is.
3. A data dependent `if` on a word (fold_copy's `if letters != 0`,
   which skips an add of 0) becomes the unconditional form when the
   skipped operation is the identity on that lane (an add or subtract
   of a value that is 0 when the condition is false); anything else is
   refused.
4. Later, and only after 1 to 3 measure: four lanes (two q registers a
   pass, `ldp q`/`stp q`) as LLVM does, and the search loops (scan.span,
   jsontext.str_end, mem_byte), whose early exit needs a combined test
   of the lanes (`umaxv`, or an `orr` of the two halves) and a scalar
   rescan of the pair that matched.

Not widened: anything on x86_64 (SSE2 is a separate decision; the pass
checks g.x86), anything under XO_PASSES=-widen_i64 (the build stays
correct), and loops with a call or a fault path in the body.

## Candidate loops

- obj.fold_copy and obj.fold (Str.to_lower and to_upper, and the folded
  compares): the unicode upper, lower, upper_az and lower_az rows.
- Map loops of the same shape elsewhere in std/native/llrt, to be
  listed by the pass's own counter (a build of xo and of bench/perf
  with a dump of the loops it widened) before any claim. The SWAR mask
  users are scan.xo (span, stops8, mem_byte, find_short, hex4,
  ctl_at), jsontext.xo (str_stops, str_end, enc_stops), fsops.xo
  (find_newline) and obj.xo (fold, fold_copy); most of scan's and
  jsontext's are search loops (step 4), not map loops.
- Keccak's and SHA-512's 64-bit lane code is straight line, not a loop:
  that is slp_f64's shape on Int, a separate stage only if its rows show
  a gap (digest sha256_big is 1.061; the other digest rows are below
  LLVM's).

## Expected gain

On fold_copy's loop with two lanes: about 12 instructions for two words
(ldr q; the range test's and, add, sub, bic, and, and; ushr; the add or
subtract; str q; the induction step and the branch) against 42 now, so
the loop at about 0.3 of its instructions, and the unicode upper and
lower rows from 1.95 to about 1.1 of LLVM's instructions; the rest is
the per-call setup and the bench's checksum. Four lanes would close
most of what remains.

## Measurement plan

1. Before building: hand-write the two-lane loop as an arm64 assembly
   function called from a scratch Xo program (the unicode bench's
   input), against the native and LLVM builds, with `xo bench --ab` in
   a quiet window. If the hand loop does not beat native's by 2x on the
   loop alone, stop and record it here.
2. Stage 1 (the pass on fold_copy and fold only): every arm64 golden
   with XO_INLINE_STRICT=1; a new golden of case folding at every
   length 0 to 40 and every alignment, overlapping and not (the tail,
   the scalar remainder word, a letter at each byte position, 0x40,
   0x5B, 0x60, 0x7B, and bytes from 0x80 up); the fixed point; the
   Docker amd64 sample (the pass must not run there); quiet `xo bench
   --ab` windows on bench/perf unicode (every row), text, json and
   strsplit against the parent.
3. Stage 2 (other loops the counter lists): the same, per loop.
4. Code size, xo's __text native and LLVM (split 12, no LTO), and a cold
   self build's time (the pass's cost).

## Consequences

- A second use of 0323's wide register class: Int values in V
  registers, never live across a call (every V upper half is caller
  saved on AAPCS64).
- A loop form the pass recognizes, not one users write: a hand
  rewrite of a std loop can still beat it; the pass is the general fix
  for the loops nobody rewrites.

## Alternatives

- A std rewrite of fold_copy's scalar loop (the mode select unswitched,
  `((letters >> 7) & mask) * 32` as `letters >> 2`, a `bic`): about 20
  to 25% fewer instructions in the loop, still about 2.5 times LLVM's a
  word. Handed to DS-1, whose code it is, on 2026-10-24; it stacks with
  this.
- A runtime intrinsic, rt.bytes_fold16 (a NEON case fold of 16 bytes,
  with wasm and amd64 lowerings): narrow, one loop, and a lowering per
  backend; the pass covers the loop shape instead.
- Leave it: native unicode case mapping stays at about 1.9 times LLVM's
  instructions.
