# Measuring xo's own speed needs each xo built by itself

Status: Observed (2026-11-04)

Symptom: a cold `xo test --std-module=native/json` --ab against 0.38.1
was 1.13 to 1.14 in instructions on the Mac for every xo from 1f648265b
(decision 0488's ShareIn) on, but 0.997 and 0.993 (within noise) on the
linux/arm64 offload host with xobuild's seed-built xos; the linux run was
reported as "the regression is darwin only", then withdrawn as a
seed-built measurement. With each xo built by itself (bootstrap s2) linux
still read 1.008, and that was right too: this regression turned out to
be in the code xo emits (made_here's 1,000 step limit put a ShareIn on
2,059 pushes of std json's GO_CASES constant, fixed in fbd8b4d2e), which a
seed-built xo shows as well. What hid it on linux: the base called
"0.38.1" there was host 1's /work/l4base/bin/xo, which reports 0.38.1 but
is a WIP commit (a93b009cf) built by a seed chain hop (`xo version -m`:
XO_BUILT_BY .../xo-hop1), with an emit phase of about 580 ms for that
test; the published 0.38.1 (370 to 375 ms) and an s2 of v0.38.1 (371 to
373 ms) are as fast as main with the fix (379 to 383 ms), and the 0.39.0
candidate, which has the regression, 573 to 575 ms (linux/arm64,
2026-11-04). Check `xo version -m` (XO_COMMIT, XO_BUILT_BY) of any xo used
as a release base; a release's archive is checked against its SHA256SUMS.

Cause: `go run ./scripts/xobuild` (and ab-host.sh's own builds) compile
the xo under test with a seed or an earlier xo. That xo then emits the
change's code for the programs it builds, but its own machine code was
generated by the seed, without the change. A change to code generation or
the runtime that makes xo itself slower (or faster) is invisible in a
measurement of xo's own speed (a cold build or test, the self build) taken
with seed-built xos; the Mac's bisect xos had been built differently.

Fix: when the claim is about xo's own speed, measure xos each built by
itself: `scripts/bootstrap-xo.sh SEED OUT` and use OUT/s2/xo (s1 built by
the seed, s2 by s1, so s2's code is the change's own), on both sides.
A claim about the code xo emits for a program (bench/perf rows, ab-host
PROG) is unaffected: there each side's xo compiles the program with its
own code generation, whatever built xo.

And a flat result against a release can hide a regression that an
unrelated gain since that release cancels: bisect or compare against the
change's parent, and look at the phase that moved (`--phase-times`)
before calling a result platform specific.
